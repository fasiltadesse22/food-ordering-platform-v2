# C1.2-P18 — Actual PostgreSQL Conflict and Failure Experiments

Protocol per selected experiment: Engineering question -> Hypothesis -> Prediction -> Setup -> Controlled variable -> Execution -> Observation -> Evidence -> Interpretation -> Limitations -> Conclusion.

Infrastructure: PostgreSQL 16 Testcontainers, Flyway V1/V2/V3, actual PostgresOrderRepository version CAS, actual OrderWorkflowService/ModifyOrderService, actual immutable Order. No fake PostgreSQL server. The synthetic interleaving wrapper is explicitly a test-only scheduler; database commits themselves are real. Commit-response loss simulation is test-only, not a real network partition.

E1 Compatible interference: Q can lifecycle acceptance survive a payment milestone? H old acceptance v1 CAS conflicts, new PLACED v1 remains acceptable. Predict second read and save to ACCEPTED v2 retaining PAYMENT_RECORDED then RESTAURANT_ACCEPTED. Inject independent real repo.saveCurrent(PAYMENT_RECORDED) immediately before first acceptance save; assert two reads/saves, version2 and history both. Evidence actual PostgresOrderConflictResolutionTest.
E2 Incompatible interference: Q can acceptance be illegally replayed after competing rejection? H stale CAS prompts reread, domain now rejects. Predict ILLEGAL_TRANSITION, one service save, version1 rejected Order; test injects independent REJECTED commit after old read.
E3 Bound: Q can repeated compatible interference spin indefinitely? Predict after two forced stale conflicts, exactly two reads/two saves, Rejected(STALE_ORDER_VERSION), no third attempt. Inject two local payments; test records two local payment occurrences as *other* requests, not replay effects.
E4 Payment safe default: Q will local milestone auto retry on stale? Predict no, STALE_ORDER_VERSION after one read/save and one independent persisted payment fact; test proves policy boundary, not provider charge.
E5 Replace lines: Q will stale customer replacement override newer payment history? Predict one conflict, no automatic merge, original lines remain, payment occurrence preserved; test checks real Postgres DB.
E6 Commit uncertainty: Q when real DB commit succeeded and response is lost, does application auto replay? Test wrapper delegates real version-CAS and real COMMIT then throws OrderCommitOutcomeUnknownException; assert one delegate save, version1 and single acceptance, exception propagates. Controlled response-loss not a real network partition; inherited P15 test separately injects after Connection.commit.
E7 Lock contention: real first JDBC transaction holds UPDATE root row; a separate repository writer sets lock_timeout 200ms; actual PostgreSQL returns 55P03, repository maps OrderDatabaseConcurrencyException.Kind.LOCK_NOT_AVAILABLE, no automatic business replay; first transaction rolled back and version stays0.
E8 Serialization: actual PostgreSQL repeatable-read writer fixes snapshot at revision0, independent repository commits acceptance revision1, first writer attempts conditional version0 update and PostgreSQL returns SQLState 40001, repository maps SERIALIZATION_FAILURE, winner persists. A JDBC proxy only schedules snapshot+competitor commit in the writer's session; conflict is raised by real PostgreSQL.

Evidence is specific to observed tests and full CI; final exact SHA to be added by verifying CI. Inherited P17 unchanged before-state checkpoint demonstrates stale version rejection. Inherited P15 and P16 tests continue to prove atomicity and coherent snapshots. No stable per-command key, provider dedup, durable response replay or generic DB transaction retry implementation claimed. Measurements absent: production p99, conflict rate, deadlock/lock timeout frequency, hot Order contention. One extra attempt may increase latency and database calls; retry budget needs future operational measurement. Following P19 can measure contention; later external provider work requires operation-specific duplicate/unknown-commit design.
