# C1.2-P18 — Production Conflict / Retry Diagnostic Runbook

1. Symptom: high HTTP409, intermittent HTTP5xx, lost response, or duplicate local milestones/provider complaint. Do not infer cause from status code alone.
2. Scope: OrderId, lifecycle command, local revision expected/actual where known, caller request ID, deployment version, PostgreSQL session identifiers, SQLState, time window, concurrent operators.
3. Timeline: last coherent read -> domain decision -> root conditional UPDATE -> child SQL -> COMMIT attempted -> response acknowledgement -> client retry. Identify which steps are evidence and which are hypothetical.
4. Competing hypotheses: P17 stale CAS, P16 torn read (guarded), P15 commit uncertainty, SQL 40001, 55P03, 40P01, duplicate command replay, direct legacy SQL bypass of version, external Payment provider divergence, client using old form.
5. Discriminating tests: compare root version and ordered local workflow via new read; inspect competing command; reproduce shared-source interleaving; inspect SQLState and PostgreSQL pg_stat_activity/pg_locks; check whether COMMIT actually issued; inspect any provider reference separately. Never read current Order version alone as proof of which logical request committed.
6. Mitigation:
  - Fresh local lifecycle stale CAS: at most one re-evaluation if current implementation has no external effect and domain still legal; else reject.
  - Stale line replacement or local payment/refund: no blind retry; caller reconciliation/new explicit intent.
  - 40001/40P01: transaction aborted; new complete transaction may be eligible under domain-specific retry policy; current project classifies and propagates rather than auto retry.
  - 55P03: lock pressure; investigate wait times and hot Order, not equivalent to business guard.
  - COMMIT unknown: do not assert rolled back; look for stable operation identity and committed authoritative fact; no automatic replay.
  - External provider: local Order milestone is not charge/refund authority. Never issue another provider charge solely due to an Order exception.
7. Validate: inspect exact version/status/lines/history of authoritative Order after failure; replay controlled P18 Testcontainers experiment; compare new vs old CI, error count and attempt budget, ensure P12 SIGKILL recovery and P15 atomicity still hold.
8. Observability: count stale conflicts, fresh-state reevaluations, ended-as-domain-rejections, exhaustion, 40001,40P01,55P03, commit_unknown, p95/p99 durations. Avoid sensitive customer/payment data in logs. SLOs absent: do not invent numbers.
