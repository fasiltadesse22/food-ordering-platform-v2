# C1.2-P22 — Production Diagnosis: Cross-Cutting Order Invariant, Concurrency and Authority Incidents

Use sequence: Symptom -> Scope -> Timeline -> Evidence -> Competing hypotheses -> Discriminating test -> Mechanism -> Causal chain -> Mitigation -> Validation.

Case A "Accepted Order cannot be loaded":
Scope OrderId, version, raw orders status, ordered history rows, caller/deployment, write path.
Hypotheses domain-invariant breach after independently committed status/history; mapper positional gap; torn read (P16), legacy/manual SQL bypass, incompatible migration.
Test: read 3 raw tables in coherent snapshot, reproduce P20 status-first/history-first, inspect mapper error. Invalid committed state remains invalid under REPEATABLE READ; don't disable domain guards or fabricate acceptance without evidence.
Mitigate stop unsafe writer, reconcile authoritative acceptance evidence, validate P15/P16/P17 and P22 invariant test.

Case B "Two Order commands acknowledged but only one final state":
Scope same OrderId, source version, status/history, concurrent commands, retry policy.
Hypotheses P17 stale CAS, pre-P17 last-write-wins, legitimate P18 domain rejection, client replay, uncertain COMMIT.
Test: controlled same-predecessor successors (P22 E2), P17 exact concurrent work, P18 compatibility/illegal re-evaluation. A raw CAS conflict means stale candidate did not publish; lost acknowledgement of COMMIT has unknown outcome and must be treated separately. Never retry financial milestone blindly.
Mitigate preserve CAS, operation-specific policy, implement stable command identity only under business contract; validate committed history and version.

Case C "Long-history Order update latency and 409 rate rise":
Scope line/history size, per-Order write frequency, SQL affected rows, connection acquisition, lock wait, p50/p95/p99.
Hypotheses P19 full-child rewrite; hot Order shared revision; DB saturation; client retries; JDBC connection overhead. 2L+2H+1 is child-row operation count for append under current SQL, not WAL bytes or latency.
Test P19 trigger counts, independently vary L/H in a controlled future benchmark, monitor pg_stat_activity/locks/plans, compare hot vs many Order IDs, don't invent SLO.
Mitigate candidate same-aggregate append-only history or differential line persistence only with full transaction/reconstitution/CAS regression; don't split hard invariant for SQL convenience.

Case D "Two customer Orders claim last stock unit":
Scope RestaurantId, menu item, stock authority, observed availability version, plan IDs, admission SQL and its COMMIT.
Hypotheses both checked snapshot and committed reservations independently; no shared stock check; wrong Restaurant scope; duplicate request; split Order and stock commits; competing adjustment.
Test P20 test-only unsafe vs guarded admission; P21 two racing eligible plans / one commit; inspect actual deployed path BEFORE assuming authority exists.
Mitigate if strong availability contract needed: define real Inventory aggregate/reservation lifecycle and authoritative conditional admission; choose same DB transaction when permitted or explicit cross-system states/reconciliation. Production PlaceOrderService currently bypasses inventory so NO stock reservation claim.

Case E "Customer charged but Order payment milestone missing":
Scope external provider transaction reference, local Order state, request identity, provider authorization/capture/refund lifecycle, timeout/commit.
Hypotheses provider succeeded response lost; local save failed; double charge after unsafe retry; duplicate callback; local milestone without provider capture.
Discriminating evidence must come from provider authority, not local PAYMENT_RECORDED. P18 unknown COMMIT is not proof of rollback. No Payment provider integration exists in this repository, so do not claim verified settlement reconciliation.
Mitigate defer blind retry; reconcile with provider using stable logical operation ID, implement durable outcome record and idempotency when specified.

Metrics and tracing proposal: result by business outcome, failed reconstitution, stale CAS, attemptCount, commitUnknown, SQLState, status transitions, L/H sizes, observed inventory vs admission, stock hot-key lock, provider reconciliation backlog when applicable. Avoid PII and secrets. No numeric SLO measured.

Verification checklist: reproduce exact failing variant, observe authoritative database state, distinguish SQL abort from unknown commit, compare current state and command identity, rerun relevant Testcontainers/inherited JVM termination checks, ensure no production data changes by test-only SQL.
