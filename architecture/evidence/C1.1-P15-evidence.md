## Requirement being explored

Repeated delivery of one logical command must not accidentally multiply a business effect that is required to occur once.

Where caller recovery depends on retries, the API must define what result a replay receives.

## Current structural fact

OrderWorkflowUseCase methods identify:
- target Order;
- acting Customer/Restaurant where relevant.

They carry no logical command ID/idempotency key.

Therefore current code cannot know whether two identical-looking calls are the same logical command.

## Evidence-backed inference

State-machine terminality can make a selected repeated state transition converge without providing request deduplication.

A semantic prior-effect guard can suppress a selected repeated milestone without providing result replay.

Neither property can be generalized to external payment effects.

## Explicit non-guarantees

- no at-most-once execution;
- no durable duplicate detection;
- no exact-once effect guarantee;
- no replay of original success result;
- no idempotency retention window;
- no same-key/different-payload conflict handling;
- no restart-safe replay identity.

## Preserved fragile state

The platform remains pre-idempotent by design.

This is required both for P16 duplicate-payment reasoning and for the later dedicated idempotency cluster.
