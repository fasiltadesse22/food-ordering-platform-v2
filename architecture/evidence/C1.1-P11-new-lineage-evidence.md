## Exact tests and observations

- `OrderLocalAtomicAssemblyTest` injects a controlled exception **after target decided**, **after private occurrence staged**, and **after completed successor constructed**. Every exception leaves the original immutable Order at its prior status with prior history unchanged. No new successor is returned or published through the tested domain invocation.
- Successful cancellation returns one complete successor with CANCELLED and ORDER_CANCELLED together; the original remains PLACED. Acceptance and local payment milestones preserve the same semantics.
- Denied business command triggers the P07 guard **before any assembly callback**, preserving P09 expected-refusal classification.
- A deliberately unsafe **test-only mutable split** sets status CANCELLED then throws before fact append, leaving observably inconsistent status/fact fields. This is a counterexample, not product code.
- `OrderLocalPublicationFailureTest` injects an exception **before** repository reference publication: current Order remains unchanged. An exception **after** reference publication leaves a complete CANCELLED+ORDER_CANCELLED Order visible even though the caller gets a technical exception. Therefore error response/exception is not proof of absent local effect.
- A deliberate **test-only** Order-plus-independent-audit split demonstrates lack of multi-object atomicity. No audit subsystem was added to production app.
- A deterministic stale-snapshot test constructs separately legal PREPARING and CANCELLED successors from the same paid-and-accepted predecessor. Publishing A then B overwrites A, demonstrating unresolved read–guard–save concurrency weakness.
- `OrderWorkflowService.execute` does not catch the post-publication error as business rejection, preserving P09 business ≠ technical classification.

## Boundaries

- Domain atomicity covers **assembly of one immutable Order successor** and its paired local state/occurrence values, not an entire concurrent service method.
- A `ConcurrentHashMap.put` publishes a complete reference but `findCurrentById → decision → saveCurrent` is not one atomic transaction; last writer can overwrite. No concurrent stress/linearizability test was performed.
- Current in-memory Order history isn't durable and won't survive process restart.
- No PostgreSQL, SQL transaction, `@Transactional`, transaction manager, optimistic locking, cross-object atomicity, outbox, Saga or remote financial/physical effects implemented.
- The P09 learning-only HTTP workflow action route remains **unauthenticated and unauthorized**; no production security claim.
- `PAYMENT_RECORDED` and `REFUND_REQUESTED` remain local facts, not actual provider money movement.
- Application tests inject exceptions via stubs and test-only probes. They do not simulate real DB/network crashes or measure transaction throughput.
