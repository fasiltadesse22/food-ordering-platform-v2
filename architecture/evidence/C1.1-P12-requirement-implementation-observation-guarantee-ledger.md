# C1.1-P12 — Requirement → Implementation → Observation → Guarantee Ledger

**Exact contract:** V8.0 Part 1.1.12 and derived Cluster 1.1 blueprint. **Type A: Conceptual + Evidence Only.** This is a source-and-test taxonomy checkpoint, not new domain architecture. P12 branches from fixed independently rebuilt `redo/checkpoints/C1.1-P11`; **no Java application or test source is changed**.

## Reading protocol

Every row answers:

1. **Requirement (R):** What business or engineering property is desired?
2. **Documented rule (D):** Where/how was the policy specified?
3. **Implemented enforcement (I):** Which code actually enforces a piece of it, at which boundary?
4. **Observation (O):** Exactly which test/run or inspected source supports it?
5. **Inference (N):** What follows under explicit assumptions?
6. **Qualified guarantee (G):** The strongest defensible scoped claim—not an absolute slogan.
7. **Non-guarantee (X):** A counterexample, untested boundary, missing mechanism or independent authority.
8. **Stronger evidence (E):** What test/proof/reconciliation would change confidence?

"Tested" does not imply exhaustive. A property can be implemented but not experimentally exercised in the target failure model. Negative tests demonstrate that an invalid state **can** occur under a specified interleaving; they do not measure its real-world frequency. A simulated provider timeout is not a financial provider transaction.

**Evidence anchor:** [P11 Java 21 Maven verify — 119 tests passed](https://github.com/fasiltadesse22/food-ordering-platform-v2/actions/runs/41598620376), zero failures/errors/skips, including 11 domain assembly tests and seven publication failure tests. This run verifies the stated code SHA of P11; a documentation-only P12 run verifies the same inherited application source on the new branch. The number 119 is the quantity of tests executed, not percentage coverage, throughput, production availability or mathematical completeness.

- **R:** A valid customer placement command can create a correct Order.
- **D:** P01/P03 placement workflow and P02 actor/use-case expectations.
- **I:** `PlaceOrderService`, `Order.place`, `OrderLine` and current `OrderRepository`.
- **O:** Existing placement unit/MockMvc tests and P11 Maven regression run. The accepted case reaches HTTP 201 within the tested configuration.
- **N:** Tested valid requests result in a saved process-local Order under sequential, available repository assumptions.
- **G:** Those specific tested placement scenarios succeed and return an Order snapshot in-process.
- **X:** Not authenticated production access, persistent storage, cross-instance uniqueness or proof every valid request works.
- **E:** Property-based boundary tests, real authentication end-to-end tests, durable repository/transaction integration, restart and concurrent placement tests.

## Evidence honesty tests

A sentence is incomplete unless it names **the concrete subject**, **the environment**, **the boundary**, **the evidence ID** and **what is excluded**.

- Unacceptable: "Cancellation is safe."
- Better: "P11's fault-injected domain assembly tests show that when the probe throws before the immutable successor returns, the original in-memory Order remains unchanged; repository atomic read–guard–save and durability remain unproven."
- Unacceptable: "Duplicate payment cannot happen."
- Better: "P10/P11 tests enforce one local PAYMENT_RECORDED occurrence per accepted Order history in the tested sequential path; no real provider payment exists and concurrent/external deduplication is not implemented."
- Unacceptable: "CI guarantees correctness."
- Better: "The named Java 21 Maven run passed 119 specified tests on a particular source SHA; correctness outside those scenarios and assumptions is not established."
