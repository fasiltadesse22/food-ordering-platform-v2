# C1.1-P12 — Test, experiment and evidence taxonomy for the unchanged new P11 application

**Scope:** V8.0 P12 Type A. Categorize pre-existing tests and evidence. **No new production or test Java code.** A green run is evidence about executed inputs, not a universal guarantee.

## 1. Evidence classes

| Type | Definition | What it can support | What it cannot support by itself |
|---|---|---|---|
| **R — Requirement** | Desired business or quality property | Scope/acceptance criterion | That software already enforces it |
| **D — Documented** | Explicit policy/ADR/diagram | That engineers wrote a rule | That every code path follows it |
| **I — Inspected implementation** | Reviewed source has specific guard/state operation | Structural existence of mechanism and a code-path argument | That runtime reached that path in all conditions |
| **T — Executed targeted test** | A named test exercised a concrete case and asserted behavior | Behavior under test assumptions and fixture | Exhaustive correctness or deployment representativeness |
| **E — Controlled failure experiment** | Deliberate injection/interleaving with observed before/after | Demonstration of one failure window/counterexample | Production frequency, real network/DB failure semantics |
| **M — Measurement** | Numeric result with defined quantity, units and method | That metric in the measured environment | Unmeasured latency, production SLO or statistical confidence |
| **N — Evidence-backed inference** | Reasoning from implementation and tests under assumptions | A bounded conditional conclusion | An assumption-free guarantee |
| **A — Assumed** | Plausible, not checked by relevant source/test | Hypothesis to validate | Verified product behavior |
| **H — Hypothetical** | Counterfactual future design/test/SQL/provider | What to explore and falsify | Implemented mechanism or actual execution |
| **G — Qualified guarantee** | Explicitly scoped property under enumerated authority, timing and failure assumptions | Strong defensible claim within those assumptions | Global claims outside boundary |
| **X — Not guaranteed** | Missing mechanism, conflicting evidence or untested assumption | An honest limit or demonstrated counterexample | That a future improved system cannot achieve it |

**Do not promote a lower class merely by adding more prose.** For example, a documented rule and passing unit test do not prove a property under concurrent requests if the test never interleaved them.

## 3. Observation versus measurement: strict vocabulary

- "P11 Maven ran 119 tests" is a **measured count** of CI test cases, with environment and run ID.
- "A specific test threw after reference publication and then read CANCELLED" is a **controlled experimental observation**.
- "Order.java has final fields and List.copyOf" is a **structurally demonstrated source fact**.
- "Accepted source Order remains unchanged across injected assembly failures" is a **qualified evidence-backed behavior** from those tests.
- "Therefore no customer will ever see inconsistent Order state under production concurrency" is **unsupported inference**.
- "The p95 API latency is 25 ms" is **not measured**; no workload or latency distribution exists.
- "Future SQL CHECK will enforce the complete business history" is **hypothetical and generally incomplete**, not an implementation.
- "No in-memory state survives a full ordinary process restart in the current architecture" is a **structural non-durability inference**, not a test of actual crash/recovery execution.
- "The payment provider can never charge twice" is **not guaranteed** because the project has no actual provider effect or its authoritative identity/deduplication.

## 4. Controlled fault-injection evidence must name its test double

### 4.1 Three P11 domain assembly probes

`Order.assembleTransition` is package-private. Injected exceptions at `TARGET_DECIDED`, `FACT_STAGED` and `SUCCESSOR_CONSTRUCTED` demonstrate the old immutable source Order remains unchanged. These are **JVM exceptions during local construction**, not process kill signals, transaction rollbacks or real network partitions.

### 4.2 Repository stub before save

A controlled repository throws before `current=successor`. The test proves this specific stub left the current object unchanged. It cannot prove that an arbitrary remote database client exception implies no commit.

### 4.3 Repository stub after save

A controlled repository assigns `current=successor`, then throws. The test proves **a caller-visible exception can coexist with an already published local effect**.

### 4.4 Second-object inconsistency

A test-only List representing independent audit state is not updated after Order was cancelled. It demonstrates the gap between atomic Order value and multi-object atomicity. It is **not** a production audit subsystem.

### 4.5 Stale-snapshot overwrite

Two successors are built from the same previous Order and published in a deliberate sequence A then B; B overwrites A's accepted occurrence. This is an **executed deterministic interleaving**, but not a concurrent two-thread stress test or a production incident measurement.

## 5. How to upgrade evidence strength without adding unjustified architecture

| Claim | Current ceiling | What would genuinely strengthen it |
|---|---|---|
| Local successor atomicity | Targeted JUnit stage tests | Adversarial property/mutation tests for all actions and construction paths |
| Shared current-state serializability | Demonstrated stale-overwrite counterexample | Add justified versioned commit mechanism, then concurrency linearizability tests |
| Durable Order | No persistence; structurally absent | Implement real durable store and verify restart/crash recovery |
| Multi-object atomic commit | Negative test-only fixture | Define and implement actual shared transactional resource, inject rollback faults |
| Duplicate local payment milestone | One-history guard/invariant tests | Race/replay tests for repeated commands and stable command identity |
| Real provider exactly-once capture | No provider integration | Controlled provider sandbox/test double with authoritative ledger, duplicate/replay/ACK-loss/reconciliation tests |
| HTTP actor authorization | Direct modeled context tests; HTTP self-declared identity | Implement trusted principals, verify end-to-end authorization and spoofing resistance |
| Production error rate | P09 conceptual error categories | Actual telemetry, workload eligibility/denominators, deployed observations |
| Availability/latency SLO | No representative workload | Load/fault tests and monitored SLI distributions over defined windows |
| SQL constraints | SQL only illustrative | Migrations and real PostgreSQL integration, invariant and isolation tests |

## 6. Guarantee ladder as an audit discipline

```text
Business need
   ↓ define actor, authority, invariant, consistency scope
Documented rule
   ↓ point to exact policy/ADR and version
Implemented enforcement
   ↓ inspect code path, bypass paths and deployment assumptions
Test observation
   ↓ assert expected state and absence of forbidden effects
Controlled experiment
   ↓ manipulate crash point, order, concurrency and dependencies
Evidence-backed inference
   ↓ state why evidence covers claim and under what assumptions
Qualified guarantee
   ↓ name boundary, environment and explicit exclusions
```

The ladder is not a literal maturity score where any green test automatically promotes a requirement to a guarantee. A negative experiment can reduce confidence. "Guaranteed" is a conditional contract backed by proof/invariants/implementation tests within an explicit failure model, not a promise that arbitrary unmodeled conditions are impossible.

## 7. Staff-level adversarial challenge

Someone says: **"Duplicate payment cannot happen."** Before agreeing, ask:

1. What does "payment" mean—local `PAYMENT_RECORDED` occurrence, API request, authorization, capture or settlement?
2. Who owns the authoritative provider effect?
3. What is the business identity of one charge and one logical user operation?
4. Does the service enforce uniqueness in one Order history, across multiple JVMs and over process restarts?
5. Were simultaneous attempts tested under an atomic current-state commit?
6. Were replayed messages and client retries tested?
7. Did the provider execute a real financial transaction in any test?
8. Was an ACK lost after a confirmed provider effect?
9. Can an observer reconcile local history to the provider ledger?
10. What exact test/measurement/proof would falsify or establish the narrowed guarantee?

**Answer today:** The source and tests support at most the local accepted-history duplicate milestone rule under the tested sequential model. The project **does not integrate or control real external captures**; any broader claim is false as an evidence claim.

## 8. V8 no-mechanism rule

Do not introduce PostgreSQL, optimistic locking, authentication, provider integration, Kafka, Saga or Outbox just to strengthen an adjective in a report. Future technical work is justified by business correctness requirements and actual failure pressures. P12 changes **the clarity of what we know**, not the system topology.
