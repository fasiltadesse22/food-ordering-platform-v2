## Requirement

Two incompatible decisions derived from the same logical Order version must not both be independently accepted if they cannot coexist in one valid serial business history.

P13 demonstrates the current implementation does not yet enforce that requirement under the selected concurrent interleavings.

## Implementation statement

Structurally demonstrated:
- OrderWorkflowService uses find→evolve→save;
- saveCurrent accepts a complete Order without expected-version comparison;
- InMemoryOrderRepository uses ConcurrentHashMap get/put;
- no business-level compare-and-set spans the sequence.

## Evidence-backed inference

Given the observed schedules, the concurrency defect arises because each operation validates a locally valid successor against a snapshot that is stale by the time one of the saves executes.

An equivalent persistence implementation that permits stale successor replacement without conflict detection would retain the same class of risk.

## Scoped guarantee

The current domain state machine rejects an incompatible second operation when that operation observes the already-updated authoritative state, as demonstrated by the sequential control.

This does not imply concurrent serialization.

## Explicit non-guarantees

- no atomic find→evolve→save;
- no optimistic version protection;
- no pessimistic locking;
- no serialization of conflicting Order decisions;
- no multi-JVM concurrency guarantee;
- no database transaction/isolation guarantee;
- no guarantee that an Accepted response remains represented in later current authority.

## Critical observation

Both concurrent callers can receive Accepted even though only one mutually exclusive successor remains in current authority.

This is stronger than saying:
"last write wins."

A business decision acknowledged as accepted can disappear from the current authoritative representation.
