## Actual implementation and bounded invariants
Order aggregate identity OrderId (UUID record), CustomerId/RestaurantId (typed external concept references), lines (OrderLine value objects), lifecycle status, placement instant, ordered local workflow occurrences, aggregate version. Current local Order domain enforces selected implications: accepted requires acceptance fact; preparing requires accepted+preparing facts; completed requires acceptance+preparation+completion; cancellation/rejection facts require compatible current status; modifying line requires PLACED and owning CustomerId; accepting/rejecting requires PLACED and assigned RestaurantId; refund request requires rejected/cancelled + local payment occurrence + no prior local refund-request. These are the rules observed; do NOT claim exhaustive history semantics, actual provider settlement or menu stock correctness.
Entity != row, value object != DTO, aggregate != table, aggregate != bounded context, bounded context != deployable service, transaction != deployment. Correctness ownership determines logical boundary, not the number of Java classes/SQL tables.

## PostgreSQL write/read path
Flyway V1-V3 schema: orders, order_lines, order_workflow_occurrences (and selected constraints, version revision). PostgresOrderRepository.createNew version0 INSERT root+owned lines/history one JDBC transaction, exposes creation collision. saveCurrent successor version>=1 UPDATE orders WHERE id AND version=successor.version-1; on one match, deletes/reinserts complete child collections and COMMIT; on zero match, StaleOrderVersionException before child changes. Precommit SQL errors rollback and classify recognized SQLState 40001,40P01,55P03. JDBC COMMIT attempted but acknowledgement lost => OrderCommitOutcomeUnknownException; caller must not infer rollback. findCurrentById reads root, ordered lines, ordered history on a single read-only REPEATABLE READ snapshot and reconstitutes through domain validation. PostgreSQL-backed state survives fresh JVM; in-memory adapter does not.
No universal command idempotency or request-result replay. Currently PlaceOrderService uses random OrderId and calls OrderRepository.createNew; no inventory-aware admission. Payment milestone is local, not external financial truth.

## Dependency/failure-causality audit
D1 Valid Order successor created in memory but repository save not called => no authoritative update; immutability != persistence.
D2 SQL root version CAS fails => stale candidate never reaches child rewrite; competing winner retained.
D3 Root update succeeds but later child INSERT fails BEFORE commit => rollback; old valid Order authoritative.
D4 COMMIT attempt acknowledgement lost => either committed or aborted from caller knowledge; no automatic replay or invented financial state.
D5 Reader executes root/children under different READ COMMITTED statement snapshots => torn reconstruction possible; P16 single REPEATABLE READ snapshot prevents that selected hazard but not future write races.
D6 Invalid status and history independently COMMITTED => repeatable-read snapshot returns faithfully invalid business state; domain mapper rejects, not rescued by isolation.
D7 Large Order with L lines,H history: read 1+L+H rows, appended occurrence causes 2L+2H+1 child-row DELETE/INSERT operations (not WAL bytes/network trips); contention concentrated on one root for same-Order commands, different Order identities independently advance.
D8 Two independent reservations individually valid with capacity1 => over-allocation without shared stock admission; test-only stock authority conditional update prevents selected local oversell.
D9 Order and stock separately committed => partial outcomes; same-DB transaction can commit selected local Order+reservation atomically, not provider charge.
D10 InventoryReservationPlan derived from observed stock => proposal, not reservation; concurrent plans can both pass before only one is admitted.
D11 Local Payment recorded does not prove provider authorization, capture, settlement or refund; independent provider authority and customer-visible operation identity require future explicit protocol.

## Quality attributes and measurable scenario rubric
Correctness/data integrity: preserve status/history, line requirements, version monotonic currentness, no stale overwrites.
Durability: actual fresh JVM/Postgres retrieval after process termination.
Availability/recoverability: do not confuse SQLState error with business rejection, unknown COMMIT with rollback, no generic retries to amplify outage.
Performance/latency: P19 row counts and CI timing samples only, NOT SLO; measure p50/p95/p99, lock waits, connection acquisition, WAL, dead tuples before optimization.
Throughput/scalability: distinguish growing number of Orders, history size, and hot shared inventory/Order rows. One per-Order revision protects one Order but may cause hot aggregate conflicts.
Maintainability/modifiability: domain policy pure, persistence authority isolated, physical optimization does not justify logical split, one monorepo rather than speculative microservices.
Observability/operability: record OrderId, command type, expected/actual revision, SQLState, attempt count, outcome knowledge, invariant violation, partial authority state and correlated provider IDs if implemented. Avoid customer/payment secrets.
Interoperability/deployability: no database-per-service decision yet; cross-context translation belongs to Cluster 1.3.

## Architecture boundary decision
1 Preserve current Order root/status/owned lines/local workflow fact consistency boundary.
2 Preserve transaction currentness, isolation and precommit rollback; do not 'optimize' by independently committing status and explaining history.
3 Keep external Customer/Restaurant identity references; full Restaurant/Payment source truth not in Order. Current inventory is advisory planning only, test-only authority/admission examples.
4 Consider append-only history and differential line persistence as physical optimization candidates only after measured workload AND same atomic/currentness validation.
5 Do not introduce brokers/Saga/Outbox/CDC/Redis/distributed locks or databases per service merely because nouns have independent names. Future selection requires business consistency windows, external participant capabilities, deployment forces, retries, operation identity and recovery evidence.
