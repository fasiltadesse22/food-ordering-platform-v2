## Engineering question
When Order creation and limited stock allocation participate in one business workflow, which authority enforces quantity, who decides eligibility versus confirmed admission, which local commits must be atomic, and what partial failure windows appear if those authorities later split? Domain aggregate boundaries, physical tables, local transaction boundaries, and deployment boundaries are distinct concepts.

## Source-derived existing facts
Production Order aggregate has OrderId, CustomerId, RestaurantId, order lines, status, workflow history and version. Order.place has at least one line; PlaceOrderService creates random OrderId and OrderRepository.createNew. RestaurantId is a reference and actor guard, not authoritative Restaurant open/capacity truth. Local PAYMENT_RECORDED occurrence is not provider capture. P15 Order root/children one PostgreSQL transaction, P16 full coherent snapshot, P17 version CAS, P18 selected re-evaluations, P19 full-child rewrite, P20 split status/history corruption and test-only independent inventory oversell.
No production Inventory stock/reservation authority, stock admission, Payment provider, authenticated Restaurant lifecycle, or inventory-aware HTTP path is present at inherited P20.

## New P21 pure domain-service implementation
New immutable InventoryAvailabilitySnapshot(restaurantId, observedVersion, availableByMenuItem) validates and defensively copies source. It is an observation, NOT a reserved quantity. New InventoryReservationPlan(orderId,restaurantId,observedInventoryVersion,requestedByMenuItem) validates and is immutable; proposal NOT authoritative allocation. OrderInventoryReservationPolicy.propose(Order,InventoryAvailabilitySnapshot) verifies same RestaurantId, Order PLACED, groups duplicate OrderLine.menuItemId quantities using Math.addExact, requires item in observation and sufficient observed quantity, returns proposed per-item reservation. Explicit typed InventoryReservationPlanningException distinguishes WRONG_RESTAURANT, ORDER_NOT_PLACED, ITEM_NOT_IN_SNAPSHOT, INSUFFICIENT_OBSERVED_QUANTITY.
The pure service never writes inventory, changes Order version, confirms stock, charges provider, or contacts network. Its observed inventory version is NOT yet an enforced CAS token: no production inventory repository exists. The example illustrates a domain service needing knowledge from two distinct concepts; application service would load state and coordinate authoritative commits.

## Invariant and authority graph
Order: OrderId and own lifecycle/status/history, selected local payment and refund milestones, commercial OrderLines. RestaurantId: reference to external conceptual Restaurant, which would own operational state if implemented. Inventory: hypothetical separately authoritative stock by (restaurantId,menuItemId), with hard narrow capacity rule Remaining>=0 and reservations<=initialCapacity, enforced at an admission point rather than separate OrderLine checks. Payment: separate provider financial authority, not established by local ORDER/payment events.
Planning invariant Req(item)=SUM(OrderLine quantities for that item), Req<=ObservedAvailable(item) is an observation-time advisory eligibility test, NOT a commit-time guarantee. Two Orders can both plan with same stock=1. Only authoritative conditional update in one transaction can serialize local admission.

## Local commit alternatives
A One local database, Order root+lines and stock decrement/reservation INSERT under ONE PostgreSQL transaction: for narrow business rule 'publish Order only with stock admission' either all commit or all rollback. Does not change independent aggregate identities or complete REST/Payment flow. Selected as demonstrated positive control, implemented only in a test-only JDBC helper, NOT wired production use case.
B Order creation commits first, independent stock check later: after stock unavailable, valid PLACED Order remains without reservation. Not intrinsically invalid unless business promised stock at placement, but violates that hypothetical strong promise. Demonstrated negative.
C Inventory stock decrement commits first, Order insert later fails or never runs: capacity disappears without matching Order/reservation; recovery/expiry needed. Demonstrated negative.
D Different PostgreSQL DBs or remote authority: local ACID transaction cannot atomically cover both. Need explicit states, operation identity, idempotency, reservation lifetime, retries/reconciliation or business-approved weaker consistency. No premature Saga/2PC selection.
E Separate domain services and aggregates in same deployable: valid modeling choice; service boundary != aggregate boundary.

## Failure windows and knowledge boundaries
W0 Planning computed from snapshot: can become stale immediately; no stock reserved.
W1 After independent Order commit, before inventory admission: Order present without reservation. Must define if valid 'PENDING_RESERVATION' state; current production Order has no such status.
W2 After independent inventory decrement, before Order creation: stock consumed, no corresponding Order. Requires authoritative reservation identity/expiry/recovery; current proof only test-only SQL.
W3 Shared local tx: order insert, stock decrement, reservation INSERT, later SQL failure => all rollback (real P21 trigger-injected SQLState P0001). External readers get old valid or new coordinated local state.
W4 Concurrent proposals from same snapshot: two planning decisions can both pass, but conditional stock UPDATE prevents two commits of remaining one; losing transaction also rolls back Order creation. Real Testcontainers PostgreSQL.
W5 COMMIT response lost on coordinated tx: unknown whether both committed, not half; require stable operation identity and reconciliation, P15/P18 distinctions preserved. Not directly P21 network-failure tested.
W6 External Payment capture uncertain: local Order+Inventory transaction says nothing about provider financial truth; never use local version as provider proof.
W7 Subsequent Order cancellation/rejection: inventory release, capacity corrections, expiration and duplicate retries have not been defined for production; no claim of completed full reservation lifecycle.

## Domain service vs application service
Aggregate method: local business mutation/invariants. Pure domain service: calculates cross-concept decision from supplied domain inputs without doing IO and without pretending observation is authority. Application service: loads authoritative participants, orchestrates and invokes transaction-capable coordinator, chooses partial outcome handling, retries, compensation. Infrastructure adapter: implements atomic persistence/admission and SQL concurrency. A pure rule 'repeated item quantities sum first' belongs outside JDBC SQL coordination, but current stock admission requires authoritative DB predicate at write time.
Avoid false lesson 'all cross-aggregate rules belong in domain services'—some coordinated workflows are application orchestration, some business policies are aggregates, some depend on shared authority, and simple operations may require no separate service.

## Quality attributes and tradeoffs
Correctness: coordinate Order and strict stock allocation when shared same-DB authority is legitimate. Latency: one local tx may include multiple rows/locks, no measured production p99. Throughput: per-item stock row can be hot, domain read snapshot might race, authoritative UPDATE guards. Availability: DB failure aborts both local effects under one transaction; independent system failure requires explicit workflow state. Reliability/recoverability: no partial local commit in shared tx, independent commit windows require reconciliation. Deployability: do not force database-per-service; future decomposition will change transaction options. Observability: reservation_plan vs admission result, OrderId, RestaurantId, item/quantity, stock remaining, conflict rate, aborted transaction, recovery backlog; privacy safe. Modifiability: keep pure domain logic distinct from IO and authority; no auto payout/stock release assumptions.

## Alternatives and P22 handoff
Compare one same-DB tx vs two local commits vs async coordination vs one giant aggregate vs independent services and distributed transactions. Refuse premature Kafka/outbox/Saga/CQRS and Payment provider integration until workload/business failure requirements justify them. P22 must synthesize invariants, ownership, size/contention, real SQL guarantees, inter-aggregate tradeoffs, cluster evidence, unresolved flows and explicit readiness for next Cluster1.3 context mapping.
