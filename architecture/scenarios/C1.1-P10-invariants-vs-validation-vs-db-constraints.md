# C1.1-P10 — Business invariants vs validation rules vs future database constraints

**Exact scope authority:** V8.0 Part 1.1.10 + derived Cluster 1.1 blueprint.
**New implementation:** `redo/v8-c1.1-p10` from verified `redo/checkpoints/C1.1-P09`; no historical old P10 implementation used.

## Ownership hierarchy

1. **Business invariant**: property that every accepted and reachable Order state/history must satisfy, regardless of HTTP/SQL technology. Example: a cancelled Order cannot later enter preparation. The real P10 checker replays accepted in-memory local occurrences and validates that a final status could arise from legal ordered actions.
2. **Input/boundary validation**: controls whether a request is representable and structurally valid (UUID, customer ID, nonempty lines, quantity and unit price). A syntactically valid command may still be illegal for the Order's current state.
3. **Database constraint**: a persistence *mechanism* for a chosen subset (future `NOT NULL`, `CHECK(quantity > 0)`, `CHECK(unit_price >= 0)`, `FOREIGN KEY`, `UNIQUE`). It is not business meaning and cannot by itself prove temporal history and multi-step lifecycle integrity. **There is no database in P10.**

## Formal semantic rule

Let accepted local actions be sequence `H = [h1, ..., hn]`, with initial fulfillment state `PLACED`, `paid=false`, `refund=false`. Fold `H` under the previously selected P06/P07 transition model, requiring:
- restaurant acceptance/rejection only from PLACED;
- cancellation only from PLACED or ACCEPTED;
- payment recorded at most once before preparation;
- preparation only from ACCEPTED *with prior PAYMENT_RECORDED*;
- completion only from PREPARING;
- refund request only from CANCELLED or REJECTED with earlier PAYMENT_RECORDED and no earlier request;
- accepted occurrence actor labels match the locally defined action participant class; **labels are not authenticated real people**;
- final folded status equals the Order's claimed status.

These invariants are checked on every new immutable Order construction. The P07 per-action guard and before/after checks remain separate and intact.

## Required contrasts

### Input validation passes but invariant/business rule rejects

Create a valid Order through `POST /orders`, obtain its UUID; send `POST /orders/{id}/actions/ORDER_COMPLETED`. UUID and action representation are valid, but status is PLACED, not PREPARING. P09 typed boundary returns HTTP **409 BUSINESS_REJECTION**, not 400. P10 dedicated `OrderValidationBoundaryTest.syntacticallyValidRequestPassesValidationButViolatesLifecycleBusinessRule` executes the case.

### Hypothetical DB column constraints pass but invariant fails

Consider a row with valid, non-null status enum `PREPARING`, valid non-null actions `[PAYMENT_RECORDED, ORDER_CANCELLED, RESTAURANT_ACCEPTED, PREPARATION_STARTED]`, and valid timestamps. Individual column `NOT NULL` and status enum checks would pass, yet the history tries to accept/prep **after cancellation**, violating the temporal business invariant. `OrderBusinessInvariantsTest.validNonNullCancelledStatusWithPreparationAfterCancellationViolatesTemporalInvariant` executes this fabricated *in-memory* history and asserts `OrderInvariantViolationException`; **no SQL engine is run**.

Also: claimed status COMPLETED with only ORDER_CANCELLED as accepted history has a syntactically permitted status but contradicts its preceding history.

## Invariant scope and failure boundary

- **Intra-Order**: current status matches local accepted workflow history; no forbidden sequence or duplicate local milestone.
- **Cross-aggregate**: customer account authority, restaurant availability, inventory, actual payment provider capture and external delivery are **not** covered.
- **Temporal safety**: after `CANCELLED`, this accepted local fulfillment trace never enters `PREPARING`.
- **No global proof**: independent in-memory calls can race between current-state read, guard and save. A newly verified successor can still overwrite another accepted successor. No DB/transaction/expected-version consistency added.
- **No durable audit**: `List.copyOf` is not a database or tamperproof ledger; process restart drops accepted Order state.
- **No authenticated actor identity**: `WorkflowParticipant` names are local semantic labels, not trusted principals.
- **No external financial effects**: `PAYMENT_RECORDED` and `REFUND_REQUESTED` remain local workflow occurrences, not provider capture/refund.

## Evidence contract
