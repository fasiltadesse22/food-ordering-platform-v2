# C1.2-P02 — Required State, Authority, Identity and Lifecycle Continuity

## Scope / inherited checkpoint
Roadmap V8.0, Cluster 1.2, Part 1.2.2. Inherit the verified `checkpoints/C1.2-P01` commit `2a61909a2cf3470b3917caab2abecdafe9334e81`.
Engineering question: What makes business state belong to the same continuing object across successive decisions, reconstructed representations and process lifetimes?
Type A/C: identity contract clarification + targeted executable tests; no production behavior change, database, version field, service split or extra authority.

## Source-inspected domain identity
- `OrderId` is `record OrderId(UUID value)`; it disallows null and provides random ID creation, textual parse and `toString`.
- `CustomerId` and `RestaurantId` are different Java record types wrapping nonblank Strings.
- `Order` is a final immutable class with a private constructor; public lifecycle methods construct successors preserving `id`, `customerId`, `restaurantId`, `placedAt` and other unchanged fields while evolving status/history.
- `Order` does not override `equals` or `hashCode`, so ordinary Java equality is reference-based. **Domain entity identity should not be conflated with `Order.equals()`.**
- `OrderSnapshot` is a detached response-oriented representation. It preserves identifying references, but does not become authority by being returned.
- `PlaceOrderService` creates `OrderId.random()` and `saveCurrent`; this is probabilistic UUID generation, not database-backed uniqueness.
- `OrderRepository.findCurrentById` and `saveCurrent` address state by `OrderId`. Its in-memory adapter holds one current map value per equal identifier **per repository instance**.

## Explicit continuity contract — normative proposal, not automatically enforced end-to-end
1. One accepted placement creates one new business Order identity (creation-time uniqueness remains a probabilistic assumption in the current JVM).
2. Normal lifecycle changes preserve `OrderId`; they are successive versions/representations of the same Order.
3. Identical public attributes with different OrderIds still denote different Orders.
4. Same OrderId in two representations denotes the same **claimed** business identity, not proof that either representation is authoritative, current, legal, or authentic.
5. Current authority is a function of the selected repository and time/scope, not of possessing an ID or an HTTP snapshot.
6. Terminal states restrict permitted future operations; they do not imply that the Order's identity has ceased to exist.
7. A restart must not silently invent a new ID for an existing continuing Order; correct durable reconstruction, when introduced, must preserve identity and sufficient authoritative state.
8. Unknown or deleted/cleared current state is distinct from syntactically invalid identity and from technical retrieval failure.
9. Identity value equality, JVM object reference equality, state equivalence, and temporal freshness are separate predicates.
10. No current implementation prevents arbitrary same-ID representation replacement; this is intentionally preserved for P17/P16–18 comparisons.

## Formal model and proof obligations
Let business identity I, state S_t, and Order representation O_t=(I,S_t).
On a legal lifecycle transition `T`, `identity(T(O_t))=identity(O_t)`.
Different I values imply different Orders even when S is equivalent.
Equal I does not imply equal S, object-reference equality, or equal authority.
Let `A_p(I,t)` denote current representation returned by repository instance p for identity I at time t.
`A_p(I,t)` may be absent. A different repository q need not have the same state.
A detached `Snapshot(I,t_0)` is an observation and need not equal `A_p(I,t_1)` for t_1>t_0.
There is no persisted version or compare-and-set, so authority may regress when stale representations are saved.

## State ownership and lifecycle matrix
| State | Identity role | Continuity behavior | Authority qualification |
|---|---|---|---|
| OrderId | Identifies continuing Order | Preserved across domain evolutions | Does not prove existence/currentness |
| CustomerId | Order's associated Customer identity reference | Preserved by current Order evolutions | Not full Customer account authority |
| RestaurantId | Order's assigned Restaurant identity reference | Preserved by current Order evolutions | Not full Restaurant profile/menu authority |
| lines | Current commercial contents | Retained or replaced on modify | May differ across same-identity snapshots |
| status | Current Order lifecycle | Evolves under legal domain operations | Validity of stale copy != authority |
| placedAt | Creation timestamp | Preserved under normal evolution | Not a stable unique identifier |
| occurrences | Selected local facts | Appended on normal evolution | Not provider truth/durable audit guarantee |
| OrderSnapshot | Detached observation | Doesn't mutate as authority changes | Never current source by itself |
| repository mapping | Current state of one ID in one process | Replaced by saveCurrent | Not durable or cross-process shared |

## Failure and ambiguity matrix
| Scenario | Expected identity relation | Actual authority concern |
|---|---|---|
| Same Order, PLACED then ACCEPTED | Same business ID, distinct Java objects | Only saved successor is current |
| Different Orders with same contents | Different business IDs | Both must be addressable independently |
| Identical OrderId values constructed separately | Same identity value | Repository key equality within one instance |
| Same ID, divergent concurrent successor branches | Same claimed entity identity | Only one current representation; incompatible acknowledgements P13/P14 |
| Stale snapshot O0 after later current O1 | Same identity | Snapshot is not current; stale writes possible P17 |
| Valid ID not present in repository | Refers to no currently known Order | No identity-based existence proof |
| New process with empty in-memory repository | Same textual ID still parsable | Business state unrecoverable P18 |
| Provider charge with OrderId correlation | Local reference only | Not financial authority P16 |
| Duplicate business-generated UUID (hypothetical) | Identifier collision | No DB uniqueness guarantee; current map would overwrite |
| Terminal Order | Identity continues as historical Order | Transition permissions narrow; no identity deletion implied |

## Source-based trade-offs and explicitly deferred decisions
Typed identity prevents some accidental type mixing at compile time; String wrappers still allow many semantically invalid but nonblank external references. 
UUID randomness provides strong practical uniqueness expectations, but no proof of absolute uniqueness. Current implementation does not check ID collision in `saveCurrent`.
`Order` intentionally uses reference-based Java equality; do not introduce a broad equals/hashCode change without examining how it interacts with mutable lifecycle representations and persistence identity maps.
`OrderId` record equality is value-based and appropriate as a repository key.
No future database primary-key, row-to-object, ORM persistence-context or reconstitution strategy is chosen in P02.
No optimistic version field or transaction is introduced early.

## Experiments
1. Current normal transitions create distinct objects with one stable OrderId while preserving source representation and assigned IDs.
2. Two otherwise equivalent Orders with different OrderIds occupy distinct current mappings.
3. Two separately constructed equal OrderId values and canonical parse round trip preserve identifier value equality; CustomerId and RestaurantId do not become interchangeable.
4. Two independent in-memory repository instances share no Order authority even if a caller knows the same OrderId.
5. A stale PLACED representation can construct a locally legal cancellation after the repository advances to ACCEPTED; in this P02 test it is **not saved**. The P17 baseline demonstrates the danger of saving it.
6. Reuse the real P18 JVM replacement experiment as continuity/durability **negative evidence**, not as a claim that P02 implemented recovery.
