# C1.1-P01 — Initial Correctness Contract

## Engineering question

What must remain correct before we make any architectural decision?

## Business intent represented in this baseline

A customer can place one order for one restaurant containing one or more order lines.

This is deliberately a minimal vertical slice. It does not yet model payment, restaurant acceptance, cancellation, refund, preparation, completion, concurrency, duplicates, or stale decisions. Those are later Cluster 1.1 parts.

## Rules currently represented

1. An order has an identity.
2. It is associated with a customer and restaurant.
3. A newly placed order begins in `PLACED`.
4. An order must contain at least one line.
5. Each order line has positive quantity.
6. Unit price cannot be negative.
7. The order total is derived from line quantity × unit price.
8. The application stores the order through an output port.
9. HTTP is an adapter; it is not the owner of the business rule.

## Explicit non-guarantees

This candidate does not guarantee:

- durability across process restarts;
- database ACID behavior;
- concurrency correctness;
- duplicate-command safety;
- idempotent payment effects;
- distributed consistency;
- network failure handling;
- retry safety;
- availability;
- scalability;
- production throughput;
- security completeness.

## Why the list is intentionally small

The baseline must be real without solving the rest of Cluster 1.1 prematurely. The next parts expand the business model and correctness obligations using evidence from this running substrate.
