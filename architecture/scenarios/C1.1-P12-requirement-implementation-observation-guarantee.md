# C1.1-P12 — Requirement, Implementation, Observation and Guarantee

## Engineering question

What exactly do we know, how do we know it, and how strong a claim are we justified in making?

## One example through all levels

### Requirement

A completed Order must have lifecycle/history coherence.

This is normative.

It states what correct behavior should be.

### Implementation

Order.recordCompletion uses the COMPLETE transition.

Order.transition creates OrderEvolution containing:
- target COMPLETED;
- ORDER_COMPLETED workflow occurrence.

Order.apply constructs one new Order.

Order constructor runs OrderInvariants.verify.

This is structurally demonstrated by source.

### Observation

In GitHub Actions run 37886764685:
- OrderAtomicityAndConsistencyTest executed;
- normal completion produced COMPLETED with ORDER_COMPLETED;
- status-first injected failure produced invariant-invalid partial state;
- history-first injected failure produced invariant-invalid partial state;
- all 68 tests passed.

This is an execution observation.

### Evidence-backed inference

If future persistence commits lifecycle state and completion history independently, either ordering exposes a partial-state failure window.

If the current invariant remains immediate, future persistence needs one atomic boundary or an equivalent mechanism that prevents partial authoritative visibility.

This is an inference from the experiment plus mechanism reasoning.

### Scoped guarantee

Within the current normal in-process Order construction path, successful Order construction is checked against OrderInvariants before the new object is returned from that path.

This guarantee is scoped.

It does not mean:
- the repository is durable;
- concurrent read-modify-write is safe;
- persistence mappings cannot bypass the path;
- a future DB schema enforces the same property;
- distributed participants are consistent.

## Requirement can exist without implementation

We may require:
"state must survive process restart."

Today it does not.

A requirement is not evidence of implementation.

## Implementation can exist without observation

A developer may add:
"retry = 3"

to configuration.

Until exercised, we can say the configuration exists.

We cannot truthfully say:
"retries were observed to recover failure."

## Observation can exist without guarantee

One concurrent test may execute and show no lost update.

That does not guarantee lost updates cannot happen.

The test may simply have executed a favorable interleaving.

## Guarantee without scope is usually misleading

"The repository is thread-safe."

Which property?

ConcurrentHashMap protects its own structural operations.

It does not make:
find
→ decide
→ save
one atomic business transaction.

Replace broad claims with property-specific scoped claims.

## Negative evidence

A failed experiment can be more informative than a passing happy path.

P11 deliberately demonstrated:
- state-first partial update is invalid;
- history-first partial update is invalid.

Those failures justify an atomicity requirement.

## Absence of failure is not proof of safety

If 1,000 requests run without error:
- no error was observed in that run.

That does not prove:
- no race exists;
- no rare crash window exists;
- no failure appears at 10,000 requests;
- no other configuration fails.

## Source, test, CI and production telemetry answer different questions

Source:
what implementation exists?

Unit/domain test:
what path behaved as asserted under controlled inputs?

Integration test:
how selected components behaved together?

Failure injection:
what happens at a chosen failure point?

Load test:
what happens under specified workload/resource conditions?

Production telemetry:
what happened in deployed real workload?

No single evidence source replaces all others.
