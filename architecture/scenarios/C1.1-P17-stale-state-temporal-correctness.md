# C1.1-P17 — Stale-State Decisions and Temporal Correctness

## Engineering question

What happens when a decision was correct for the state we observed but is wrong, incomplete, or unsafe for the state that exists when we act?

## Core timeline

T0 observe authoritative state S0
T1 derive decision D assuming S0
T2 authority changes to S1
T3 execute/apply D using S0 assumptions
T4 stale successor/effect becomes visible

The defect is not that S0 was never valid.

S0 was authoritative at T0.

The defect is temporal:
D's correctness depended on facts that no longer held at T3/T4.

## Stale data versus stale decision

A stale read can be harmless:
- display old data;
- compute a non-authoritative preview;
- discard it before committing.

A stale decision becomes dangerous when it:
- changes authoritative state;
- emits an external effect;
- makes an irreversible commitment;
- suppresses/overwrites newer facts.

## Experiment A — modification after payment

Observed state:
PLACED, no payment fact.

Decision assumption:
the Order can be modified according to the state observed.

Intervening current-state change:
PAYMENT_RECORDED.

Delayed stale modification:
new lines + ORDER_MODIFIED derived from the pre-payment Order.

Unconditional save can replace current authority with:
PLACED + ORDER_MODIFIED

and erase:
PAYMENT_RECORDED.

This is a stale successor overwrite.

## Experiment B — payment after cancellation

Observed state:
PLACED.

Decision assumption:
payment may proceed according to that snapshot.

Intervening current-state change:
CANCELLED + ORDER_CANCELLED.

Delayed stale payment:
recordPayment against the earlier PLACED copy.

Unconditional save can replace authority with:
PLACED + PAYMENT_RECORDED

and erase:
CANCELLED + ORDER_CANCELLED.

This is both:
- stale decision;
- state/history resurrection from an obsolete snapshot.

## Fresh payment after cancellation — separate policy finding

If recordPayment is invoked through the current service after cancellation, it reads fresh CANCELLED and still appends PAYMENT_RECORDED while keeping CANCELLED.

That behavior is possible because payment has no contextual guard.

It must not be misdiagnosed as stale-state corruption.

P17 records it as a separate current policy/non-guarantee.

## Experiment C — fresh guard versus stale guard

Current authority after restaurant acceptance:
ACCEPTED.

modifyLines against current ACCEPTED:
rejected because modification requires PLACED.

modifyLines against an earlier PLACED copy:
guard passes.

Saving the stale modified copy:
can restore PLACED and erase RESTAURANT_ACCEPTED.

Therefore:
correct predicate + stale input != temporally correct decision.

## Temporal precondition

A normal precondition says:
P(S) must be true.

A temporal correctness requirement may need:
P(S_observed) was true
AND
the relevant authority has not changed in a way that invalidates P
before commit/effect.

Conceptually:
decision validity has a lifetime.

## Causal ordering

If event/change B invalidates assumptions used by decision A, then applying A after B may be incorrect even if A was derived earlier.

The system needs a way to establish or detect relevant causal order at the authoritative boundary.

P17 does not yet choose the mechanism.
