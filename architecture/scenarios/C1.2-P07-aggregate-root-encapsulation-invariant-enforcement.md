# C1.2-P07 — Aggregate Roots, Encapsulation, and Invariant Enforcement

## Scope and baseline
V8.0 Cluster 1.2 Part 1.2.7. Inherit verified `checkpoints/C1.2-P06` at `edde75f6dc63cb4c1568939497ab7cea218c5759`.
Engineering question: How can one aggregate root control all operations capable of violating its immediate invariants?
Evolution: Type B minimal correctness refinement plus Type C controlled boundary tests and Type A architectural evidence. Do not introduce DB/versioning/service split.

## Actual root and state
`Order` is final, with private constructor and final OrderId/CustomerId/RestaurantId/lines/status/placedAt/workflowOccurrences.
`Order.place` validates nonempty lines; `OrderLine` validates field shape. `List.copyOf` protects collection structure (not arbitrary future mutable elements).
`transition` checks legal source state, then contextual actor-ID guard, builds OrderEvolution(target status + occurrence), constructs fresh Order and runs OrderInvariants.verify.
`modifyLines` checks CustomerId and PLACED; creates new line collection with ORDER_MODIFIED.
`recordRefundRequest` checks REJECTED/CANCELLED + PAYMENT_RECORDED + no prior REFUND_REQUESTED before adding a fact.
`recordPayment` appends a local milestone without lifecycle guard or deduplication.
Application services load/evolve/save; InMemoryOrderRepository.saveCurrent does unconditional ConcurrentHashMap.put.

## Rule taxonomy
- Structural: IDs not null/nonblank, OrderLine positive quantity/nonnegative price, nonempty Order lines at place/modify.
- Operation preconditions: ACCEPT/REJECT/CANCEL from PLACED; PREPARATION from ACCEPTED; COMPLETE from PREPARING.
- Contextual business guard: actor IDs equal assigned CustomerId or RestaurantId (not authentication).
- Representation invariants: selected status/history implications verified in Order constructor.
- Authority invariants: latest state and legal committed history require future repository/transaction control; not supplied by current root.

## Demonstrated gap and minimal remedy
Before P07, `OrderInvariants.verify(PLACED, [RESTAURANT_ACCEPTED])` returned normally despite normal lifecycle requiring acceptance to move the Order to ACCEPTED.
This did not arise through intended public normal transition, but would be a dangerous shape to accept from an alternative construction/reconstitution path.
New selected invariant: when RESTAURANT_ACCEPTED is present, under the **current** state machine status must be ACCEPTED, PREPARING or COMPLETED. New violation code: ACCEPTANCE_FACT_REQUIRES_ACCEPTED_OR_LATER_STATE.
This also rejects acceptance coexisting with REJECTED or CANCELLED. If future policy permits cancellation after acceptance, revisit the invariant explicitly.
Do not claim comprehensive history validation (participant/action correctness, time ordering, duplicate acceptance, payment milestones, causal replay) from this additional implication.

## Threat and bypass analysis
1. An outside caller cannot call private constructor, change private final status, or mutate List.copyOf collections through getters; no public generic setter.
2. An outside caller can invoke `recordPayment` repeatedly: local PAYMENT_RECORDED duplicates are currently permitted. This is preserved as a **negative-control test**, not silently fixed by inventing a payment policy.
3. `OrderWorkflowOccurrence` constructor validates nonnull components, but currently no semantic participant-action matching or occurrence-identity guarantee.
4. Package-private OrderInvariants controls only selected representation rules and must not be treated as full event-history verification.
5. Reflection, unsafe deserialization, or future ORM mapping may bypass normal construction semantics; persistence reconstitution must be designed carefully at P10–P14.
6. Current repository unconditional save accepts stale otherwise valid same-identity representations; P13/P14/P17 remain reproducible.
7. In-memory publication has no process recovery; P18 negative control remains.
8. Neither domain guard nor owned ID proves caller authentication; external Payment/Restaurant/Customer authorities are excluded.

## Acceptance criterion and non-guarantees
Root should forbid ordinary public paths to selected illegal lifecycle transitions, protect collections from external mutation, and reject internally contradictory acceptance-history/current-state combinations.
It is not a promise of all possible history validity, command deduplication, global actor authorization, JPA enforcement, SQL transaction, concurrency isolation, durability, provider charge or atomic external effects.
No Money/currency/price normalization, transaction/version strategy, Kafka/Redis/Saga or service split.
