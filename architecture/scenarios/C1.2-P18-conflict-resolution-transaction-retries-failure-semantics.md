# C1.2-P18 — Conflict Resolution, Transaction Retries and Failure Semantics

Authority: Enterprise Distributed Systems Architecture & System Design V8.0 plus Cluster1.2 derived blueprint P1.2.18. Inherited actual frozen verified C1.2-P17 SHA 40144edeb245c9739e74aaabcf9e5359d6601ebf. Single Food Ordering Platform; local immutable Order, PostgreSQL V1-V3, root+lines+history atomic writes (P15), coherent read snapshot (P16), PostgreSQL conditional version CAS (P17).

## Engineering question
A version predicate or database error detects an execution problem, but which participant knows whether the logical Order command committed, whether a fresh-state re-execution would be legal, and whether a duplicate request should replay the previous result? Do not confuse DB transaction replay, application-command re-evaluation, and client replay. The former can need all SQL/reads repeated; the latter can produce new domain rejection; the final needs stable operation identity and result recording.

## Failure window and outcome matrix
1 Domain illegal transition before save: no attempted successor publication; return domain rejection.
2 Stale CAS (zero row update, confirmed): candidate did not publish; another operation may or may not have performed equivalent intent. Requires fresh load/re-evaluation or return conflict; no resubmit of same immutable successor.
3 40001 serialization failure pre-COMMIT: current PostgreSQL write transaction aborted; any retry requires new transaction+recompute complete dependent logic, not a stale SQL update. P18 classifies, deliberately does NOT auto retry.
4 40P01 deadlock pre-COMMIT: database victim transaction aborted; investigate lock order, retry budget/resource pressure; classification only.
5 55P03 NOWAIT or lock_timeout: requested database lock was not acquired; no proof of another business command's outcome. Classify separately, no automatic retry.
6 23505 creation collision: ID conflict; not idempotency proof. A fresh unique OrderId can duplicate original customer intent.
7 SQL statement failure before commit: attempted local transaction rollback (P15) unless connection failure leaves uncertainty; do not label committed without evidence.
8 COMMIT attempted, acknowledgement lost: may have committed OR aborted. P15 specific OrderCommitOutcomeUnknownException must be preserved; no automatic replay.
9 Client HTTP timeout after server already returned or committed: client doesn't know. Operation key/result replay or authoritative reconciliation needed.
10 External Payment provider charge/response loss: local Order milestone and provider money authority can diverge. Order.version is NOT provider transaction id or effect dedup.
11 Retry storm/high contention: repeated retries increase connections, lock wait, CPU and p99; bound attempts and monitor conflicts.

## Actual inspected source and authorized mechanism
OrderWorkflowService at P17 maps raw StaleOrderVersionException to Rejected(STALE_ORDER_VERSION). P18 permits precisely one fresh-state re-evaluation for local pure lifecycle transitions: accept, reject, cancel, start preparation, complete. Reload Order via repository on each attempt; domain transition re-evaluates status and owning actor; then save next CAS successor. If compatible concurrent milestone (such as local payment history) advanced Order while status stayed PLACED, new acceptance v2 succeeds and preserves milestone; never submit stale v1 again.
If competitor rejected while acceptance was pending, fresh re-evaluation returns ILLEGAL_TRANSITION, no second save. If conflict persists after two attempts total, surface STALE_ORDER_VERSION (no unbounded tight retry).
No auto retry for recordPayment, recordRefundRequest (local milestone command identity and provider semantics unresolved), or ModifyOrderService replacement lines (stale user intent merge policy absent). No generic retry for PlaceOrderService new random ID (duplicate customer intent risk). These are policy choices justified by the CURRENT local-only code: if local lifecycle methods ever gain external effects, reevaluation policy must be revisited.
Classify recognized PostgreSQL pre-COMMIT SQLState 40001/40P01/55P03 into OrderDatabaseConcurrencyException with Kind, OrderId, sqlState; unrecognized/nullable SQLState remains OrderPersistenceException. In P15 COMMIT-attempted branch, return OrderCommitOutcomeUnknownException as before, even if exception text might resemble SQLSTATE; cannot infer rollback from missing acknowledgement.
No message broker, Outbox, Saga, provider processing, distributed locking, new DB schema, or durable request replay table introduced.

## Alternatives & force analysis
1 Retry every exception: categorically unsafe on uncertain commit, duplicate provider, stale business guards; reject.
2 Resubmit same successor on CAS failure: predicate still stale; reject.
3 Reload/reapply all commands: lines may overwrite customer intent, milestone/provider duplicates, no command ID; reject.
4 One fresh-state retry only for current local-only lifecycle operations: chosen bounded mechanism.
5 Automatically retry 40001/40P01/55P03 at repository: no transaction/business context and can amplify contention; classify only, defer generalized policy.
6 Durable idempotency key + request fingerprint, persisted result and atomic same-DB effects: viable when user-visible repeated command contract demands it, but requires SQL schema, TTL/key-scoping, response replay, in-progress/crash handling, external provider dedup and long-term semantics; not introduced as false blanket P18 solution.
7 External saga/Kafka: unjustified for current one-DB aggregate; cannot make provider operations globally atomic by message broker alone.

## Quality attributes, failure causes, observability
Consistency: winner's history preserved, re-evaluated guards; stale never overwritten. Latency: at most one extra full Order read+write for selected lifecycle conflicts, no p99 benchmark. Throughput: bounded retry avoids infinite retry storms; can still contend with concurrent traffic. Availability: transient lock/serialization failure propagated pending caller policy. Reliability: no blind duplicate financial milestones. Durability: P12 Postgres JVM recovery unchanged. Operability: classify SQLState and command-level rejection separately and log OrderId/expectedVersion/attempt counts/request correlation without PII; monitor retry_attempts, stale_version_conflicts, lock_wait, sqlstate40001, 55P03, unknown_commit_outcome, latency. No fabricated SLO.
Production diagnosis: Symptom repeated 409 vs 500 -> scope OrderId/actions -> timeline read version, CAS, competing commit -> evidence SQLState/current revision/history -> hypotheses stale overwrite vs external replay vs lock vs lost COMMIT -> controlled interleaving test -> causal chain -> policy mitigation -> verification on actual PG. Error alone is not root cause.
Forward dependencies: P19 contention sizing; P20 undersized invariants; P21 cross-aggregate truth; later command identity and external Payment reliability must be justified separately.
