# C1.2-P16 — Database Isolation and Concurrent Aggregate Modification

Source contract: Enterprise Distributed Systems Master Roadmap V8.0, derived Cluster 1.2 blueprint Part 1.2.16. Inherited frozen C1.2-P15 at aae54a4346f190cc02ff809b241c6fc64c11d3b8. The single production Food Ordering Platform persists one immutable Order aggregate over orders, order_lines, order_workflow_occurrences in PostgreSQL 16.

## Two distinct engineering questions
(1) Read coherence: can three SELECT statements used for one Order reconstruction observe ONE actual committed snapshot, or a mixture of old root and newer workflow history?
(2) Concurrent modification: what does PostgreSQL row locking and transaction isolation serialize/reject, and why does atomic committed SQL not imply fresh business decisions when the Order is loaded and saved in separate transactions?

## Inherited fragile state
P15 write repository uses explicit JDBC transaction for root and both child collections; COMMIT uncertainty classified separately. read findCurrentById previously used ordinary connection autoCommit true with three distinct SELECTs, so READ COMMITTED snapshots differ by statement. P14 domain reconstruction correctly rejects logically invalid root/history mixes, but this can incorrectly look like persisted corruption even when only valid states were committed. saveCurrent remains unconditional UPSERT/delete/reinsert successor without expectedVersion; two stale decisions may each be committed.

## Mechanism and chosen production evolution
P16 adds one read-only JDBC transaction per findCurrentById with TRANSACTION_REPEATABLE_READ, setReadOnly(true), setAutoCommit(false), root SELECT, ordered lines SELECT, ordered occurrences SELECT, domain reconstitution, db.commit to end read snapshot. On exception, rollback attempted with suppressed rollback failure. Absent root returns Optional.empty after ending transaction. RootReadObserver is a package-private NOOP for production and deterministic test-only scheduling at the root/child SQL boundary (allowed via package-private constructor); public API/DI untouched. Existing P15 ConnectionSource test seam preserved.
This is PostgreSQL MVCC *read coherence*, not a freshness/currentness guarantee, not SELECT FOR UPDATE locking, not serializable business decision, and not version-aware writes. A long-lived repeatable-read snapshot can be stale relative to later commits and may retain MVCC versions longer; keep read transaction bounded. DriverManager opens fresh connections; no pooled configuration or p99 performance evidence yet.

## Real failure and correctness schedules
S1 READ COMMITTED: reader transaction SELECT root -> PLACED; separate writer repo.saveCurrent commits ACCEPTED+RESTAURANT_ACCEPTED atomically; same reader SELECT history -> [RESTAURANT_ACCEPTED]. Assembled PLACED + ACCEPTANCE never a committed Order and current domain OrderInvariants rejects it.
S2 READ COMMITTED nonrepeatable: reader SELECT status PLACED, writer commits, reader SELECT same status -> ACCEPTED.
S3 REPEATABLE READ: reader first root SELECT PLACED fixes snapshot; writer commits ACCEPTED; reader still sees PLACED root and EMPTY history; subsequent fresh repository read sees ACCEPTED+history.
S4 Actual production repository deterministic interleaving: RootReadObserver CountDownLatch pauses reader after first SELECT, writer commits while reader paused (proves nonlocking ordinary MVCC SELECT), reader resumes and returns coherent precommit PLACED with old lines/history. Fresh read returns new accepted aggregate.
S5 Absent ID: read-only snapshot safely ends and returns Optional.empty.
S6 Row update lock: writer A UPDATE orders holds row lock in uncommitted tx; another writer with lock_timeout=250ms fails SQLState 55P03. Lock wait is a bounded resource, not proof of business currentness.
S7 SELECT FOR UPDATE NOWAIT: first transaction row locks root, ordinary MVCC SELECT from second connection succeeds; second SELECT ... FOR UPDATE NOWAIT fails 55P03. Not adopted for general read repository because unnecessary read contention and doesn't automatically protect read-then-save across separate transactions.
S8 Two actual application threads read SAME precommit PLACED Order, then concurrently attempt valid ACCEPT and REJECT domain successor writes; both return success despite mutually exclusive decisions; final state and one local workflow history correspond to whichever successor was last persisted. Physical write serialization != stale decision rejection. Preserve negative for P17 expected-version/CAS.
S9 A single PostgreSQL REPEATABLE READ read-modify-write transaction sees original PLACED snapshot, another connection commits ACCEPTED, then first tries to UPDATE stale row -> SQLState 40001 (serialization_failure); older accepted state persists. This protection does NOT apply to current application repository where read transaction already completed before separate saveCurrent write transaction. A 40001 must not be blindly retried without correct replay/re-evaluation policy (P18).

## Isolation alternatives
A Keep READ COMMITTED + three SELECTs: least setup overhead but proven torn root/history and spurious invalid reconstitution; reject for full aggregate read contract.
B One read-only REPEATABLE READ transaction (chosen): stable MVCC snapshot across statements, does not lock writers, small code change; adds read-transaction lifecycle and snapshot/resource retention.
C One SQL statement with JOIN or JSON aggregation: one PostgreSQL statement snapshot under READ COMMITTED, but multiple child JOIN produces LxH row multiplicity (P14), mapping/index/NULL child handling complexity and redesign; not warranted solely to avoid read tx.
D SELECT ... FOR UPDATE: row lock serializes certain modifications while held; increases contention, requires same transaction for read+business decision+write to guard currentness; does not replace P17 expected-version protocol.
E SERIALIZABLE: stronger guarantee for appropriate whole transactions, can cause SQLState 40001 and require complete retry (P18); expense/abort trade-offs not justified for simple read coherence.
F Optimistic version/CAS: P17 scope. No new version field added now.
G Queue/Redis/distributed lock/microservice topology: unrelated to local MVCC snapshot guarantee, unjustified.

## Architectural quality attributes / physical costs
Correctness: one committed snapshot per full Order reconstitution. Latency: 3 SQL SELECT plus BEGIN/COMMIT, connection per call; not benchmarked. Concurrency: MVCC read doesn't block writer in controlled test; actual row writes acquire locks; lock waits, lock_timeout and SQLState 55P03 observable. Snapshot age/repeatability competes with latest-state freshness; prolonged reads consume DB resources/MVCC cleanup horizon. Serializability/version conflict and retries deferred. Data integrity: source/epoch of persisted state must be distinguished from cross-row committed corruption. Observability: log OrderId, transaction snapshot context, SQLState, lock wait, query timing, and connection resource context without sensitive data.

## Production incident analysis
Symptom: InvalidPersistedOrderException occurs only during concurrent acceptance. Competing hypotheses: committed corrupt rows (P13), incomplete write (P15), wrong mapper (P14), mixed READ COMMITTED snapshots (P16). Discriminating test pauses after root SELECT and commits writer before history SELECT, compare READ COMMITTED mismatch versus REPEATABLE READ coherent precommit snapshot. Fix selected at read boundary. Separate incident: two business operations both acknowledged -> reconstruct shared stale source version and no expectedVersion guard; P17 needed. A 55P03 lock timeout is not a business rejection and retrying it blindly can amplify pressure.

## Future handoff
P17 expected version/CAS detect stale immutable successor across separate read/save transactions. P18 conflict classification, retry and idempotency handling for 40001/55P03/committed-ack-unknown as appropriate. No external Payment provider outcome guaranteed by any local DB isolation. No work in additional microservices or Customer/Restaurant SQL entities here.
