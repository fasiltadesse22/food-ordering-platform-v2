# C1.2-P04 — Deriving Aggregate Candidates from Invariants

Inherited: checkpoints/C1.2-P03 (55c6169194ebbc19aae437462ec1a7358a772f3d). Course 2 V8.0, Cluster 1.2 Part 1.2.4, Type A.
Question: How can we derive an aggregate candidate from invariant ownership and lifecycle cohesion rather than classes, tables or prospective services?

## Actual source observations
Order.java holds OrderId, CustomerId, RestaurantId, List<OrderLine>, OrderStatus, placedAt and List<OrderWorkflowOccurrence>. Order.place creates initial representation. recordRestaurantAcceptance, recordRestaurantRejection, recordCancellation, recordPreparationStarted and recordCompletion use transition -> OrderEvolution -> apply -> a new immutable Order with selected OrderInvariants checks. modifyLines needs customerId/status and appends ORDER_MODIFIED. recordRefundRequest checks status plus PAYMENT_RECORDED/REFUND_REQUESTED in local history. OrderRepository stores/loads one current Order by OrderId; in-memory saveCurrent is unconditional ConcurrentHashMap.put. There is one deployable and no DB.

## Candidate consistency root
- Identity and lifecycle unit: one continuing OrderId, not one Java object reference.
- Candidate root: Order as domain decision entrypoint for current Order state, lifecycle and selected local rules.
- Internally governed state: OrderStatus, workflow occurrences, Order lines, associated customer/restaurant IDs and initial placement time.
- References, not owned full aggregates: Customer account, Restaurant profile/menu, payment provider charge/refund; no current local authority for those.
- Current value-like constituents: typed IDs, OrderLine, workflow occurrences. Entity/value classification and Java equality are reserved for P05/P06.
- Guard / invariant / persistence semantics are separate: normal domain path checks selected rules; repository currentness/commit lacks freshness, durable transaction or restart recovery.

## Invariant ownership matrix
| Operation or invariant | State required | Candidate enforcing authority | Boundary pressure and caveat |
|---|---|---|---|
| Placing Order requires nonempty valid lines | identity, customerId, restaurantId, lines | Order factory | business actor guard also in application |
| ACCEPT requires PLACED and matching restaurant | current status, restaurantId, actor context | Order decision | context ID is not authenticated external Restaurant truth |
| CANCEL requires PLACED and matching customer | current status, customerId, actor context | Order decision | concurrency winner policy unresolved |
| REJECT requires PLACED and matching restaurant | status, restaurantId, actor context | Order decision | mutually exclusive with accepted/cancelled histories |
| PREPARING requires acceptance + preparation facts | status and occurrences | Order construction | exact complete-history validation not implemented |
| COMPLETED requires acceptance/preparation/completion facts | status and occurrences | Order construction | P11 split-write failure justifies coupled authoritative commit |
| Cancellation/rejection/completion facts imply corresponding status | status and occurrences | Order construction | selected implications, not event-store validation |
| MODIFY requires PLACED, matching customer, valid replacement lines | status, customerId, lines and history | Order decision | P17 stale representations can evade current-state precondition |
| REFUND_REQUEST requires rejected/cancelled, payment fact, no refund request | status and local occurrences | Order decision | external provider refund/charge authority excluded |
| Current authority must survive JVM lifetime | entire committed Order needed for recovery | future repository | not guaranteed now, P18 negative evidence |
| Incompatible concurrent commands require correct authoritative result | selected Order version / current state | future repository commit contract | P13/P14 negative evidence; no version mechanism yet |

## Candidate comparison
A: One Order-centered local immediate consistency boundary. Strong direct invariant and lifecycle alignment; minimal current coordination. Risks: history size and aggregate-wide contention, not yet measured. Preferred provisional model.
B: Separate status and history aggregates with independent commit. Unjustified: P11 shows invalid partial states when status and facts are independently changed; would need joint coordination or weaker business requirement. Separate SQL tables inside one transaction might still map to A; table split != aggregate split.
C: Giant Order owning entire Customer, Restaurant, menu, inventory, provider payment ledger. Rejected: no established immediate invariant for full related state; independent lifecycles, false financial authority and excess coupling. Cannot create atomic provider effect through object containment.
D: Aggregate per prospective service (Order, Payment, Restaurant). Rejected as derivation method: deployable is not aggregate, bounded context, transaction or table.
E: History as asynchronous projection. Viable under a changed business contract where it is not immediately authoritative and has reliable reconstructible source; not current model. Explicitly defer.

## Falsification and evolution conditions
Revisit candidate when measured contention, independently evolving local responsibilities, huge history, new inventory capacity invariants or changed history-authority policy justify changes. Do not claim those pressures are currently measured.
An artificial split failure is an epistemic counterexample, not a proposal to replace production Order with mutable status/history models.
Neither aggregate nor immutable representation alone guarantees isolation, stale rejection, durability, external idempotency or global business correctness.

## Deferred
