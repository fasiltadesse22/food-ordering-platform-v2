# C1.1-P11 — Atomicity and Local Consistency Boundaries

## Engineering question

Which related changes belong to one logical business decision and must not become independently visible?

## Completion decision

For the current Order model, completing preparation logically requires:

1. lifecycle state becomes COMPLETED;
2. workflow history gains ORDER_COMPLETED.

These are not two independent business outcomes.

They are two representations of one business decision.

Therefore the current invariant requires them to move together.

## Safe current path

PREPARING Order
→ validate COMPLETE transition
→ create OrderEvolution(
     nextStatus = COMPLETED,
     occurrence = ORDER_COMPLETED
   )
→ build one new immutable Order
→ verify invariants
→ repository replaces one current Order reference

No normal production path intentionally exposes a new Order with only one half of the pair.

## Fragile split model

If the same decision is represented by two independently committed mutable stores:

status authority
history authority

then both orderings contain a failure window.

### Status first

status = COMPLETED
[FAILURE WINDOW]
append ORDER_COMPLETED

### History first

append ORDER_COMPLETED
[FAILURE WINDOW]
status = COMPLETED

The invariant detects either partial state.

## Atomicity versus consistency

Atomicity:
the related changes become visible together or not at all.

Consistency:
the resulting state satisfies the domain invariants.

Atomicity does not create correct rules.

An atomic operation can still atomically commit an invalid business state if the rules are wrong.

## Atomicity versus concurrency

One complete map-entry replacement does not make:

read current
→ decide
→ replace current

atomic across competing threads.

Concurrent lost-update/conflict behavior is intentionally preserved for P13/P14.

## Atomicity versus durability

The repository is in memory.

Even a perfectly complete current representation disappears on process restart.

Atomicity answers "partial or whole?" within the current authority boundary.

Durability answers "does committed state survive failure/restart?"

Different property.

## Atomicity versus distributed transaction

P11 has one JVM and one in-process Order authority.

There is no multi-service atomic commit and no 2PC/Saga.

Those mechanisms are not authorized by this part.
