## Engineering question
Which Order state constraints can and should PostgreSQL enforce independently of Java domain constructors, which depend on multiple rows/decisions/authorities, and what observable effects follow when invalid data or legacy dirty data meets a migration?

## Actual before-state
P11 V1: UUID root PK; composite child position PKs, child FK, required NOT NULL. Direct SQL accepted order_lines quantity=0 / unit_price=-2 even though OrderLine.java rejected those values. P12 reconstitution rejects zero quantity, but that does not prevent invalid rows from being committed. P12 still used PostgreSQL and retained original memory P18 negative and actual DB recovery positive.

## Classification and scope
Identity: orders(id) UUID PK; child (order_id,position) PK — inherited, no duplication.
Referential integrity: child order_id FK orders(id) — inherited. FK does NOT ensure every Order has >=1 line.
Local row validity: selected CHECK constraints added in immutable forward-only Flyway V2.
Cross-row/aggregate causal invariants: completed status requires accepted+preparing+completed history (domain P07) and Order nonempty line collection; ordinary row-local CHECKs do NOT prove these; P12 reconstitution and later transactional analysis needed.
Cross-aggregate or external authority: Customer identity, Restaurant eligibility, Payment provider charge and refund are NOT enforced with invented FK or database-per-service design.

## Added V2 constraints (11 named CHECK constraints)
orders: customer_id/restaurant_id btrim length >0; status in PLACED,ACCEPTED,REJECTED,CANCELLED,PREPARING,COMPLETED.
order_lines: line_position>=0; menu_item_id/item_name btrim length >0; quantity>0; price>=0 AND != numeric NaN AND != numeric +Infinity. Negative Infinity excluded by >=0. Zero price remains legal; no currency, fixed NUMERIC scale, rounding or maximum amount introduced.
order_workflow_occurrences: occurrence_position>=0; action in eight OrderWorkflowAction enum names; participant in four WorkflowParticipant enum names.
Constraints are attached to DB rows, apply to direct SQL and future adapters, and report PostgreSQL SQLState 23514 for violations. SQL CHECK accepts UNKNOWN, so already-existing NOT NULL columns remain important.
SQL btrim default ASCII-space trimming != Java String.isBlank Unicode semantics. This adds a database barrier but is not proof of fully equivalent cross-language Unicode handling.
Enum vocabulary constraints couple schema evolution to the Java domain. Adding a new lifecycle/action/participant label will require a compatible versioned DB migration.

## Mechanism and atomicity
P13 does not redefine the Order aggregate or its local write transaction. A violated CHECK rejects the DML statement; P12 writer propagates SQL failure as OrderPersistenceException rather than normal Order business rejection. On a rejected update, earlier row values remain unchanged in the tested autocommit case.
P12 createNew maps duplicate UUID 23505 to OrderAlreadyExistsException, but row-level CHECK 23514 is not identity conflict. Parent FK 23503, NOT NULL 23502, UNIQUE 23505 all distinct.
A row-local check cannot verify accepted workflow history or min child count, cannot prove domain-causal ordering, correct acting actor, source state or Payment provider truth. No full state-machine triggers or distributed transactions added.

## Migration and operational correctness
V1 is unchanged, V2 additive versioned Flyway script. PostgreSQL validates old rows on ADD CONSTRAINT. Test starts one DB at V1, inserts invalid qty/price, attempts V2 (fails), repairs the row under explicit test control, then retries V2 (success); after V2 it rejects the same invalid write. Production must investigate/remediate existing invalid rows before rollout; NEVER pretend a migration always succeeds with populated data. For large tables, alternative staged NOT VALID + VALIDATE CONSTRAINT can reduce some operational lock impact; not implemented because baseline is small and scope evidence does not demand it. Real deployment time/locks and rolling compatibility not benchmarked.
