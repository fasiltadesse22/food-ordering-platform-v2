# C1.1-P13 — Conflicting Operations, Concurrency Windows and Deterministic Traces

**Contract:** V8.0 and Cluster 1.1 blueprint P13; **Type C Controlled Failure / Stress Evolution**. The experiment uses actual Java worker threads, `CountDownLatch` and a **test-only** coordinating `OrderRepository` wrapping the unchanged production `InMemoryOrderRepository`. There is **no distributed lock, database lock, optimistic version, transaction manager or new runtime synchronization**.

## Question, hypothesis and prediction

**Question:** What happens when individually legal commands overlap on one authoritative current Order?

**Hypothesis:** Given `OrderWorkflowService.update` = repository read → P07 guard → new immutable valid Order → map put, two workers may both read the same predecessor, both construct locally valid successors, and the last save may erase an earlier accepted effect.

**Prediction:** If A (preparation) and B (cancellation) both read the same paid-and-accepted Order, their individual domain decisions pass. Force A save then B save: A returns PREPARING but final current is CANCELLED without A's preparation occurrence. Force B save then A save: B returns CANCELLED but final current is PREPARING without the terminal cancellation fact. Both final Orders remain P10-locally valid relative to their *own* histories; that is precisely why local guards/invariants don't establish global correctness.

## Controlled variables

- Real `Thread` A and B with a separate `OrderWorkflowService` for each; both use the same test wrapper over the real production in-memory repository.
- Fixed Java `Clock` and same `OrderId` for conflicting cases.
- At `findCurrentById` each thread captures an actual returned reference **before** signaling `bothRead`. The barrier prevents either from computing/publishing until both have captured the old Order.
- `firstSaved` latch forces a chosen first and second repository save order. B is *not* permitted to publish first when A is designated first.
- Thread names, read status/history counts and saved status/action histories are captured in a synchronized trace.
- 10-second bounded waits and cleanup release latch on failed test; no infinite random retry loop.
- No source changes in `OrderWorkflowService`, `Order`, `OrderTransitionContract`, `OrderBusinessInvariants` or `InMemoryOrderRepository`.

## Interleaving A — Prepare then Cancel

Initial: `ACCEPTED` with prior `PAYMENT_RECORDED` and `RESTAURANT_ACCEPTED`.

```text
A (p13-A)                           B (p13-B)
READ ACCEPTED, paid                 READ ACCEPTED, paid
             [both-read barrier released]
PREPARATION_STARTED guard passes    ORDER_CANCELLED guard passes
build PREPARING+fact                build CANCELLED+fact
P10 local history valid             P10 local history valid
SAVE PREPARING [firstSaved]         waits for firstSaved
returns PREPARING snapshot          SAVE CANCELLED
                                    returns CANCELLED snapshot
repository final = CANCELLED, no PREPARATION_STARTED
```

**Broken global condition:** A was acknowledged as having started preparation, but accepted Order's current history no longer records A. No individual Order representation contains an impossible sequence: the failure is **loss of the already-accepted transition**.

## Interleaving B — Cancel then Prepare

Identical initial state and two captured reads, but force B save first. B reports CANCELLED, then stale A publishes PREPARING. Final current Order has no ORDER_CANCELLED fact. **Terminal cancellation was acknowledged then effectively undone by a stale writer**, even though no local legal transition from CANCELLED to PREPARING was executed. This is not a legitimate state reversal or a financial compensation.

## Interleaving C — Cancel then record local payment

Start PLACED with empty history. Force A's cancellation write first, B's `PAYMENT_RECORDED` (built from stale PLACED) second. Final current Order returns to PLACED with local payment occurrence, losing the previously accepted terminal cancellation. This is an **application-local payment milestone**, not a real card charge.

## Interleaving D — Local payment then cancel

Start PLACED. B's local payment event publishes first; then A's stale cancellation publishes. Final current Order is CANCELLED with no PAYMENT_RECORDED occurrence, despite B's successful returned snapshot. The absence of the local payment fact does not prove funds weren't actually captured—there is no provider.

## Interleaving E — Two simultaneous cancellations

Both read PLACED; both construct CANCELLED with one occurrence; both report accepted. The final current Order may contain only one local cancellation occurrence. This demonstrates **acceptance ambiguity**, not an implementation of deduplicated command identity; repeated commands are studied in P15.

## Serial control experiments

A fully **serial** preparation followed by cancellation denies cancellation from PREPARING; serial cancellation followed by preparation denies preparation from CANCELLED. P07/P10 correctly enforce both sequences when each subsequent command reads the actual newest Order.

The critical manipulated variable is the read synchronization: in the concurrent experiment, both guards inspect the same earlier source.

## Independent-key control

Two operations on different OrderIds may both be committed into different map entries without overwriting each other. The race depends on conflicting ownership of the **same current business identity**; it is not proof that every concurrent pair causes corruption.

## Exact evidence expected from Maven execution

The new source `OrderConflictingOperationsConcurrencyTest` comprises **10 named JUnit tests**. Each intentionally asserts the *undesirable final state* so the test suite passes when the **known weakness is reproduced**. A green CI run is therefore **not proof the race was solved**. It proves the harness could force the documented schedule and observe the asserted lost-fact outcome.

Record the actual GitHub Actions run ID, test count and result in the subsequent evidence ledger **only after execution finishes**.

## Consistency / evidence distinctions

- P10 checks `I(Order)`, one immutable represented history.
- P13 demonstrates a violation of **accepted-operation preservation**: once an action was returned as accepted to its caller, its fact should not vanish from subsequent authoritative history without an explicitly modeled correction.
- A read-barrier + two real threads is an **executed deterministic concurrency test**. It is not an uncontrolled production traffic measurement or a network partition simulation.
- `CountDownLatch` is **test-only coordination** here. It does not protect business state in production.
- Individual `ConcurrentHashMap.put` operations can publish complete immutable Orders; this does not make **read–guard–save** one atomic conditional decision.
