# C1.1-P14 — Cancellation / Acceptance Race

## Engineering question

When customer cancellation and restaurant acceptance race from the same Order version, what should correctness mean, who is allowed to win, what can each participant know, and how do we distinguish concurrency-control mechanism from business conflict policy?

## Actors and intents

Customer:
"I no longer want this Order."

Restaurant operator:
"I commit to fulfil this Order."

Both intents may be legitimate while current authority is:
PLACED

## Serial histories

### Cancellation serializes first

PLACED
→ CUSTOMER CANCEL
→ CANCELLED

Restaurant ACCEPT then observes:
CANCELLED

Outcome:
- cancellation accepted;
- acceptance rejected as ILLEGAL_TRANSITION.

### Acceptance serializes first

PLACED
→ RESTAURANT ACCEPT
→ ACCEPTED

Customer CANCEL then observes:
ACCEPTED

Outcome under current lifecycle:
- acceptance accepted;
- cancellation rejected as ILLEGAL_TRANSITION.

Both are valid serial histories.

## Invalid concurrent acknowledgement history

Both actors capture:
PLACED

Customer derives:
CANCELLED + ORDER_CANCELLED

Restaurant derives:
ACCEPTED + RESTAURANT_ACCEPTED

Both application calls return:
Accepted

No valid serial ordering of the current state machine permits both to independently succeed from the same logical PLACED version.

Therefore the acknowledgement history is invalid even if the final Order object is itself structurally valid.

## Participant knowledge

### Customer after local success

Customer-side request knows:
- it read/captured a PLACED Order through the service path;
- cancellation transition passed;
- saveCurrent returned;
- application returned Accepted(CANCELLED).

It does not know:
- a restaurant acceptance was derived concurrently;
- its cancellation will remain the surviving current authority.

### Restaurant after local success

Restaurant-side request knows:
- it read/captured PLACED;
- acceptance transition and restaurant ownership guard passed;
- saveCurrent returned;
- application returned Accepted(ACCEPTED).

It does not know:
- a customer cancellation was derived concurrently;
- its acceptance will remain current authority.

### Later observer

A later reader knows only the last surviving current Order representation.

With today's repository it may not know that another mutually exclusive decision was previously acknowledged.

## Authority versus intent ordering

Customer pressing Cancel first in wall-clock/user perception is not automatically the same as:
- request reaching server first;
- authoritative state being read first;
- decision being computed first;
- authoritative save committing first.

Correctness policy must define which event matters.

## Minimal correctness property

At most one mutually exclusive transition from one logical PLACED version may be acknowledged as authoritative success.

The losing intent must receive a conflict/business outcome consistent with whichever serial order/business priority the policy defines.

## Mechanism versus policy

Mechanism examples:
- expected-version conditional write;
- optimistic lock;
- per-Order serialization;
- pessimistic lock.

Policy examples:
- first successful authoritative commit wins;
- cancellation has priority before cutoff;
- acceptance creates a commitment after which cancellation changes semantics.

Mechanism enforces a decision boundary.

Policy defines what the decision means.
