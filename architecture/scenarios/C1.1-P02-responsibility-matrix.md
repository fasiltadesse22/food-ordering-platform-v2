# C1.1-P02 — Responsibility Matrix

| Business participant / element | Goal or purpose | Business responsibility | Software responsibility currently carrying it | What this does **not** imply |
|---|---|---|---|---|
| Customer | Obtain food from a restaurant | Initiate their own order intent | `PlaceOrderUseCase` / `PlaceOrderService` | Customer Service, customer database, microservice |
| Restaurant operator | Decide whether restaurant will fulfill order | Accept/reject; later preparation actions | Not implemented yet | Restaurant Service |
| Payment participant | Produce/communicate monetary outcome | Payment/refund participation | Not implemented yet | Payment Service, Kafka, Saga |
| Order | Represent order identity/state | Hold valid order state/behavior | Domain `Order` | Actor, service, table boundary |
| HTTP client | Transport a request | None inherently; caller role depends on business context | `OrderController` translates HTTP to application input | Authenticated customer |
| Application service | Coordinate use-case steps | No independent business goal | `PlaceOrderService` | Business actor |
| Repository | Store/retrieve current state | No business goal | `OrderRepository` + in-memory adapter | Aggregate/service/database ownership decision |

## Responsibility-allocation test

For every proposed noun, ask:

1. Is this a participant with a goal?
2. Is it a business responsibility?
3. Is it application orchestration?
4. Is it domain state/behavior?
5. Is it an infrastructure mechanism?
6. Is it merely a future decomposition hypothesis?

The answer determines whether the concept belongs in an actor model, use-case model, domain model, adapter, or later architecture decision.
