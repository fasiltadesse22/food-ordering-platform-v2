# C1.1-P03 — Candidate Command and Fact Catalog

This catalog is a semantic discovery artifact, not an implementation plan.

Only PlaceOrder → OrderPlaced is executable in P03.

| Actor intent | Candidate command | Candidate accepted fact | P03 status | Important unresolved questions |
|---|---|---|---|---|
| Customer wants to place order | PlaceOrder | OrderPlaced | Executable | duplicate intent, later lifecycle legality |
| Payment participant reports/records successful payment | RecordPayment | PaymentRecorded | Candidate only | authority, provider semantics, duplicate external effects |
| Restaurant wants to accept | AcceptOrder | OrderAccepted | Candidate only | legal source states, cancellation race |
| Restaurant wants to reject | RejectOrder | OrderRejected | Candidate only | legal timing, reasons, payment consequence |
| Customer/policy actor wants cancellation | CancelOrder | OrderCancelled | Candidate only | who may cancel, terminal states, compensation |
| Customer/platform requests refund | RequestRefund | RefundRequested | Candidate only | request vs completed financial refund fact |
| Restaurant begins preparation | StartPreparation | PreparationStarted | Candidate only | requires accepted state, concurrent cancellation |
| Restaurant/platform completes order | CompleteOrder | OrderCompleted | Candidate only | terminal semantics and preconditions |

## Why these are only candidates

Names such as OrderAccepted or OrderCancelled sound obvious, but their legitimacy depends on lifecycle, state-machine and invariant reasoning in later parts.

CancelOrder is only a request. Whether OrderCancelled may become true depends on current state and business rules.

Likewise RequestRefund must not be confused with RefundCompleted: requesting an external financial action and observing that it completed are different facts.

The catalog intentionally creates vocabulary pressure for later parts without implementing those semantics early.
