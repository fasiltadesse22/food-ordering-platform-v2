# C1.1-P07 — Guards, Preconditions and Postconditions

## Engineering question

Even when a transition is structurally legal from the current state, what else must be true before it may occur, and what must be true afterward?

## Contract layers

### Validation

Validation asks whether supplied values are structurally acceptable.

Examples:
- CustomerId must not be blank.
- RestaurantId must not be blank.

A value can pass validation and still fail a domain guard.

### State precondition

For a lifecycle transition, the current OrderStatus must match the transition source.

Example:

ACCEPT requires PLACED.

### Contextual precondition

Business context must satisfy additional facts.

Examples:
- acting restaurant must equal Order.restaurantId;
- acting customer must equal Order.customerId;
- refund request requires a recorded payment;
- refund request requires REJECTED or CANCELLED lifecycle state.

### Guard

A guard is the executable predicate/check that enforces a selected precondition at the decision point.

A precondition is the contract statement.

A guard is one mechanism that checks it.

### Postcondition

A postcondition states what a successful operation guarantees afterward.

For successful ACCEPT in P07:
- same OrderId;
- same CustomerId;
- same RestaurantId;
- same lines, placedAt and derived total;
- status becomes ACCEPTED;
- one RESTAURANT_ACCEPTED workflow occurrence is appended at the operation time;
- original immutable Order remains PLACED.

## Evaluation path

Restaurant acceptance:

current Order
→ require source state PLACED
→ require actingRestaurantId == order.restaurantId
→ create next immutable Order
→ status ACCEPTED
→ append RESTAURANT_ACCEPTED
→ save current representation

Cancellation:

current Order
→ require source state PLACED
→ require actingCustomerId == order.customerId
→ create next immutable Order
→ status CANCELLED
→ append ORDER_CANCELLED
→ save current representation

Refund request:

current Order
→ require status REJECTED or CANCELLED
→ require PAYMENT_RECORDED in workflow
→ keep lifecycle status unchanged
→ append REFUND_REQUESTED

## Important distinctions

guard != input validation

precondition != postcondition

source-state legality != complete business eligibility

claimed actor identity != authenticated identity

guard rejection != technical infrastructure failure

## P06 fragile baseline

At checkpoint C1.1-P06, restaurant/customer identity was not supplied to workflow operations.

Therefore the system had no information with which to distinguish:
- owning restaurant vs another restaurant;
- owning customer vs another customer.

This is the preserved guard-bypass baseline.

## Remaining weakness

The guard reads the current Order representation passed to it.

If that representation is stale, a guard can correctly evaluate stale facts.

P07 does not solve that problem.

That is intentional pressure for later stale-decision/concurrency parts.
