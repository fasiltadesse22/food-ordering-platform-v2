# C1.1-P13 — Conflicting Operations and Concurrency Windows

## Engineering question

How can two individually legal business decisions conflict when both are made from the same previously authoritative state?

## Conflict definition

Two operations conflict when:
- they address the same authoritative business state;
- their effects cannot both belong to one valid serial history as independently accepted outcomes; and
- execution overlap allows both decisions to be made before either observes the other's committed successor.

For the P13 experiment:

Initial:
PLACED

Operation A:
ACCEPT
PLACED → ACCEPTED

Operation B:
REJECT
PLACED → REJECTED

Both transitions are individually legal from PLACED.

But one serial history cannot contain both as independently accepted transitions from the same Order version.

## Sequential baseline

History:

read PLACED
→ ACCEPT
→ save ACCEPTED

then:

read ACCEPTED
→ REJECT
→ ILLEGAL_TRANSITION

Only one decision succeeds.

This is consistent with the state machine.

## Concurrent vulnerable path

Timeline:

T0 authority = PLACED

T1 A reads PLACED
T2 B reads PLACED

T3 A validates ACCEPT against its PLACED snapshot
T4 B validates REJECT against its PLACED snapshot

T5 A constructs ACCEPTED
T6 B constructs REJECTED

T7 A saves ACCEPTED
T8 B saves REJECTED

Final authority:
REJECTED

A still received:
Accepted(ACCEPTED)

The final authoritative history has no RESTAURANT_ACCEPTED occurrence because B's immutable successor was independently derived from the original PLACED snapshot.

## Lost-decision shape

This is similar to a lost update:

shared S0

A: f(S0) = SA
B: g(S0) = SB

save SA
save SB

final = SB

The important business meaning is stronger than "one field got overwritten."

A complete accepted decision and its history disappeared from current authority.

## Conflict window

The vulnerable interval is:

read current authority
----------------------
decision against read snapshot
construct successor
----------------------
save successor

The wider this interval becomes, the more opportunity another writer has to change authority before this operation saves.

Network/database latency will later make such windows larger and more consequential.

## Local validity versus global history validity

A's successor is valid by itself.

B's successor is valid by itself.

The problem is the combined concurrent history:

both application calls report Accepted
but only one successor survives.

Therefore:

valid(A(S0)) AND valid(B(S0))
does not imply
validConcurrentHistory(A,B,S0)

## Why immutable Order does not solve it

Immutability prevents half-mutated individual Order objects.

It does not stop two callers from:
- reading the same immutable S0;
- independently deriving SA/SB;
- overwriting current authority in different orders.

## Why ConcurrentHashMap does not solve it

Each get/put is safe at the collection-operation level.

The business transaction spans:
get
→ decide
→ put

No compare-with-original-version occurs at put time.

## Why P13 does not fix it

The roadmap requires preserved fragile states and evidence before tactics.

Adding a lock/version now would erase the before-state.

P13 therefore establishes:
- the conflict;
- the exact window;
- schedule sensitivity;
- evidence;
- non-guarantees.

Mechanism selection comes later when the persistence/consistency context is known.
