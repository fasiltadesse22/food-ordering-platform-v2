# C1.2-P12 — PostgreSQL Adapter, Reconstitution and Durable Recovery

Roadmap: Master V8.0 Cluster 1.2, derived blueprint part 1.2.12.
Inherited frozen P11: 1defeffc57170d86b5c0afc122f48b8f5ef826a2.
Engineering question: Can a fresh JVM reconstruct one complete, valid, previously acknowledged Order from the same PostgreSQL authority after SIGKILL?

## Source-derived architecture
Production `PostgresOrderRepository implements OrderRepository` with `createNew`, `saveCurrent`, `findCurrentById`; root + ordered lines/history on schema V1.
`Order.reconstitute` is distinct from `Order.place`, invoking the constructor and P07 selected status/history invariants. No command replay; no reconstructed `OrderPlaced` event or payment provider truth.
`OrderPersistenceException` signals SQL/connection failures; `InvalidPersistedOrderException` signals present but invalid stored domain data; missing root returns Optional.empty only.
Backend selection: env ORDER_REPOSITORY_BACKEND defaults memory for inherited experiments, postgres opt-in; runtime connection ORDER_JDBC_URL, ORDER_DB_USERNAME, ORDER_DB_PASSWORD. The PostgreSQL backend runs Flyway V1 before use and fails startup if unusable; never silently falls back to memory.
No new deployable services. CustomerId and RestaurantId remain references, not new DB authorities.

## Write mechanism
`createNew`: connection autocommit false; INSERT root; batch INSERT all lines and history; COMMIT or ROLLBACK. Duplicate root UUID SQLState 23505 maps to OrderAlreadyExistsException. No hidden business duplicate/idempotency claim.
`saveCurrent`: deliberately unconditional root UPSERT ON CONFLICT, DELETE+INSERT entire owned line/history collections in one JDBC transaction. Commits complete aggregate snapshot; still accepts stale last-writer-wins, preserves P17 and P10 upsert negative controls. No expectedVersion, no CAS, no distributed coordination.
Transaction necessity: PostgreSQL multiple tables must not leave a committed partial Order after a failing write; P15 owns the rigorous failure-injection and rollback/transaction-isolation evolution. Current simple local transaction is minimum coherent multi-table persistence prerequisite, not evidence of all failure windows.

## Read/reconstitution
SELECT root; if no row -> Optional.empty. SELECT lines ordered by line_position; SELECT occurrences ordered by occurrence_position on same connection. Build OrderLine and OrderWorkflowOccurrence real domain values, parse enums, and invoke Order.reconstitute; verify nonempty lines and selected status/history invariants. Actual malformed row -> InvalidPersistedOrderException; connection/SQL failures -> OrderPersistenceException; never conflate missing, invalid, inaccessible state.
READ COMMITTED default multiple SELECTs may observe cross-statement inconsistent snapshots under concurrent writers. P12 demonstrates serial reconstruction and durable recovery, NOT comprehensive consistency of concurrent reads. P16 will measure and decide isolation semantics. No full causal chronology/duplicate event validation.

## Actual process restart experiment
CI starts PostgreSQL 16 GitHub Actions service with same DB alive across two java -jar processes. Env selects postgres. Process A HTTP POST /orders ->201, POST /orders/{id}/cancel ->200 status CANCELLED; SIGKILL Java PID. Process B starts with same JDBC URL, auto-validates migration, GET same OrderId ->200 with preserved CANCELLED status, identity/customer/restaurant/line price/quantity/total.
This positive control is run alongside original C1.1-P18 memory negative control (A CANCELLED -> B 404). Same runtime domain and HTTP API, only backend changes.
This experiment isolates process replacement, not DB host failure, replica failover, fsync hardware faults or disaster recovery. Response DTO does not expose workflow history; separate real JDBC tests verify history restoration.

## Remaining risks and handoffs
P13 constraints: DB currently accepts invalid quantity/price (direct SQL); reconstitution detects selected corruption but does not prevent insertion.
P14 representation/reconstitution options and time/BigDecimal precision mapping; Java Instant ns -> PostgreSQL us precision may differ.
P15 explicit transaction failure windows/rollback, partial writes and commit-ack ambiguity.
P16 actual isolation/read tearing and contention; read uses default READ COMMITTED with separate SELECTs.
P17 stale successor overwrite because no version/CAS.
P18 conflict/retry decisions, idempotency/unknown outcomes; no retries automatically.
No Hikari pool currently, each repository operation opens a JDBC connection; performance/scalability not measured. Database durability is conditional on PostgreSQL operating/durability config; no HA/backup/DR claims.
