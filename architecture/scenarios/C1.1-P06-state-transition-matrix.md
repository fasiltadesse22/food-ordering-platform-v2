# C1.1-P06 — Business-derived lifecycle transition matrix

**Lineage:** independently implemented on `redo/v8-c1.1-p06`, branched from verified historical P05 commit `fa37c3b0cff91e3812cc0d6fa10373c9d46a9daf`. Pre-existing P06 and later branches were deliberately **not** consulted as implementation sources.

**Engineering decision:** Model one primary *fulfillment* lifecycle with distinct orthogonal payment/refund milestones. This policy is **provisional**: restaurant/payment business stakeholders must validate it before production.

## State vocabulary

- `PLACED` — the application accepted initial Order placement; fulfillment not yet committed by restaurant.
- `ACCEPTED` — restaurant accepted responsibility, without preparation started.
- `PREPARING` — preparation started after acceptance and a local payment milestone, as this P06 teaching policy requires.
- `COMPLETED` — preparation was completed for this selected restaurant-side fulfillment definition; no further fulfillment transitions.
- `REJECTED` — restaurant declined fulfillment before acceptance; terminal for fulfillment.
- `CANCELLED` — cancellation was accepted while placed or accepted; terminal for fulfillment.

`PAYMENT_RECORDED` and `REFUND_REQUESTED` remain workflow occurrences, not primary fulfillment states. They are **not** authoritative provider effects. Refund request can be appended after terminal fulfillment rejection/cancellation without reopening that primary state.

## Legal transition matrix

| Current primary state | Action / trigger | Guard | Next primary state | Resulting local occurrence |
|---|---|---|---|---|
| PLACED | PAYMENT_RECORDED | no earlier payment occurrence | PLACED | payment milestone |
| ACCEPTED | PAYMENT_RECORDED | no earlier payment occurrence | ACCEPTED | payment milestone |
| PLACED | RESTAURANT_ACCEPTED | state is PLACED | ACCEPTED | restaurant acceptance |
| PLACED | RESTAURANT_REJECTED | state is PLACED | REJECTED | restaurant rejection |
| PLACED | ORDER_CANCELLED | state is PLACED | CANCELLED | customer cancellation |
| ACCEPTED | ORDER_CANCELLED | before preparation | CANCELLED | customer cancellation |
| ACCEPTED | PREPARATION_STARTED | payment milestone already recorded | PREPARING | preparation started |
| PREPARING | ORDER_COMPLETED | state is PREPARING | COMPLETED | restaurant completion |
| REJECTED | REFUND_REQUESTED | prior payment and no prior refund request | REJECTED | refund request |
| CANCELLED | REFUND_REQUESTED | prior payment and no prior refund request | CANCELLED | refund request |

**All unspecified combinations are rejected** with `InvalidOrderTransitionException`, including duplicate accepted decisions and attempts to resume fulfillment after terminality. A denied action never appends its occurrence and does not reach `repository.saveCurrent` on the synchronous application path.

## Representative forbidden edges (exact V8 blueprint)

| Attempt | Why forbidden |
|---|---|
| COMPLETED → ACCEPTED | A completed fulfillment cannot be newly accepted |
| CANCELLED → PREPARING | Cancellation closes fulfillment; consumed resources cannot be restarted via the same Order state |
| REJECTED → COMPLETED | Declined fulfillment cannot be completed under the same lifecycle |
| PLACED → PREPARING | Restaurant acceptance is missing |
| ACCEPTED → PREPARING without PAYMENT_RECORDED | This specific provisional P06 payment prerequisite is missing |
| ACCEPTED → REJECTED | Restaurant cannot contradict an already accepted commitment through generic rejection |
| PREPARING → CANCELLED | Beyond selected early-cancel cutoff; alternative resolution requires separate later policy |
| COMPLETED → CANCELLED | Terminality; later dispute/refund would be separate workflow |
| any state → duplicate PAYMENT_RECORDED | Local duplicate milestone, absent provider reconciliation; reject rather than silently duplicate |
| REJECTED without prior payment → REFUND_REQUESTED | No recorded local financial basis for request in this model |
| CANCELLED with existing refund request → duplicate REFUND_REQUESTED | Local repeat is rejected; this is not distributed idempotency |

## Explicit state and orthogonal history

The full conceptual state space is not only six enum labels. It is approximately:

```text
(primary fulfillment status, paymentRecorded?, refundRequested?, workflowOccurrences)
```

The guards admit a subset of these combinations. For example `(PREPARING,false,*)` is not reachable through the P06 command handler, and `(PLACED,*,true)` is rejected. We do not encode every combination in one giant enum.

No payment capture, real refund, financial settlement, restaurant authentication, state-version optimistic lock or distributed workflow is claimed.

## Concurrency and durability deliberately unresolved

Two individually legal actions against the same old state can pass guards separately. `OrderWorkflowService` still follows `findCurrentById → domain transition → saveCurrent`, and the in-memory repository unconditionally replaces equal-ID values. An immutable object does not turn a multi-step command into an atomic transaction.

No PostgreSQL, Kafka, Saga, Outbox, Event Sourcing, event delivery or across-restart recovery introduced.

## Requirements still needing product decisions

- Whether preparation *must* wait for a recorded payment step; which distinction between authorization and capture matters.
- Whether restaurant may reject after acceptance and under which exception/override process.
- Exact cancellation cutoff, partial preparation and compensation.
- What "COMPLETED" denotes (kitchen completion versus pickup/delivery).
- Whether a refund request without recorded payment has a legitimate exception (manual/other channel).
- What to do when provider state is unknown, duplicated or arrives after terminal fulfillment.

These are written constraints in the P06 learning model, **not asserted universal restaurant laws**.
