## Logical correctness rule

A successful local cancellation of a PLACED/ACCEPTED Order must produce **one immutable successor** with:
- fulfillment status CANCELLED;
- exactly one newly appended ORDER_CANCELLED occurrence;
- identical OrderId, lines/total, customer/restaurant and prior accepted occurrence prefix;
- P10 whole-history invariants satisfied;
- no mutable intermediate Order published or exposed before completion.

Neither updating the status alone nor recording the fact alone represents an accepted cancellation. A command denied by its guard publishes **neither**.

## Source order

```text
existing immutable Order
  → P07 admission guard and target-state decision
  → temporary new event list assembled privately
  → immutable new Order constructor + P10 history invariant
  → P07 successor postconditions
  → return complete successor
  → application OrderRepository.saveCurrent(successor)
  → return OrderSnapshot / HTTP response
```

The P11 package-private `Order.assembleTransition(..., AssemblyProbe)` is an **experiment-only fault seam** used from tests in the domain package. Public business methods pass a no-op probe. It is not a production failure injector, transaction manager, or business API.

## Failure injection matrix

| Fault location | Actual test | Expected observable state |
|---|---|---|
| After target state calculated but before occurrence staged | `throwAfterTargetDecisionCannotPublishCancelledWithoutOccurrence` | Prior Order still PLACED, zero new accepted facts |
| After fact staged in private mutable list, before new Order constructed | `throwAfterFactIsStagedCannotExposeOccurrenceWithoutStatus` | Prior Order still PLACED, history unchanged |
| After successor constructed but before return/publication | `throwAfterNewSuccessorConstructionStillCannotMutateOriginal` | Prior Order unchanged; no returned successor |
| Normal successful cancellation | `successfulCancellationReturnsStatusAndFactTogether` | New Order has CANCELLED+ORDER_CANCELLED, old Order remains PLACED |
| Intentionally unsafe mutable status/fact split (test fixture only) | `deliberatelyUnsafeMutableSplitMakesPartialStateObservable` | Status CANCELLED with no fact visible, showing failure mechanism |
| Business guard denies before assembly | `guardRejectsBeforeAnyAssemblyProbeRuns` | No callback, no accepted mutation |
| Repository throws **before** reference publication | `failureBeforeReferencePublicationLeavesOldOrderCompletelyVisible` | Current prior Order remains PLACED, no new fact |
| Repository throws **after** reference publication | `failureAfterReferencePublicationLeavesNewOrderVisibleDespiteCallerException` | Current is CANCELLED with fact, caller still saw technical exception |
| Order committed but independent audit update fails (test fixture only) | `twoIndependentObjectsAreNotAtomicallyUpdatedByOrderPublication` | New Order visible, second object unchanged |
| Stale A/B successors each pass guards and invariants | `twoIndividuallyLegalStaleSuccessorsCanOverwriteEachOther` | Last writer wins; earlier accepted occurrence lost |

## Atomicity tiers and non-guarantees

1. **Intra-Order assembly**: construction of a complete immutable successor, no partially mutated prior Order. **Tested.**
2. **Single map-entry reference publication**: `ConcurrentHashMap.put` publishes one complete immutable Order reference on the normal path. **Tested by controlled repository, not concurrent linearizability stress test.**
3. **Entire current-state decision**: `findCurrentById → guard → saveCurrent` is **not atomic**; stale writers may overwrite each other. The stale-snapshot interleaving is demonstrated by an executable test.
4. **Multi-object change**: no common transaction for Order plus another independent state store; demonstrated inconsistent test-only audit/object fixture.
5. **Durability**: no database/restart recovery; all data is in memory.
6. **Distributed effects**: no provider financial transaction, kitchen physical operation, cross-service state, Saga or atomic commit.
7. **Response certainty**: a technical failure after local publication means the caller's exception does **not** prove the mutation was absent.

## Explicit V8 distinctions

- **Atomic operation != fast operation**: the property concerns visibility of all-or-nothing effect, not latency.
- **Atomicity != distributed transaction**: one immutable domain object does not coordinate provider money or independently committed systems.
- **Transaction boundary != @Transactional**: annotation is one framework declaration; actual guarantee depends on a configured transaction manager, enlisted resource, proxy invocation and underlying resource semantics. P11 has none.
