# C1.2-P10 — Repository Semantics, Persistence Authority and Reconstitution

Roadmap V8.0 Cluster 1.2 / blueprint Part 1.2.10. Inherit verified checkpoints/C1.2-P09 at 000c2960fdbbe85106fc68c051193f5fafc37675.
**Engineering question:** What must create, save, retrieve and reconstruct mean for one Order aggregate's authoritative current state?

## Inherited real code
`OrderRepository`: `saveCurrent(Order)`, `findCurrentById(OrderId)`; in-memory `ConcurrentHashMap.put` silently replaces same ID and is also used by `PlaceOrderService` for creation. `Order` is immutable, private constructor; `OrderId` record UUID; local history and Order lines are stored within Order. P09 OrderPlaced constructed after save, with initial-placement guard. P13/P14/P17 prove stale overwrites; P18 proves state loss after real JVM replacement.

## Distinct repository obligations
A. New aggregate identity creation: require absence, never overwrite existing. `createNew(Order)` with typed OrderAlreadyExistsException; `ConcurrentHashMap.putIfAbsent` decides absence/insertion atomically in ONE process-owned map. This closes a real identity-creation weakness without claiming global cross-process uniqueness or HTTP idempotency.
B. Existing aggregate evolution: `saveCurrent(Order)` remains unconditional, including absent-key upsert. It is explicitly documented as a legacy unsafe replacement API, preserving P13/P14/P17 replay and stale conflicts for later P16–P18 version-aware evolution. This is NOT an update-only contract yet.
C. Lookup: `Optional.empty()` means key absent within current repository scope; cannot distinguish never-created, state lost at restart, deleted, wrong partition, future replica lag, or technical failures across other storage designs without additional evidence. Technical failures must not be converted to `ORDER_NOT_FOUND`.
D. Reconstitution (future): reconstruct identity, customer/restaurant references, immutable OrderLine list, status, placedAt, history, selected invariants; storage mapping must not bypass constructor constraints. `Order.place` is creation, not reconstitution; do not replay domain commands to fabricate old historical state. P12 implementation path and P14 ORM mapping later.
E. Authority lifetime: current repository is process-local. P18 demonstrates acknowledged state absent after real JVM SIGKILL + restart. `createNew` is not durable.

## Time and correctness model
T0 Order.place returns valid candidate; T1 createNew attempts absence check, T2 map publication; T3 OrderPlaced.from, Accepted result; T4 HTTP reply may be lost; T5 JVM may die. Current fact still not durable.
For updates: T0 read O0; T1 domain creates O1; T2 concurrently another change O2 may save; T3 saveCurrent(O1) blindly replaces; neither entity-ID equality nor immutable class prevents it.
Creation safety and replacement freshness are separate requirements. Atomic map single-key insertion does not imply atomic read-modify-write across find/save, nor multi-key/multi-table local transaction.

## Identity collision vs logical duplicate request
Two candidate Orders with identical OrderId => createNew rejects second even if values identical. This is key uniqueness, NOT idempotency.
Same client intent retried => PlaceOrderService generates two different UUIDs; both may be created because no stable logical command identity exists. Must not claim replay protection.

## Cross-domain authority
OrderRepository is NOT authority for Restaurant existence/capacity, Customer authentication, Payment provider settlement, inventory reservations or event publication. Reference identifiers are typed values, not proof of remote state. Database primary key != aggregate itself. Aggregate != row/table or service.

## PostgreSQL handoff contract P11–P14
P11: schema must represent complete Order with business UUID uniqueness; migrations and reproducible database tests. Define FK/NOT NULL/CHECK only where justified; don't force single aggregate into one table.
P12: real durable repository, create-only INSERT enforced by unique key; reconstitution and real P18 process A SIGKILL / B GET survives. Validate invalid persisted state appropriately, distinguish missing vs malformed/corrupt.
P13: relational constraints complement, not replace aggregate rules.
P14: JDBC/JPA mapping decisions must preserve Order identity/value semantics and invariant-enforced reconstitution.
P15: transactions support multi-table atomic state/history commit.
P16–P18: reproduce isolation anomalies; version-aware expected-state changes to reject stale updates and define retry/conflict behavior. Do not implement versions/locks in P10.

## Competing designs
1. Single saveCurrent for create/update (before-state): minimal but permits identity collision overwrite, unbounded upsert.
2. `if(findCurrentById(id).isEmpty()) saveCurrent(order)`: check-then-act race, violates concurrent unique creation.
3. `createNew` via ConcurrentHashMap.putIfAbsent + retained legacy saveCurrent (chosen): narrow hardening, honest remaining gaps.
4. `saveCurrent(order, expectedVersion)` now: eliminates important before-state experiment and skips database isolation lesson; defer until P16–P18.
5. Premature SQL/JPA, event sourcing or Kafka as 'repository': introduces unrelated mechanics ahead of P11–P14 and forces storage vocabulary into domain model.

## Quality attributes
Correctness: at most one creation per OrderId within current instance, with original authority retained on collision.
Concurrency: map-level atomicity on create; updates remain exposed to lost updates.
Durability: none across process replacement.
Latency: O(1) expected hash map operations, not measured with representative load; no invented p99 numbers.
Maintainability: explicit create/update intent reduces semantic ambiguity; cost is interface/API migration.
Reconstructability: current Order instance stored directly, so persistence mapping/recovery not yet proven.
Operability: typed conflict distinct from actor rejection, missing key and repository technical failure.
