# C1.2-P17 — Optimistic Concurrency, Versioning and Stale-Write Detection

Authoritative scope: Course 2 Enterprise Distributed Systems Master Roadmap V8.0 and derived Cluster 1.2 blueprint Part 1.2.17.
Inherited exact verified C1.2-P16: c48869ff7f9282229ce130ed8209fca0b78658bf. One continuous Food Ordering Platform, Spring Boot/Java21, immutable Order, PostgreSQL three-table aggregate, real MVCC P16 read-only coherent snapshot and atomic P15 write transaction.

## Engineering question
How can an immutable successor built from an earlier valid Order be published ONLY if the PostgreSQL authoritative Order has not advanced, even if both competitors make legal domain choices under their shared source snapshot? Version must cover status-preserving modifications, local milestone history and multirow state. It is NOT entity identity, wall clock time, authorization, Payment provider confirmation or operation idempotency.

## Before-state, causality and preserved evidence
C1.2-P16 PostgreSQL experiment: two independent application threads read PLACED Order, one produces ACCEPTED+RESTAURANT_ACCEPTED, other REJECTED+RESTAURANT_REJECTED. Both saveCurrent commands acknowledged success despite mutually exclusive source requirement; last replace wins. Root row writes serialize physically but no source-currentness comparison. P14 reconstructed Order correctly, P15 writes atomically, P16 reads one MVCC snapshot; these do not protect later decisions made from a completed read transaction.
A same-status example is even more important: two PLACED updates (recordPayment, modifyLines) can erase each other's history if repository compares only status. A numeric revision is needed for every aggregate evolution.

## New invariant and implementation
OrderId stays constant. Order.version starts at zero on placement, reconstitution accepts explicit stored version >=0; every immutable decision producing a successor increments by Math.addExact(version,1). A versioned successor is NOT automatically current. Prior reconstitute overload with default revision zero retained only for existing call compatibility; PostgreSQL mapper explicitly reads and supplies persisted revision.
PostgreSQL forward-only Flyway V3 adds orders.version BIGINT NOT NULL DEFAULT 0 with CHECK version>=0. Existing V1/V2 migrations are unchanged. Legacy pre-V3 rows begin at revision baseline zero without claiming historical operation counts.
createNew only publishes version-zero Order; create collision still 23505 -> OrderAlreadyExistsException. saveCurrent is no longer UPSERT: it issues a conditional UPDATE orders SET customer_id=?,restaurant_id=?,status=?,placed_at=?,version=? WHERE id=? AND version=? with expected=successor.version-1. Require row count EXACTLY 1. If zero, raise StaleOrderVersionException carrying OrderId and expected revision; do not delete or reinsert any owned child. Entire compare-and-set update and complete line/history replacement remain inside P15 one JDBC transaction. If later child SQL fails, rollback version+root+children together.
The in-process authority uses ConcurrentHashMap.compute to atomically compare current.version with successor.version-1 and reject missing or stale values. It is process-local and remains nondurable; don't conflate with PostgreSQL interprocess authority.
OrderWorkflowService and ModifyOrderService explicitly convert StaleOrderVersionException into OrderActionResult.Rejected(STALE_ORDER_VERSION); OrderController maps it to HTTP 409 CONFLICT. Illegal domain transitions remain separate; SQL technical failure and P15 OrderCommitOutcomeUnknownException are not disguised as normal business rejection.

## Mechanism: linearization point
The root conditional UPDATE is the local commit admission test. PostgreSQL row locking and MVCC coordinate competing version predicates; precisely one of two successors expecting version zero can update the same row and advance to version one. The losing update matches zero after conflict resolution; it never modifies child history/lines. The full transaction commit makes one complete successor authoritative.
A zero-row update may mean absent identity OR stale revision; the exception is an expected-revision rejection, not proof of current state or absence. A forged future successor cannot skip revision if its expected predecessor isn't stored. Direct SQL writers that bypass revision advancement can defeat the guarantee; upgrading all writers is an operational release requirement.

## Architectural mechanism comparisons
- Java separate SELECT version, compare, then unconditional UPDATE: TOCTOU race, reject.
- SQL WHERE status=:expected: insufficient for status-preserving history/line changes.
- Database compare-and-set version in same aggregate write transaction (chosen): no long-held application read lock; stale submissions rejected, contention still exists; no retries in P17.
- SELECT FOR UPDATE held throughout decision+write: can serialize commands but requires longer write transaction, P16 lock evidence 55P03; not required under chosen boundary.
- Entire SERIALIZABLE read-modify-write transaction: possible alternative but coupling service logic to tx, 40001 retry semantics; P18 owns retries.
- Timestamp/ETag without authoritative revision mechanism: clock and precision issues P14, or conditional ETag based on revision may be viable future HTTP policy; not chosen alone.
- Event sourcing/distributed locks/Kafka/Saga: no need for one PostgreSQL Order CAS.

## Real project limitations / future dependencies
No user-supplied version/If-Match in HTTP at P17; server loads current state at request time. A user editing an outdated UI payload does not necessarily get conflict unless command contract later includes source revision. No full idempotency for repeated local milestones or external payment provider charges; a command invoked again AFTER fresh read may append another milestone. P18 must evaluate retries, lost acknowledgements, reconciliation, and conflicts.
No version stored on independent Customer, Restaurant or Payment entities because they are not yet authoritative Order-owned state. The Order version cannot prove external financial truth. No Kafka or outbox here.
Operational rollout: all writers including old application nodes and manual scripts must increment the revision consistently. V3 baselines existing rows at zero rather than reconstructing historical counts; mixed old/new writers may violate guard. No zero-downtime rolling-deployment proof. No p99 throughput, hot-row lock contention or large-scale migration measurement.
P18 next: do not automatically retry stale successor. Reload, re-evaluate business rule and operation identity, distinguish stale conflict from Postgres 40001, 55P03, and P15 uncertain commit outcome; measure and classify safely.
