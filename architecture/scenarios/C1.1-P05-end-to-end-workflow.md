# C1.1-P05 — End-to-End Workflow Discovery

## Engineering question

What actually happens from order placement to a business outcome, including alternatives, handoffs, cancellation, refund pressure, preparation and completion?

## Workflow is broader than lifecycle state

A workflow describes the journey across participants and activities.

A state machine describes legal/illegal state transitions for an entity.

P05 discovers the journey first.

## Baseline start

The inherited application can already execute:

Customer
→ PlaceOrder intent
→ PlaceOrderCommand
→ accepted decision
→ current Order created
→ OrderPlaced local domain fact

P05 begins after that accepted placement.

## Selected happy-path scenario

One executable learning scenario is:

Customer
→ Order placed
→ Payment participant: PAYMENT_RECORDED
→ Restaurant operator: RESTAURANT_ACCEPTED
→ Restaurant operator: PREPARATION_STARTED
→ Restaurant operator: ORDER_COMPLETED

This is a selected scenario, not a claim that every production food-ordering business must charge before restaurant acceptance.

## Restaurant-rejection branch

Selected executable branch:

Customer
→ Order placed
→ Payment participant: PAYMENT_RECORDED
→ Restaurant operator: RESTAURANT_REJECTED
→ Platform: REFUND_REQUESTED

The branch exposes an important business consequence:

If money has already been recorded as paid before rejection, rejection may create refund/compensation pressure.

P05 does not implement a real refund provider or claim that a refund completed.

REFUND_REQUESTED != REFUND_COMPLETED.

## Cancellation-before-payment branch

Customer
→ Order placed
→ Customer: ORDER_CANCELLED

This scenario contains no recorded payment milestone and therefore no refund request in the trace.

P05 does not yet declare this cancellation universally legal or terminal. It is a workflow branch candidate.

## Cancellation-after-payment branch

Customer
→ Order placed
→ Payment participant: PAYMENT_RECORDED
→ Customer: ORDER_CANCELLED
→ Platform: REFUND_REQUESTED

This path exposes why ordering of business activities matters.

The same cancellation intent has different financial consequences depending on what happened earlier.

## Handoffs

The discovered workflow contains handoffs among:

- Customer
- Payment participant
- Restaurant operator
- Platform

A handoff is a transfer of business responsibility/knowledge.

It is not automatically a service-to-service network call.

All current P05 operations remain in one Spring Boot process.

## Unresolved policy questions

P05 deliberately leaves these unanswered:

- Must payment happen before restaurant acceptance?
- Is payment authorization different from capture?
- Can a restaurant reject after payment?
- Can a customer cancel after restaurant acceptance?
- Can cancellation occur after preparation starts?
- Who is authorized to request refund?
- Does refund request always follow cancellation after payment?
- What does "completed" mean exactly?
- Which states are terminal?
- Which operations are reversible versus compensating?

Those questions are inputs to later lifecycle/invariant work, not gaps to hide.

## Payment-sequencing alternatives

At least three plausible business strategies exist:

1. Charge/record payment before restaurant decision.
2. Authorize before restaurant decision but capture after acceptance.
3. Restaurant accepts first, then payment is attempted.

They create different latency, failure, refund and customer-experience trade-offs.

P05 does not select a final production strategy.

Its executable scenario intentionally chooses one path so consequences can be observed.

## Why completion is not yet declared terminal

ORDER_COMPLETED appears as a workflow milestone.

P05 does not yet prove:
- no later operation is possible;
- completion cannot be reversed;
- cancellation after completion is illegal.

Those are P06/P08 questions.

## Current evidence pressure

The permissive recorder can represent contradictory sequences.

Therefore the workflow has been discovered sufficiently to expose the need for explicit lifecycle legality.

That pressure enables Part 1.1.6.
