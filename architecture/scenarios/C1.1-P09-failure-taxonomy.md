# C1.1-P09 — Business Failure Versus Technical Failure

## Engineering question

When an operation does not produce the requested outcome, did the system correctly reject the request, or did the system itself fail to execute correctly?

## Failure taxonomy

### Business rejection

The system:
- received enough information to make the business decision;
- executed the relevant decision logic;
- reached a known negative outcome;
- preserved its correctness guarantees.

Examples:
- preparation requested while Order is PLACED;
- cancellation by wrong customer;
- second semantic refund request;
- terminal Order modification;
- requested Order does not exist in the application authority.

Business rejection is expected behavior.

### Technical failure

The system could not execute correctly because the mechanism/runtime/infrastructure failed.

Examples:
- OrderRepository throws while reading;
- OrderRepository throws while saving;
- unexpected NullPointerException/programming defect;
- future database/network dependency unavailable.

Technical failure is not a business decision.

## Key distinction

Business rejection:
system worked and answered NO.

Technical failure:
system could not reliably answer/complete the operation.

HTTP 4xx and 5xx may reflect this distinction, but HTTP status itself is not the domain definition.

## Application result contract

OrderActionResult:
- Accepted
- Rejected

Only known expected domain conditions become Rejected.

Technical exceptions are deliberately not caught by a broad RuntimeException catch.

## Example: repeated cancellation

Current Order = CANCELLED
Request = Cancel again

Domain mechanism:
IllegalOrderTransitionException

Application interpretation:
Rejected(
  code = ILLEGAL_TRANSITION
)

HTTP:
409 Conflict

The server is healthy. The request conflicts with business lifecycle.

## Example: repository unavailable

Request = Cancel Order
Repository read throws IllegalStateException("repository unavailable")

Application:
exception propagates

HTTP technical boundary:
500

No business conclusion such as "cancellation forbidden" is invented.

## Why this matters

If technical failure is mislabeled as business rejection:
- clients may stop retrying when recovery was possible;
- incidents can be hidden as user errors;
- availability metrics look artificially healthy;
- support receives false explanations;
- correctness becomes impossible to diagnose.

If business rejection is mislabeled as technical failure:
- normal domain behavior inflates error rates;
- clients may retry impossible operations;
- alerts fire on expected behavior;
- operators chase non-incidents.
