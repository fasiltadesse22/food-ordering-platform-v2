# C1.1-P04 — Identity and Authoritative State

## Engineering question

How do we know which business thing we are talking about, and which representation of its state should be trusted?

## Identity chain

A business Order persists conceptually across many implementation representations.

The same logical Order may appear as:
- one Order object in memory;
- another Order object reconstructed later with the same OrderId;
- an OrderSnapshot;
- an OrderResponse;
- an OrderPlaced fact referring to that Order;
- eventually a database row or serialized message.

Those representations are not the identity.

OrderId is the stable identifier used to refer to the business Order.

## Required distinctions

### Identity != Java object reference

Two different Order instances can carry equal OrderId values.

They are different Java objects but can represent the same logical business identity.

### Identifier != database primary key

OrderId currently uses UUID value semantics.

No database exists yet, so it is not accurate to call OrderId "the database primary key."

A future database may use it directly as a key, map it to another storage key, or store it under a unique constraint. That choice is not made in P04.

### Identifier representation != identity

The UUID string in an HTTP path is a textual representation of OrderId.

The string itself is not the domain identity type.

The HTTP adapter parses the string into OrderId before invoking application logic.

### Snapshot != authority

OrderSnapshot is a detached point-in-time copy.

It does not update automatically if repository current state changes.

### HTTP response != authority

OrderResponse is what an adapter exposed at one observation point.

It is not the owner of current Order state.

### Domain fact != current-state authority

OrderPlaced says that placement was accepted.

It does not answer every later question about the Order's current state.

### Observation != ownership

A component can observe a value without owning or authoritatively deciding it.

## Current authority model

Within the current process:

HTTP path string
  → OrderId
  → GetOrderUseCase
  → OrderRepository.findCurrentById(OrderId)
  → current Order
  → OrderSnapshot
  → OrderResponse

The repository-managed current Order is the current application authority.

The downstream snapshot/response are observations derived from it.

## Same identity, multiple representations

The P04 experiment intentionally creates two different Order objects with the same OrderId.

The repository stores one current mapping per equal OrderId.

When the second representation is saved under the same identity, it becomes the current repository representation.

This experiment does not claim that arbitrary business mutation is legal. It isolates identity and authority mechanics before lifecycle rules exist.

## Stale copy

A snapshot is captured from the first repository representation.

The repository is then given a later same-identity representation with different order-line quantity.

The old snapshot remains unchanged while the repository current state changes.

That demonstrates the meaning of stale observation:

same identity
+ different observation time
+ detached copy
= possible stale representation

## Unknown identity

A well-formed OrderId that has no repository entry is not an Order with empty state.

It is an unknown identity in the current authority.

GetOrderService therefore raises OrderNotFoundException.

## Important non-guarantees

P04 does not guarantee:
- durability across restart;
- globally unique OrderId across every possible system;
- optimistic locking;
- stale-write rejection;
- distributed source-of-truth coordination;
- database uniqueness;
- valid lifecycle updates.

Those are later concerns.
