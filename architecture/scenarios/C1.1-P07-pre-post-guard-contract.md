# C1.1-P07 — Preconditions, Postconditions and Guards: executable contract

**Scope:** V8.0 Part 1.1.7 and independently authored blueprint. **Lineage:** `redo/v8-c1.1-p07` from frozen new checkpoint `redo/checkpoints/C1.1-P06` commit `0300b8f26f069c5bfb9fc7e2582efc60b6d27b5e`. Do not import older P07 implementation.

## Shared contract

For an existing authoritative Order representation `before`, a requested `OrderWorkflowAction` and timestamp `at`:

```text
P(before, action)        // explicit source/related-milestone precondition
    IF false → InvalidOrderTransitionException
    IF true  → compute expected successor state; append one occurrence
Q(before, after)          // executable postcondition, before returning
    must preserve OrderId, customerId, restaurantId, placedAt,
         lines and total
    must set status exactly to the accepted expected state
    must retain every earlier accepted occurrence in order
    must append exactly one (action, participant, timestamp) occurrence
    failure → OrderTransitionContractViolationException (developer breach)
Repository.saveCurrent(after) happens only after domain success.
```

**Important:** This tests a *local sequential domain/application contract*, **not** database transaction atomicity, provider effects, or serializability. `OrderTransitionContractViolationException` is **not** a routine business rejection.

## Precondition matrix and postconditions

| Trigger | Preconditions (P) | Status postcondition (Q) | Workflow postcondition (Q) |
|---|---|---|---|
| PAYMENT_RECORDED | PLACED or ACCEPTED; no earlier local payment recorded | unchanged | exactly one PAYMENT_RECORDED |
| RESTAURANT_ACCEPTED | PLACED | ACCEPTED | exactly one RESTAURANT_ACCEPTED |
| RESTAURANT_REJECTED | PLACED | REJECTED | exactly one RESTAURANT_REJECTED |
| ORDER_CANCELLED | PLACED or ACCEPTED (no PREPARING) | CANCELLED | exactly one ORDER_CANCELLED |
| PREPARATION_STARTED | ACCEPTED and local PAYMENT_RECORDED already present | PREPARING | exactly one PREPARATION_STARTED |
| ORDER_COMPLETED | PREPARING | COMPLETED | exactly one ORDER_COMPLETED |
| REFUND_REQUESTED | REJECTED or CANCELLED; prior local payment; no prior refund request | unchanged (terminal fulfillment) | exactly one REFUND_REQUESTED |

All accepted successors preserve all preexisting occurrence entries and stable business identity, restaurant/customer association, line items, total and placed timestamp. A denied trigger has **no accepted successor** and the existing application path performs **zero save calls**.

## CancelOrder: specific V8 contract

```text
command: recordCancellation(OrderId)
pre:       a current Order exists
           AND fulfillment state ∈ {PLACED, ACCEPTED}
           AND accepted operation is associated with a modeled CUSTOMER label
success:   new Order status = CANCELLED
           OrderId, owner, restaurant, lines and prior history preserved
           exactly one ORDER_CANCELLED occurrence appended
           current Order selected by OrderRepository.saveCurrent
rejection: a forbidden source state yields typed business denial
           no new occurrence; no normal repository save
```

**“Preparation has not continued” is not fully provable in P07.** The implementation enforces no further *local PREPARATION_STARTED* transition after cancellation on the **sequential current Order**, but does not stop a physical kitchen, authenticate a restaurant employee, prevent a concurrently saved stale acceptance/preparation, or coordinate a remote device. Those are separate necessary future guarantees. Thus a strong postcondition about physical preparation would be an unsupported claim.

## Ordered mechanism

```text
HTTP adapter? (none for workflow milestones yet)
    → OrderWorkflowUseCase
    → OrderWorkflowService: findCurrentById
    → Order.transition
       1. requirePreconditions(before, action)  [business check]
           ├─ denied → InvalidOrderTransitionException
           └─ expected successor OrderStatus
       2. construct one immutable next Order and occurrence
       3. requirePostconditions(before, next, action, participant, time, expected)
           ├─ breach → OrderTransitionContractViolationException
           └─ next Order returned
    → saveCurrent(next)
    → OrderSnapshot
```

**Validation != guard:** parsing a UUID, rejecting null timestamp, or validating a DTO field cannot establish the Order is cancellable. **Business rejection != technical exception:** a disallowed lifecycle command is expected denial; a failed postcondition is a programming correctness breach; a repository outage is infrastructure failure.

## Controlled mutation experiment

Isolated non-baseline branch:
[`redo/experiments/c1.1-p07-bypass-payment-guard`](https://github.com/fasiltadesse22/food-ordering-platform-v2/tree/redo/experiments/c1.1-p07-bypass-payment-guard).

One specific guard was removed: `PREPARATION_STARTED` no longer checks for prior `PAYMENT_RECORDED`, while retaining the required source `ACCEPTED`. The mutation predicts `ACCEPTED → PREPARING` **without local payment evidence**, contrary to the guarded policy. The existing tests should fail; record the *actual* CI result and failed assertion before describing the experiment as observed.

This experiment branch is deliberately broken and must **never** become P08's baseline. P07's main branch retains the guard and its tests.

## Preserved fragility

A guard evaluates a supplied Order representation. It does not prove another thread hasn't saved a newer one; `findCurrentById → guard → saveCurrent` still has an uncontrolled stale-read window. No optimistic locking, relational transaction, distributed coordination, Saga, provider calls, authenticated workflow routes or durable state is introduced here.
