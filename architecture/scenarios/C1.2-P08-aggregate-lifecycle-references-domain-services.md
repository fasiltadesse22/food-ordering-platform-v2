# C1.2-P08 — Aggregate Lifecycle, Identity References and Domain Services

Authoritative roadmap: Course 2 V8.0, Cluster 1.2, Part 1.2.8. 
Inherited verified repository: checkpoints/C1.2-P07 at `670ce14c7f985015dc65c3caafc60113a97d7c90`.
Engineering question: Which behaviors belong inside one aggregate, which require independent domain decision support, and which related entities should be referenced rather than owned?
Type A/C: source-grounded architectural analysis and deterministic contract tests; no premature service/model mechanisms.

## Actual source inventory
- One domain aggregate candidate: Order(final, private constructor, immutable successors). Owned state: OrderId, references to CustomerId and RestaurantId, lines, status, placedAt, workflowOccurrences.
- Existing public Order behavior: place, modifyLines, recordPayment, accept/reject/cancel, start/complete preparation, recordRefundRequest. The root implements selected local operation guards and status/history invariants.
- PlaceOrderService checks the command's supplied ActorContext and constructs Order, saves it, then returns OrderPlaced (local fact) and OrderSnapshot.
- OrderWorkflowService loads current Order via OrderRepository, calls domain operation, saves successor, projects result. ModifyOrderService maps replacement line inputs; GetOrderService projects current state.
- OrderRepository is only in-process Order authority. No CustomerRepository, RestaurantRepository, PaymentRepository, full Customer/Restaurant/Payment entities, provider gateway integration, distributed authority or persistent transaction exists.
- WorkflowParticipant labels are business trace metadata, NOT authentication roles, microservices or autonomous actors.

## Aggregate-owned lifecycle versus process lifecycle
Order state machine: PLACED -> ACCEPTED -> PREPARING -> COMPLETED; PLACED -> REJECTED/CANCELLED. Status terminality forbids further **status transitions currently modeled**, not later local milestone facts: payment milestone/refund request can append under selected rules.
The business process may span independently governed Customer, Restaurant, Payment, Inventory, Delivery state. An ID reference does not transfer ownership or make a remote effect atomic.
Two Orders with the same CustomerId/RestaurantId are distinct Order aggregates and evolve independently.

## Responsibility classification
| Requirement | Current owner | Proposed decision |
|---|---|---|
| Order ACCEPT from PLACED and correct assigned RestaurantId | Order root | Keep inside root |
| Order CANCEL with assigned CustomerId | Order root | Keep inside root |
| Modify lines only when PLACED | Order root | Keep inside root |
| Refund-request eligibility from local status/history | Order root | Keep as local policy |
| PlaceOrder actor context type/matching and create/save/result orchestration | PlaceOrderService | Keep application-level; ActorContext is NOT authentication |
| Repository find/save current and technical failure handling | OrderRepository adapter and application | Not domain service |
| Restaurant availability/capacity shared across Orders | Not implemented | Derive Restaurant/Capacity authority and cross-domain policy when requirement exists |
| Customer active account / credit | Not implemented | Independent authority; do not embed full Customer |
| External payment authorization, charge, refund | Not implemented | Independent Payment/provider authority; local PAYMENT_RECORDED not proof |
| Complete business-process compensation | Not implemented | Defer Saga/Outbox/coordination until real cross-authority pressure |
| Timeline and fact publication | Local OrderPlaced record in result | P09 will explore fact/domain/integration-event distinction |

## Domain service vs application service
Aggregate method decides rules about state it owns and should protect, e.g. Order.recordRestaurantAcceptance.
Domain service/policy is suitable for domain behavior spanning state not naturally owned by one entity; a pure RestaurantAcceptancePolicy receiving trustworthy operating facts is **hypothetical**, not a production interface in P08.
Application service coordinates loading the Order, obtaining outside facts, evaluating policies, calling aggregate methods and saving/returning results.
A domain service is NOT a transaction coordinator by its class name. It cannot eliminate time-of-check/time-of-use races or independently owned commits.
Infrastructure adapter provides external technical access; OrderRepository is not Restaurant, Customer or Payment authority.

## Trade-offs and scenarios
1. Embed full Restaurant in Order: risks stale snapshots, contention and false ownership, unjustified by current immediate invariants.
2. Use RestaurantId + Order root local guards (current): simple for current policy; does not validate restaurant existence/availability.
3. Add pure domain acceptance policy with externally supplied facts in future: helps express business rule, but not commit-time correctness across independent authorities.
4. Move all rules to application services: may scatter invariants and weaken root.
5. Split into separate services or introduce distributed Saga now: complexity before a real cross-aggregate business rule or authority exists.

## Failure-window pressure
Two Orders for one last capacity slot both read availability=1 -> both policies approve -> both Orders accepted. Policy purity does not enforce shared capacity invariant.
Provider charge succeeds but local payment milestone fails -> external financial truth differs from Order state (P16).
Two Order commands evolve stale same-ID snapshots -> P13/P14/P17; no version field.
Process A loss -> Order unavailable after JVM restart P18.
No current availability, capacity, payment or restaurant data service is implemented; these scenarios are architectural hypotheses or inherited controlled experiments, not newly measured production results.

## P08 test plan
Eight tests in OrderAggregateLifecycleReferenceBoundaryTest:
1. two Orders sharing CustomerId/RestaurantId keep independent state;
2. normal lifecycle preserves reference IDs without embedding full related entities;
3. OrderWorkflowService load->root decision->save->snapshot;
4. nonmatching RestaurantId rejected without authority change;
5. PlaceOrderService rejects mismatched supplied ActorContext before publication;
6. PlaceOrderService creates one Order and returns a local OrderPlaced fact;
7. local recordPayment creates only a local occurrence, not verified provider outcome;
8. terminal cancelled Order can append local REFUND_REQUESTED without new identity or lifecycle-state change.
These tests DO NOT prove other aggregate existence or cross-authority correctness.
