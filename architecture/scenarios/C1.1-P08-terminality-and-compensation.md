# C1.1-P08 — Terminality, reversibility and financial follow-up semantics

**Authoritative scope:** V8.0 Part 1.1.8 and derived Cluster 1.1 blueprint. **New lineage:** `redo/v8-c1.1-p08` from verified new P07 `1df034bce36020e3e921e2aec3ae7e8eddf4819b`. Historical older P08 source and earlier manuscript not used.

## Business model: two dimensions, not one mutable status

| Current Order state | Fulfillment closure | May normal fulfillment reopen? | Local refund-request readiness |
|---|---|---|---|
| PLACED | ACTIVE | Not a terminal state; regular legal edges remain | NOT_A_CLOSED_REFUND_PATH |
| ACCEPTED | ACTIVE | Regular legal transitions remain | NOT_A_CLOSED_REFUND_PATH |
| PREPARING | ACTIVE | Completion is still possible | NOT_A_CLOSED_REFUND_PATH |
| COMPLETED | FULFILLMENT_COMPLETED (terminal) | **No**; cancellation/reacceptance denied | NOT_A_CLOSED_REFUND_PATH |
| REJECTED, no payment occurrence | RESTAURANT_REJECTED (terminal) | **No** | NO_LOCAL_PAYMENT_EVIDENCE |
| CANCELLED, no payment occurrence | CUSTOMER_CANCELLED (terminal) | **No** | NO_LOCAL_PAYMENT_EVIDENCE |
| REJECTED, payment occurrence, no refund request | RESTAURANT_REJECTED (terminal) | **No** | MAY_RECORD_REQUEST |
| CANCELLED, payment occurrence, no refund request | CUSTOMER_CANCELLED (terminal) | **No** | MAY_RECORD_REQUEST |
| REJECTED or CANCELLED, payment and refund request occurrences | Terminal fulfillment | **No** | REQUEST_ALREADY_RECORDED |

**CRITICAL SCOPE:** `PAYMENT_RECORDED` is only an accepted local Order workflow occurrence, not provider capture, authorization, settlement or actual irreversible transfer. `REFUND_REQUESTED` is only a local request milestone, not money returned, promise to refund or completed compensation. `OrderClosure` is a read-only policy interpretation, not a financial processor.

## Reversal versus compensation

- **Semantic reversal / undo:** an operation genuinely returns the modeled pre-commit mutable intent to a former meaningful condition, such as editing an unsubmitted cart line. It need not rewrite an authoritative completed historical effect because none occurred.
- **Compensation:** a separate, new business action attempts to counter a previous accepted effect. The earlier effect remains historical truth. A captured payment followed by a successful actual refund would be two distinct facts—not one erased payment. This example is **conceptual only**, not implemented in P08.
- **Refund-request recording:** our available P08 mechanism merely records one request after selected cancellation/rejection-with-local-payment scenarios. It does not coordinate a Saga or guarantee that any payment exists externally.
- **Fulfillment closure:** terminality applies to primary Order fulfillment. A terminal REJECTED/CANCELLED Order may still accept the separate local refund-request milestone, without reopening preparation, acceptance or completion.

## Four required V8 experiments

1. **Refund before payment:** rejected/cancelled Order without local payment milestone denies `recordRefundRequest` and preserves accepted history.
2. **Refund twice:** a paid closed Order can append one `REFUND_REQUESTED`; the second call is denied; there remains exactly one request fact.
3. **Cancel completed Order:** `recordCancellation` on COMPLETED throws `InvalidOrderTransitionException`; COMPLETED remains terminal.
4. **Modify terminal Order:** no arbitrary edit/update or reopen command exists. Attempting to mutate immutable `lines()` or `workflowOccurrences()` throws `UnsupportedOperationException` and leaves the Order unchanged. This is a **structural immutability test, not a domain-level edit-command guard test**; do not claim the latter.

## Sequence examples

```text
Local payment recorded (not provider capture)
    → restaurant rejects
    → record refund request (new occurrence)
    → fulfillment stays REJECTED
    → payment-recorded history remains present
    → duplicate refund request denied
```

```text
Placed → restaurant accepts → preparation begins → COMPLETED
    → cancel attempt denied
    → no "restore ACCEPTED" or "set UNPAID" operation
```

## Persistent fragility and unresolved obligations

- No distributed compensation coordinator, Saga, real payment/refund execution, provider ledger, amount/recipient eligibility, reversal validation or financial reconciliation.
- No durable history; process restart still loses this in-memory Order and its occurrence list.
- Concurrent read–check–save may overwrite accepted outcomes based on stale versions.
- No new public authenticated refund/cancellation action HTTP endpoints or physical kitchen work-stop acknowledgement.
- There is no genuine edit-cart/modify-Order business command in this project stage; P08 does not invent one just to prove terminality.
- Success/failure classification and compensation outcome across external systems belong to later V8 phases.

## Architectural decision
Terminality does not mean "the world can never do anything related to an Order again." It means the specific *fulfillment lifecycle* is closed. If a financial effect already occurred, historical truth should be preserved and a **new compensating fact** introduced under the relevant authority, rather than rewriting status as if the earlier event never happened.

See the separately documented ADR and test/evidence ledger.
