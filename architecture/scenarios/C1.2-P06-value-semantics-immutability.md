# C1.2-P06 — Value Objects, Value Semantics and Immutability

V8.0 Cluster 1.2 Part 1.2.6. Inherits frozen checkpoints/C1.2-P05 (2cc2277436b0729aed4e1712e7aa3cf9bad6521c). 
Central question: Which concepts are defined by values rather than independent identity, and which validity, equality, ownership and immutability guarantees should their implementations provide?

## Actual source
OrderLine is record(menuItemId, name, quantity, BigDecimal unitPrice), with nonblank item ID/name, positive quantity, nonnegative price, and derived unitPrice.multiply(BigDecimal.valueOf(quantity)).
OrderId is UUID record with nonnull guard; CustomerId/RestaurantId are distinct String-record identifiers.
Order stores immutable List.copyOf(lines) and workflowOccurrences in a final class; modifyLines creates a new Order and records ORDER_MODIFIED.
OrderSnapshot is an application-layer projection record with nested Line and WorkflowOccurrence DTO records and List.copyOf collections; it is not business authority.
OrderWorkflowOccurrence is a record containing action, participant, occurredAt; it represents a local fact, not a durable event-store entry.
There is no Money/currency abstraction, persistent table/precision constraint, payment price commitment, tax/discount policy or JPA mapper.

## Distinctions
Entity continuity depends on OrderId; value equality for an OrderLine record depends on all of its components, including BigDecimal.equals scale. Value object does not equal Java record or DTO. Typed ID is a value object that *refers to* entity identity; it is not the identified entity itself.
The menuItemId inside OrderLine refers to catalog identity; it does not automatically endow the OrderLine with independent business lifecycle/identity. Line ordering, repeated menu items, size/customization and merge policies are not established.
A monetary amount without currency is not generally a complete Money concept; unitPrice currently permits nonnegative arbitrary BigDecimal scales and values. Do not silently invent ISO currency, 2-decimal precision or positive-only amount invariants.
BigDecimal: new BigDecimal("5.0").compareTo(new BigDecimal("5.00"))==0 but equals is false because scale differs. Java record equality inherits this distinction; lineTotal likewise retains scale. Numeric equivalence is not structural equality.
List.copyOf creates unmodifiable snapshot of elements, not recursive deep immutability. Current elements are immutable records holding immutable BigDecimal/String values, so practical deep stability holds for the present model. Future mutable nested values would require review.
Immutability aids local invariant preservation but cannot prevent stale/colliding authoritative successors P13/P14/P17 or JVM loss P18.

## Domain invariants and policy gaps
Validated: line positive quantity, nonnegative price, nonblank item id/name, nonnull price. Order place and modify require nonempty lines. Total is derived, not separately stored. No currency/unit precision, taxes, discounts, monetary overflow/rounding rules, duplicate-item merging, catalog freshness, accepted-price immutability after payment or gateway-charge agreement is established.
The scale difference is demonstrated before changing production equality behavior. A normalization decision would need explicit business and storage contracts.

## Competing designs
A Current validated record (chosen): minimal, stable, transparent; equality scale-sensitive.
B Normalize monetary scale in compact constructor: makes numeric-looking prices equal at chosen scale, but risks unintended rounding/validation/business behavior; premature.
C Introduce Money(currency,amount) with currency-safe arithmetic: stronger when required; no current multi-currency/payment-price semantics justify it here.
D Turn OrderLine into entity with LineId: only justified if independent line lifecycle, quantity adjustments keyed to line identity, or persistence/reconciliation semantics require it; currently not established.
E Use HTTP DTO directly as domain value: inappropriate boundary because transport representation/policy may evolve separately.

## Experiment matrix
E1 equal component OrderLines are equal despite distinct allocations.
E2 5.0 versus 5.00: numerically equal but not BigDecimal.equals; record equals false, totals compare numerically equal.
E3 invalid component construction rejected (blank IDs/names, nonpositive quantity, negative/null unit price).
E4 defensive list copy blocks caller alias mutation and exposes unmodifiable list.
E5 modifyLines preserves original immutable Order, returns same-identity new state + occurrence, defensively copies replacement list.
E6 OrderSnapshot DTO is detached from later domain changes and has unmodifiable list.
All 6 tests run in real root Maven CI. No production code change.
