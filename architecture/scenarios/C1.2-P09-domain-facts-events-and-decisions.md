# C1.2-P09 — Domain Facts, Domain Events and Aggregate Decisions

V8.0 Cluster 1.2 Part 1.2.9. Inherited verified checkpoint: checkpoints/C1.2-P08 at 5f78c68fc04b76f34fbc431010a677c0ba83bc9d.
Engineering question: When does an aggregate decision become an accepted business fact, and when does a fact become an integration concern?

## Source-grounded semantic model
- Actor intent != PlaceOrderCommand != domain/application decision != proposed Order state != OrderRepository current publication != PlaceOrderResult.Accepted != OrderPlaced historical fact != integration message.
- Actual placement code: verify supplied ActorContext, create Order.place with new UUID, repository.saveCurrent, then construct OrderPlaced.from(order), then return PlaceOrderResult.Accepted(OrderSnapshot,OrderPlaced).
- OrderPlaced is a domain fact in application result, not Kafka message, durable event-store record or outbox entry.
- OrderWorkflowOccurrence(action, participant, occurredAt) is copied into immutable Order successor and stored as part of one current in-memory Order representation. It is a local workflow trace, NOT guaranteed durable append-only event stream.
- OrderEvolution(nextStatus, occurrence) binds transition target and occurrence but is NOT committed operation or event publication.
- PAYMENT_RECORDED is a local occurrence, NOT external charge evidence (P16).
- No producer, consumer, broker, event store, Outbox, CDC, PostgreSQL or transaction manager exists.

## Demonstrated semantic gap
Before P09, OrderPlaced.from(any Order) accepted later snapshots and recomputed total while preserving placedAt, making an old placement fact appear to contain changed current lines' total.
After P09, OrderPlaced.from requires status PLACED and empty workflowOccurrences: a source-level precondition for the *initial placement representation*.
This rule is intentionally narrower than a globally authenticated historical fact: OrderPlaced has a public record constructor; it can be constructed independently. The factory cannot establish repository publication by itself. Application sequencing (save then from) determines accepted-result semantics only for its normal in-process path.
This is not full event identity, event ordering or immutable durable history.

## Different fact types and temporal meaning
OrderPlaced.from(initial) copies OrderId, CustomerId, RestaurantId, placement time and initial total.
OrderWorkflowOccurrence records a local action/participant/timestamp within an Order successor.
OrderSnapshot is current projected state, not a historical event.
Current state can change while previously constructed immutable fact remains unchanged; reconstructing placement event from current Order is not generally safe.
OrderStatus alone is not historical event evidence. An enum action in history does not imply legal causal ordering, uniqueness, participant authenticity or provider financial truth.

## Failure window and authority matrix
| Window | Authority | Fact / caller interpretation |
|---|---|---|
| Actor command rejected before construction | No new Order | No accepted OrderPlaced |
| Domain construction fails | No new Order saved | No accepted OrderPlaced |
| Valid Order constructed before save | Local candidate | Fact could be instantiated by type but not authoritative |
| Repository fails before publication | Old/no current state | No accepted result returned |
| In-memory put succeeds | One current Order in process | Application constructs fact afterward |
| Adapter publishes then throws | New current state may exist | Caller gets error; returned accepted fact absent; outcome unknown to caller |
| Accepted result constructed then response lost | State may exist | Client not informed; retry can create a second Order |
| Process dies after accepted save | Current in-memory state lost P18 | Previously returned fact not durably recoverable |
| Concurrent stale successor overwrites state | P13/P14/P17 | Local facts/history may be erased despite prior successful response |
| Provider charge succeeds, local fact missing | P16 | External money state and Order history differ |
| Broker publishing introduced later | Independent failure authority | Requires new contract; no such behavior in P09 |

## Domain event vs integration event vs event store
Domain event: fact expressing business occurrence within a model; conceptually may be produced by aggregate decision.
Integration event: separately designed, versioned, identifiable, serialized message for cross-boundary consumers, with contract on producer publication and receiver behavior.
Event-store record: authoritative durable append-only history and replay rules; NOT current occurrence list.
Transactional outbox: future mechanism to bridge durable domain commit and reliable publication when justified; no such mechanism now.
A domain fact constructed or returned in process is not automatically an integration event or proof of event-driven architecture.

## Production design alternatives
A. Existing in-process fact returned after current save + placement-state validation (chosen for P09): minimal, honest, no producer.
B. Create fact at domain candidate creation: represents proposed occurrence but cannot claim accepted publication without later authority handling.
C. Introduce event-collection on aggregate: useful only with an explicit lifecycle, draining and atomic persistence contract; otherwise risks duplicates and lost events.
D. Emit Kafka message before saving Order: orphan event after local save failure.
E. Save Order and then publish message without atomic bridging: may lose event if process crashes; dual-write problem.
F. Event-source aggregate immediately: requires authoritative event IDs, snapshots, ordering, replay, deduplication and durable store; unwarranted at P09.

## Future acceptance conditions
P10 repository contract must make creation/update and authority implications precise.
P11–P15 PostgreSQL transaction and durability proof required before any claim of committed historical fact.
P16–P18 concurrency and unknown-outcome semantics must distinguish acknowledged state from event delivery.
Later communication/EDA clusters must decide whether consumers, independent delivery and replay justify a broker, outbox, event schema or CDC.
