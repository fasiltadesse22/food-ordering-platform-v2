## Source-grounded state inventory
The actual `Order` holds: `OrderId id`, `CustomerId customerId`,
`RestaurantId restaurantId`, `List<OrderLine> lines`, `OrderStatus status`,
`Instant placedAt`, and `List<OrderWorkflowOccurrence> workflowOccurrences`.
`total()` is derived from current lines, not independently authoritative storage.
`OrderInvariants.verify(status, workflowOccurrences)` runs on normal construction.
`OrderWorkflowService.update` reads via `findCurrentById`, evolves an immutable
Order, then unconditionally calls `saveCurrent` on the in-memory adapter.
These are source-inspected implementation observations, not general guarantees.

## Explicit distinction: current implementation vs proposed boundary
Observed structure: one immutable Order contains the selected status, lines, ownership identifiers and workflow occurrences.
Evidence-backed candidate: *one Order-centered immediate consistency decision boundary* for local lifecycle/status/history/selected guards/line modification.
This does not prove that all fields need independent database rows, that all occurrences are exhaustively validated, or that one giant transaction is optimal.
The current application has one deployable; no future service or database boundary follows from this candidate.
References to Customer and Restaurant identities do not make their entire external business state owned children of Order.

## Mechanics of current execution and precise failure windows

### Normal completion
PREPARING current -> domain verifies PREPARING precondition and restaurantId guard
-> constructs successor with status COMPLETED and occurrence ORDER_COMPLETED
-> constructor checks selected status/history invariants
-> repository replaces one Order reference.
Claim: one locally valid immutable successor is constructed and published on the normal path.
Not guaranteed: durable commit, isolation across competing readers/writers, complete historical validity beyond checked rules.

### Intentionally fragile status-first split model
status := COMPLETED -> injected failure -> missing ORDER_COMPLETED.
The already-executed P11 test detects this invalid partial representation.
History-first is symmetric: ORDER_COMPLETED exists while status remains PREPARING.
The test-only split is a controlled model, **not** the production storage architecture.

### Concurrent conflicting lifecycle decisions
Both actors read PLACED. One creates ACCEPTED+RESTAURANT_ACCEPTED; another REJECTED+RESTAURANT_REJECTED.
Both local successors pass domain checks; `saveCurrent` has no expected-version condition.
P13 verified both Accepted responses with only the last complete successor surviving.
This is a history/acknowledgement problem, not just a corrupted Order object.

### Sequential stale snapshot
Read PLACED; another operation commits cancellation; stale snapshot independently records payment; stale save replaces current Order, erasing cancellation.
P17 verified resurrection without simultaneous threads. Immutability does not establish temporal freshness.

### Process failure
P18 verified CANCELLED / HTTP 200 in process A -> SIGKILL -> same ID HTTP 404 in new process B.
The absence of durable recovery is independent of status/history atomic publication.

## Boundary alternatives evaluated
A. One local Order decision boundary (preliminary preference): strong alignment with status/history invariants; simple single-deployable control; potential contention/large histories later.
B. Separate status and history authorities with independent commits: permits a partial-state window; requires extra coordination; not justified for current immediate invariant.
C. Enlarge Order boundary to own full Restaurant menu, Customer account and payment-provider transaction: increases coupling, contention, and false ownership; no evidence requiring synchronous consistency with those authorities.
D. Store/compute derived total separately: unnecessary duplicated authority today; if persistence requires a snapshot, specify immutable pricing policy and synchronization requirements before deciding.
Decision for P01: retain A as **candidate**, pending precise aggregate modeling in P04/P07 and transactional implementation in later parts.

- payment authorization/capture/refund completion rules;
- payment after cancellation / modification after payment;
- broad event-history completeness/ordering guarantees;
- external payment idempotency/atomicity;
- bounded-context or service boundaries.
