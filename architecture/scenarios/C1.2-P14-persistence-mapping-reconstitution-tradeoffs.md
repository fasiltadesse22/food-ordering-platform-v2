# C1.2-P14 — Persistence Mapping, Aggregate Reconstitution and Representation Trade-offs

**Scope contract:** V8.0 Cluster 1.2 + derived blueprint Part 1.2.14. **Inherited verified:** checkpoints/C1.2-P13 at 9fd1fe7c3c9a0608c29af5c8397e8bfc3ae9588e.

## Engineering question
How can mapping rows to Order preserve business identity, selected invariants, ordered collections, BigDecimal/Instant semantics and historical meaning, while selecting a storage/load strategy whose query costs and read-consistency limitations are explicit?

## Actual inspection
PostgresOrderRepository P13: read root SELECT, lines SELECT ORDER BY line_position, history SELECT ORDER BY occurrence_position, create OrderLine / OrderWorkflowOccurrence values then Order.reconstitute. Three SELECTs for present Order, all on same JDBC connection but autocommit default true and no explicit single read transaction/snapshot. READ COMMITTED across statements may tear with a concurrent writer, P16 scope.
Writes: P12 JDBC transaction, root UPSERT and DELETE+INSERT child lists, no optimistic version (P17 failure preserved).
V1 three tables; V2 CHECKs nonnegative positions and known enums/prices; neither V1 nor V2 enforces contiguous list indexes, a cross-row representation contract.
Order is immutable, references value IDs, Java record OrderLine(BigDecimal) and workflow occurrence(Instant). No Order.equals override; domain identity is OrderId.

## P14 justified Type B project change
Introduce package-private PostgresOrderMapper, moving domain construction and JDBC row decoding out of repository. Validation:
- line_position and occurrence_position must be contiguous 0..n-1 when reconstructing each ordered Java List. A nonnegative gap such as 0,1,4 passes PostgreSQL V2 but now raises InvalidPersistedOrderException instead of silently collapsing positions.
- Load and reconstruct real domain values; invalid values/enums and selected Order invariants still raise InvalidPersistedOrderException, not Optional.empty.
- No business command replay, timestamp fabrication or implicit OrderId replacement.
- No transaction isolation change or database schema migration. Mapping improvement is narrower than P16 snapshot/isolation work.
Selected persistence mapping remains one root + two child collections. Stored total not duplicated.

## Competing representation alternatives
(A) three relational tables, three SELECTs (chosen): explicit child ownership, FK/CHECK, ordered children, roughly 1+L+H logical retrieved rows, three SQL statements, read tear possible under current isolation, complexity grows with full snapshot writes.
(B) one JSONB document/root row: one-row atomic storage simplicity, schema evolution/child constraints/query/index costs, potential changed query workload. Not selected and not introduced.
(C) single SQL JOIN of root + two collections: one SQL round trip, but LxH result multiplicity; mapper dedup complexity, missing-children issues with INNER JOIN. Experimental cardinality: L=3,H=3 -> 9 result rows, unlike 1+3+3 separate logical row count; no actual comparative p99 benchmark.
(D) ORM JPA/Hibernate mapping: identity map, dirty checking, cascade/flush, loading semantics, fetch strategy, potential N+1 or multi-bag Cartesian joins; valuable in other contexts, not justified to replace verified JDBC P12.
(E) targeted partial updates: fewer writes, but must preserve complete aggregate decision semantics and atomicity, careful stale versions; defer until measured.
(F) read-model projections: limited fields for display, not valid full domain Order for mutation; do not introduce distributed CQRS prematurely.

## Value semantics
Java BigDecimal.compareTo numeric equality and equals scale-sensitive equality differ. OrderLine is a record, inherits component equality. Test uses 5.5000, PostgreSQL NUMERIC recovered numeric equal with observed scale 4 in CI; do not infer every possible scale/magnitude preserves exactly or introduce currency/rounding policy.
Java Instant ns precision vs PostgreSQL TIMESTAMPTZ microsecond. Test 2026-10-12T10:30:20.123456789Z -> 2026-10-12T10:30:20.123457Z, difference 211ns. Neither a network clock-order contract nor exact nanosecond persistence is guaranteed. Keep order via positions, do not derive causality from timestamps; no invented global timestamp normalization in P14.

## Invariant and authority boundaries
Domain selected OrderInvariants checks seven status/history implications, not full historical ordering or participant authentication.
P13 database CHECK values, not cross-row completeness. Mapper rejects absent child list or position gaps but not necessarily every historical causal corruption.
Root ID absent => Optional.empty; malformed existing rows => InvalidPersistedOrderException; SQL failure => OrderPersistenceException.
One JVM recovery P12 survives app SIGKILL on shared DB; P18 memory remains loss negative.
Other authorities: Restaurant/Customer IDs only references; local PAYMENT_RECORDED is not external payment charge. No fictional Payment/Restaurant tables.

## Workload/quality attributes
For existing Order, three SQL SELECTs, one root and L/H rows; key indexes provided by root and composite child PKs. JOIN result can multiply LxH. Claim only logical row cardinality, NOT measured latency/throughput or cost dominance.
Full delete+reinsert child replacement per save causes O(L+H) logical writes; possible contention/write amplification with growing history, but no measured limits. No pool is configured; DriverManager opens connections per operation.
Maintains read authority fidelity in nonconcurrent tests but separate SELECTs may observe different commits in concurrent request, P16 must reproduce and select isolation/consistent snapshot mechanism.
