# C1.1-P09 — Business result, technical fault and HTTP translation matrix

**Authority:** V8.0 Part 1.1.9 + derived Cluster 1.1 blueprint. **New lineage:** `redo/v8-c1.1-p09` from frozen [P08 checkpoint](https://github.com/fasiltadesse22/food-ordering-platform-v2/tree/redo/checkpoints/C1.1-P08) at `9723a45bc14ed6aa9f99795687e5ec772217fb5d`. Historical P09 code was not used.

| Situation | Domain/application meaning | HTTP | Class | Service-health interpretation |
|---|---|---:|---|---|
| Restaurant rejects PLACED Order | **Accepted** RESTAURANT_REJECTED command; status now REJECTED | 200 | SUCCESSFUL_BUSINESS_DECISION | No technical failure |
| Attempt ORDER_COMPLETED from REJECTED | Domain precondition denied; no accepted successor/save | 409 | BUSINESS_REJECTION / ILLEGAL_LIFECYCLE_TRANSITION | Correct refusal, not infrastructure outage |
| Attempt second ORDER_CANCELLED | Terminality forbids duplicate cancellation command | 409 | BUSINESS_REJECTION / ILLEGAL_LIFECYCLE_TRANSITION | Correct refusal; investigate if unexpected volume |
| Unsupported workflow action | Invalid path action name, not a recognized domain operation | 400 | INVALID_INPUT | Transport/client input issue |
| Invalid OrderId syntax | Invalid representation | 400 | INVALID_INPUT | Transport input issue |
| Valid OrderId with no current Order | Lookup missing | 404 | NOT_FOUND / ORDER_NOT_FOUND | Missing local resource, not business lifecycle refusal |
| Repository unexpected failure | Cannot complete accepted local save | 500 | TECHNICAL_FAILURE | Server execution failure, not business rejection |
| Domain postcondition breach | Internal accepted successor contradicts contract | 500 | TECHNICAL_FAILURE | Programming integrity defect, not policy denial |
| Actual process crash/timeout | Could produce no HTTP response | none/timeout | TECHNICAL_FAILURE or UNKNOWN_OUTCOME | Not exhaustively observable from status codes alone |
| Existing PlaceOrder actor refusal | Typed earlier `PlaceOrderResult.Rejected` | 422 | Earlier placement-specific semantic rejection | Preserve previous API contract |

**HTTP demonstration route:** `POST /orders/{orderId}/actions/{action}`. This is a **learning-only endpoint without real authentication or authorization**; actor labels do not verify who invoked the request. Not suitable to deploy as public customer/restaurant operations.

## Source path

```text
HTTP adapter: parse UUID/action, reject invalid input
→ OrderWorkflowDecisionUseCase.execute
→ OrderWorkflowService (one Spring service implementing both old and typed ports)
→ find current Order / not-found
→ established Order P06/P07 guard and successor postconditions
   ├─ accepted → saveCurrent → OrderSnapshot → Accepted → 200
   └─ InvalidOrderTransitionException → Rejected(code,action,message) → 409
→ other exceptions propagate; global advice maps missing→404, malformed→400,
   unexpected/contract breach→sanitized 500
```

Only the narrow `InvalidOrderTransitionException` catch is converted to typed business denial. Do **not** catch every RuntimeException and claim it is a policy refusal. Other previously established workflow methods continue to expose the earlier exception-based Java API; typed `execute` is a new boundary, not a whole-repository migration.

## Failure semantics and quality-attribute scope

- `409` may mean a *correct* business refusal. A rise in 409s may nonetheless signal stale clients, product friction or abuse; separate business conflicts from server errors rather than ignoring them.
- `RESTAURANT_REJECTED` resulting in HTTP 200 is a successful application command with negative business outcome; business rejection-rate metric must be tracked separately.
- `5xx`, process crashes, timeouts, and connection failures may indicate genuine technical problems; an availability SLI needs an explicit eligible denominator and must not miss unanswered calls.
- Client-side invalid input `400`, missing resource `404` and preexisting placement `422` have distinct semantics.
- A future remote write may commit before acknowledgment is lost: HTTP 500 cannot always establish rollback. No such remote durable store exists in P09.
- No retry, circuit breaker, automatic fallback, HTTP auth, provider payment, distributed coordination, PostgreSQL, Kafka, production metrics/tracing or crash recovery added.
- Current Order read–guard–save concurrency weakness remains unresolved.
