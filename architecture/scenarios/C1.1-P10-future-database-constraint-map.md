# C1.1-P10 — Future Database Constraint Map

This document authorizes candidate constraints for later PostgreSQL work. It does not claim they exist today.

## Candidate row/table constraints

| Future persistence field | Candidate constraint | Rule supported | What it still does not prove |
|---|---|---|---|
| orders.id | PRIMARY KEY / NOT NULL | each row has unique persisted identity | that identity maps correctly to every external/business participant |
| orders.customer_id | NOT NULL | persisted Order has a customer reference | that acting caller owns the Order |
| orders.restaurant_id | NOT NULL | persisted Order has restaurant reference | that the restaurant is valid/open/authorized |
| orders.status | NOT NULL | persisted Order has lifecycle state | that the transition history producing the state was legal |
| order_lines.order_id | NOT NULL + FK later if justified | line belongs to an Order row | aggregate consistency/atomicity across all operations |
| order_lines.quantity | CHECK (quantity > 0) | structural positive quantity | lifecycle/business eligibility |
| order_lines.unit_price | CHECK (unit_price >= 0) | structural nonnegative price | correctness of price relative to menu/catalog authority |

## Rules that simple row constraints do not naturally express

The following current rules are not equivalent to a simple NOT NULL/CHECK:

CANCELLED cannot enter PREPARING.

Only the owning restaurant may accept an Order.

Refund requires a prior recorded payment and a rejected/cancelled lifecycle.

A completed Order cannot be modified.

The current actor must match the Order owner.

Those rules depend on:
- operation context;
- previous state/history;
- relationships across facts;
- temporal ordering.

A trigger or stored procedure could encode some of them, but "the database can technically encode it" does not automatically make the database the best semantic owner.

## Cluster 1.2 handoff

When PostgreSQL is introduced, compare:

domain enforcement
vs
database enforcement
vs
transaction boundaries

using actual integration tests.

Do not infer database guarantees before those tests exist.
