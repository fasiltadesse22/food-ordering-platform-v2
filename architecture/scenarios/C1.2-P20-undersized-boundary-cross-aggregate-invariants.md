# C1.2-P20 — Undersized Aggregates and Cross-Aggregate Invariants

Authority: Enterprise Distributed Systems Architecture & System Design Master Roadmap V8.0, derived Cluster 1.2 Part 1.2.20 blueprint. Inherit exactly VERIFIED/FROZEN C1.2-P19 3c1d8b56fd2cb1b1f30b2fb95ae2e0a5c2b7e8ae. Preserve one Food Ordering Platform repository and all P15-P19 real PostgreSQL mechanisms.

## Engineering question
What business invariant is violated if Order status, required explaining workflow occurrences, or commercial state are given independent commit authority solely to reduce P19 write amplification and aggregate-wide version contention? When do independent Restaurant/Payment/Inventory truths justify an actual separate aggregate rather than forced inclusion into Order?

## Actual inherited source contract (read, not hypothetical)
OrderInvariants.verify enforces selected status/history implications: ACCEPTED must have RESTAURANT_ACCEPTED; PREPARING requires RESTAURANT_ACCEPTED+PREPARATION_STARTED; COMPLETED requires acceptance/preparation/completion; REJECTED history forces REJECTED, CANCELLED history forces CANCELLED; RESTAURANT_ACCEPTED facts may occur only in ACCEPTED/PREPARING/COMPLETED. Selected checks are NOT exhaustive business history validation.
Order.java remains immutable root, owns OrderLine values, workflow facts, lifecycle state, version. PostgresOrderRepository.saveCurrent issues CAS UPDATE orders WHERE version=expected, DELETE all child histories/lines, reinsert successor children, COMMIT in SAME JDBC transaction (P15/P17). findCurrentById reads 3 tables on one P16 REPEATABLE READ snapshot and domain reconstitution rejects invariant violations as InvalidPersistedOrderException. V1/V2/V3 DB constraints are row-local/representation constraints, not all cross-table business checks. P19 observed large full-child replacement; a physical optimization is not proof of logical boundary change.

## Invariant graph and ownership decision
Graph vertices: Order status S; required workflow history H; commercial lines L; version V; independent RestaurantId ref R and CustomerId ref C; local payment occurrence M; external Payment provider state P_ext; optional hypothetical Inventory remaining I and Order reservation references O_ref.
Hard selected graph edges: ACCEPTED -> required acceptance H, PREPARING -> acceptance+preparation H, COMPLETED -> acceptance+prep+completion H, allowed line modifications -> state PLACED and acting CustomerId; local refund request -> cancelled/rejected status AND local payment fact AND no previous refund-request fact, subject to P18 failure policy; all state-changing successors require Order expected revision V, root+owned child transaction.
CustomerId and RestaurantId on Order are references. Entire Restaurant or Payment authority does NOT move into Order. A local PAYMENT_RECORDED milestone is NOT remote provider capture. Real inventory stock/capacity business authority and reservation policy have not yet been adopted in production.

## Controlled artificial splits
Split A: two independent transactions: status root updated and committed ACCEPTED version1; acceptance fact missing. Both root enum/version and empty history structurally legal rows, but reconstituted Order violates ACCEPTED=>history. Crash/timeout during gap exposes persisted invalid state; P16 snapshot coherence cannot turn an actually committed partial business state valid.
Split B: history first committed acceptance fact while status remains PLACED/version0. Every history row passes row constraints, root status legal, but acceptance fact with PLACED violates selected domain invariant.
Split C: first status commit succeeds, second history INSERT fails via real test-only PostgreSQL trigger SQLState P0001. Rolling back second transaction CANNOT roll back first; verified InvalidPersistedOrderException persists. Compensation can fail or produce additional invalid windows; not equivalent to one ACID transaction.
Control D: update root and insert acceptance history under one JDBC transaction; external REPEATABLE READ reader before COMMIT sees old valid PLACED version0; after COMMIT sees coherent ACCEPTED version1 with one acceptance fact. P15 production repo also provides this mechanism; test uses test-only direct SQL to isolate atomic publication vs split transactions.
Hypothetical Inventory demonstration E: separate positive-quantity reservations with FK to test-only inventory capacity1 each locally valid can both commit, SUM(reserved)=2>capacity1. No guarded stock admission; local validity != global correctness. Test-only tables p20_inventory and p20_reservations do not establish production Inventory aggregate, services or external authorities.
Control F: under actual PostgreSQL concurrency, two clients BOTH SELECT remaining1, then conditional UPDATE inventory SET remaining=remaining-1 WHERE remaining>=1 followed by reservation INSERT in one transaction. Exactly one admission succeeds, other conditional update affects zero rows. Conservation holds. This is an illustrative local atomic invariant, NOT production inventory or universal across independent remote systems.

## Classification: invariants versus process expectations
Strong local invariant: Order status and explaining history cannot have a committed inconsistent combination; preserve atomic local authority, even with append-only physical mapping.
Cross-aggregate invariant: hypothetical capacity/allocated total must be enforced by designated shared authoritative inventory reservation admission or equivalent coordinated process, if zero oversell is demanded by business.
Temporal business workflow: local Order PAYMENT_RECORDED and external Payment provider result can diverge; no physical single database transaction across independent provider. Do not assert 'Order paid iff provider settled' as implemented hard invariant. Define saga/reconciliation/authorized weaker consistency only when later business requirements justify them (P21 and later distributed-data clusters).
Identity/authority: CustomerId and RestaurantId are references, not proof Order owns Customer/Restaurant or that a restaurant reference makes remote inventory authoritative here.

## Failure and visibility windows
W1 first local commit succeeds, before second begins => committed invalid Order.
W2 second SQL fails after first committed => partial permanently persisted until deliberate correction.
W3 process SIGKILL between transactions => first commit durable; missing other remains after restart. P20 tests emulate durable gap/second failure, do NOT claim actual SIGKILL P20 test. Inherited P12/P18 SIGKILL checks remain.
W4 isolation: P16 REPEATABLE READ coherent SNAPSHOT of invalid committed partial state still invalid. Snapshot consistency != business completeness.
W5 independent reservations concurrency can violate SUM <= stock if no shared admission/currentness mechanism.
W6 shared conditional inventory admission protects capacity in one database; can still require separate Order creation/confirmation coordination. No P20 claim that inventory reservation+Order creation are end-to-end atomic if independently committed.
W7 attempts to 'fix' split using retries after uncertain commit can duplicate workflow events or reserve stock twice unless operation identity and reconciliation designed; P18 policy still applies.

## Alternatives and architectural decision
A Retain current one Order aggregate, one transaction (chosen correctness baseline), accepts P19 write amplification until measured persistence optimization.
B Append-only history INSERT within the SAME root CAS transaction: physically smaller write, but preserve strict ordering, prefix semantics, DB/currentness and rollback. A likely simpler optimization than logical split.
C Two logical aggregates but one shared JDBC transaction: can retain local atomic visibility in same DB, yet conceptual ownership and coordination coupling mean don't pretend independent consistency; evaluate why separate model helps.
D Independent OrderStatus and OrderHistory transactions: rejected for this current hard invariant because partial committed states observed.
E Asynchronous message to repair history later: changes hard consistency to eventual; unacceptable without explicit business requirement, operational SLA, error visibility, idempotency and repair mechanism; not chosen.
F Distributed lock only: doesn't make two independent durable commits atomic; crash gap persists.
G Make Restaurant/Payment/Inventory subentities of Order: conflicts with independently authoritative business domains; not chosen.
H Shared Inventory atomic conditional decrement with same-local-transaction reservation row: valid narrow model in test; still doesn't solve remote/Order confirmation across authorities.

## Quality attributes and evidence
Correctness: detected invalid persisted combinations through actual domain mapper. Durability: partial first commit remains durable even after later failure, unlike single transaction. Availability: independent writes may seem simpler/faster but create repair debt and reject loads. Latency/contention: split may reduce shared root CAS but coordination/reconciliation adds costs; no throughput SLA measured. Reliability/recoverability: classify uncertain second-stage outcome vs known abort, avoid blind retry. Observability: inconsistent_reconstitution, missing_required_history, partial_commit_window, capacity_overcommit, reconciliation_backlog, expectedVersion, commandId and providerRefs if later added. Security/payment: no independent provider effect performed or claimed. Simplicity: keep invariants in one local Order root, optimize mapping only after measurement.

## Staff design review question
'P19 shows 289 child writes for one appended milestone. Why not independently commit status and history?' Answer: the SQL write-amplification is a physical implementation cost; independent commits break acceptance/history invariant and allow permanent partially committed Order under failure. A single-transaction append-only history candidate targets physical cost without surrendering correctness. Show actual P20 negative and positive PostgreSQL controls, causal failure windows and next P21 tradeoffs.
