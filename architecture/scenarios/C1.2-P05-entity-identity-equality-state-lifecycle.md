# C1.2-P05 — Entity Identity, Equality, State and Lifecycle

Roadmap V8.0; derived Cluster 1.2 blueprint. Inherited frozen checkpoint: checkpoints/C1.2-P04, 0c3efa497887930618e6ab9dc3b7503b09c5ceb8.
Engineering question: What distinguishes a continuing business entity from a collection of currently equal attributes?
Evolution Type A/C: rigorous entity/equality contract + deterministic tests; no production identity or persistence mechanism introduced.

## Source-grounded mechanics
- Order is final and immutable; its private constructor preserves OrderId and selected invariants, and public lifecycle methods construct new representations.
- Order does not override equals/hashCode: Java object equality is reference-based.
- OrderId is a record wrapping UUID; its value equality and hashCode derive from record components. CustomerId and RestaurantId are distinct nonblank String record types.
- OrderRepository lookup uses OrderId rather than Order.equals; in-memory repository tracks one current representation per equal OrderId in one JVM instance.
- P02 tests identity continuity, P03 candidate != authoritative publication, C1.1-P17 stale same-ID replacements, P18 restart loss.

## Distinctions and propositions
Let O_t=(I,S_t): same business identity I permits distinct states S_t and distinct Java allocations. Equal state does not imply same business identity. Equal business identity does not imply legal lineage, current authority, successful durable commit or caller authentication.
Reference equality != ID equality != state equality != repository authority != business-event lineage.
Terminal lifecycle (COMPLETED, CANCELLED, REJECTED in current modeled transitions) restricts operations, not the continued meaning of the identity.
Creation of new Order != legal evolution of existing Order != reconstruction from persisted authority.

## Actual Java equality trade-offs
Current Object.equals means HashSet<Order> keeps two immutable successors as distinct objects, while HashSet<OrderId> merges their same-ID identity.
Identity-based equals could be coherent as a domain design but cannot decide which successor is current; may also conflict with algorithms intending to retain snapshots as distinct values.
All-field equality would treat the same Order at two states as unequal by definition and potentially conflate separate same-state orders if IDs omitted. Do not change Order.equals prematurely.
ID record value equality is appropriate as a repository key; do not equate business identity with row PK or HTTP authorization.

## Persistence/evolution questions deferred
No DB exists: cannot demonstrate primary-key, ORM persistence context equality, proxy behavior, JPA @Id or @Version, reconstitution, collision rejection or cross-process recovery. P11/P12/P14 must verify those.
UUID random is probabilistically collision-resistant, not mathematical proof of uniqueness; repository unconditional put does not distinguish initial create from legitimate successor update or malformed same-ID replacement.

## Entity/non-entity contrast
Order: business entity with continuing lifecycle and stable identity.
OrderLine: currently Java record with value semantics and catalog-item reference; detailed value-object critique deferred P06.
OrderId, CustomerId and RestaurantId: typed identifier values, not complete Customer/Restaurant aggregates.
OrderWorkflowOccurrence: local fact representation; event identity and append guarantees deferred P09.
Customer/Restaurant/Payment: Order only references Customer/Restaurant identifiers and records local payment facts; cannot claim other complete entities are implemented here.

## Verification/failure matrix
1. Same business ID, separate Java objects, different state: not same Java reference; Order.equals false; IDs equal.
2. Same attribute values, different Order IDs: two Orders in repository.
3. HashSet<Order> contains both successor snapshots, while HashSet<OrderId> contains one identity.
4. Typed id values: OrderId record value equality; CustomerId and RestaurantId are different types.
5. PLACED -> ACCEPTED -> PREPARING -> COMPLETED: distinct snapshots, identity continuous.
6. Current authority stale/restart limitations remain; P17/P18 negative evidence preserved.

## Design defense
Prefer retaining existing Order reference equality pending P05 derived-contract outcome and later ORM needs; explicitly compare ID-only, reference-only and all-field equality.
Business identity is not a global state-version field, a command idempotency key, an HTTP request ID or an external provider reference.
Reconsider equality when collection semantics, persistence mapping or identity lifecycle require a concrete change; change only with tests of hashCode and contracts.

## Handoff
P06 value-object immutability and monetary equality, P07 root encapsulation, P11/12 persisted identity, P14 ORM, P16/17 temporal authority. Do not introduce them here.
