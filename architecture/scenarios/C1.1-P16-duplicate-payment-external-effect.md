# C1.1-P16 — Duplicate Payment and External-Effect Thinking

## Engineering question

What changes when a repeated command can cause an effect in another independently committed authority, where replacing local Order state cannot erase or merge that external effect?

## Local fact versus external fact

Current local fact:
PAYMENT_RECORDED

Potential external fact:
payment authority committed a charge.

These facts may correlate.

They are not the same fact.

## Current local duplicate behavior

recordPayment is a milestone operation.

It has no:
- state transition;
- duplicate-payment guard;
- provider transaction identity;
- command identity.

Therefore repeated recordPayment can create:

PAYMENT_RECORDED
PAYMENT_RECORDED

inside one current Order history.

## External-effect model

P16 uses a test-only PaymentAuthority.

A successful charge increments the modeled external authority's committed charge count.

Replacing an Order cannot undo that count.

This models the essential independence of an external provider without claiming a production payment integration exists.

## Charge-then-record happy path

payment authority charge succeeds
→ local PAYMENT_RECORDED appended.

Two unrecognized duplicate executions:

charge #1
→ PAYMENT_RECORDED #1

charge #2
→ PAYMENT_RECORDED #2

Both local and external effects duplicate.

## Unknown outcome window

T0 charge request sent
T1 external authority commits charge #1
T2 response is lost
T3 application has no PAYMENT_RECORDED
T4 caller/application sees exception/timeout
T5 retry sends charge again
T6 external authority commits charge #2
T7 application records one PAYMENT_RECORDED

Final observations:

External authority:
2 successful charges.

Order authority:
1 PAYMENT_RECORDED.

The local Order cannot explain the external financial truth.

## Reverse ordering window

If local record occurs first:

T0 PAYMENT_RECORDED appended
T1 call external authority
T2 provider fails before effect

Final observations:

Order authority:
PAYMENT_RECORDED present.

External authority:
0 charges.

This is the opposite inconsistency.

## Core conclusion

There is no safe ordering of two independently committed operations that magically makes them atomic.

Changing:

external → local

to:

local → external

moves the failure window.

It does not remove it.

## Participant knowledge

After an ambiguous external failure:

Payment authority may know:
charge committed.

Application may know only:
no successful response received.

Order repository may know:
payment not recorded.

Caller may know:
request failed/timed out.

Those are different knowledge states.

## External-effect irreversibility

Overwriting an Order can remove a local PAYMENT_RECORDED occurrence from current state.

It cannot uncharge a card.

A separate compensating action such as refund may be required.

That is why external effects must be reasoned about independently of local state convergence.
