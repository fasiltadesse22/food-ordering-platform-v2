# C1.2-P03 — Atomicity Requirements and the Shape of a Consistency Boundary

Base: `checkpoints/C1.2-P02` (e6919e51a5deb5b105397b44205153f1375eab73). V8.0; Cluster 1.2, Part 1.2.3.
Engineering question: When must multiple changes become authoritative together, and why does a coherent domain decision not automatically produce an atomic committed update?
Evolution Type A/C: contract clarification and in-process controlled failure cases only; no persistence mechanism introduced.

## Contract derivation
The normal COMPLETE operation maps PREPARING to COMPLETED while appending ORDER_COMPLETED.
At decision time, `OrderEvolution(nextStatus, occurrence)` binds the two aspects.
`Order.apply` creates a new immutable Order and its constructor runs selected `OrderInvariants` checks.
Requirement: the business decision must not commit a state where the status and mandatory fact disagree.
This is a logical consistency requirement independent of object, table, aggregate, or service boundary.

## Representation, publication, and durable commit are distinct
- Domain construction: `Order.recordCompletion` returns a valid candidate, does not save.
- In-process publication: `saveCurrent` can replace one map entry; this is not durable.
- Read/decide/save window: unconditional map put does not protect competing decisions.
- Durable commit: no DB exists; behavior is not implemented/tested.
- Caller acknowledgement: occurs after `saveCurrent` returns; exception after publication or lost response leaves uncertain caller knowledge.
- External provider effects: not inside any current local atomic commit.

## Formal decision and publication model
Let `S=(status,history,...)`, and `Valid(S)` mean the **selected current invariant checks** pass.
Domain evolution computes candidate `S'=T(S,c)`. This does not make S' authoritative.
A logical completion requires `S'.status=COMPLETED` and a matching completion occurrence.
The future physical update of any storage representation of these facts must guarantee all-or-nothing with respect to the specified reader/commit visibility.
For concurrent updates, atomic publication of one candidate alone is insufficient to guarantee a legal serial business history (P13/P14). For process restart, in-process atomic publication does not imply durability (P18).

## Which operation state must move together?
| Operation | Decision prerequisites | Coupled authoritative result | Excluded distinct authority |
|---|---|---|---|
| Place | valid actor/input/lines | new Order identity + initial state | Customer/Restaurant account truth |
| Accept/reject/cancel | status+assigned identity+acting identity | next lifecycle status + explaining occurrence | Restaurant/Customer full profile |
| Start/complete preparation | legal source state and acting restaurant | next state + required occurrence | external fulfillment telemetry |
| Modify lines | PLACED+matching CustomerId+valid replacements | replacement lines + ORDER_MODIFIED occurrence | live menu price authority |
| Record payment milestone | existing Order | appended local milestone | actual provider charge |
| Request refund | terminal eligible state, local payment recorded, no prior refund request | appended local refund-request fact | provider refund execution |
Future per-operation contracts must also require authoritative freshness when that prerequisite can be invalidated.

## Anti-conflations
Logical aggregate boundary != one Java class != one SQL table != one transaction.
Atomicity != invariant completeness.
Atomicity != isolation or serial business history.
Atomicity != durability.
Atomicity != result replay/idempotency.
Atomicity != external charge/refund atomicity.
A change becoming atomically visible at a single in-memory map entry does not constitute a crash-safe multi-row database commit.
A database transaction does not magically decide cancellation-vs-acceptance policy.

## Alternatives
A. Current one immutable successor+in-process map replacement: simple, locally coherent, not durable/concurrent safe.
B. Separate uncoordinated status/history commits: violates immediate invariant after partial failure; P11 negative control.
C. Hypothetical one local DB transaction for required related writes: may protect future atomicity, but must be built/tested P15 after P11/P12. Does not own external payment.
D. Make history a derived asynchronous projection: changes immediate business contract; not justified by current evidence.
E. Networked coordination / Saga / Outbox: premature, external authorities not currently under this local contract.

## Future acceptance criteria

P16/P17 must show actual conflicting/stale schedule outcomes and select a separate correctness mechanism.
