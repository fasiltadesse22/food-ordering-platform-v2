# C1.2-P11 — Relational Persistence Design and Schema Evolution
V8.0 roadmap + derived Cluster 1.2 blueprint, exact P11 scope.
Inherited verified: checkpoints/C1.2-P10 716a48ebf4b1591c2dbcc6aa014f1ca335b9769b.
Engineering question: How should one Order aggregate be represented in real PostgreSQL without treating physical tables as independent aggregates or introducing future mechanisms early?

## Actual implementation
- Production migration in `applications/food-ordering-app/src/main/resources/db/migration/V1__create_order_aggregate_schema.sql`, versioned by Flyway.
- `orders(id UUID PK, customer_id TEXT, restaurant_id TEXT, status TEXT, placed_at TIMESTAMPTZ)`.
- `order_lines(order_id UUID FK orders, line_position INTEGER, menu_item_id TEXT, item_name TEXT, quantity INTEGER, unit_price NUMERIC, PK(order_id,line_position))`.
- `order_workflow_occurrences(order_id UUID FK orders, occurrence_position INTEGER, action TEXT, participant TEXT, occurred_at TIMESTAMPTZ, PK(order_id,occurrence_position))`.
- Explicit position columns preserve observed Java List order: relational row retrieval has no implicit ordering.
- No independently mutable stored total: Order.total() remains derived. No Money/currency policy, fixed NUMERIC scale or OrderLineId invented. Database TIMESTAMPTZ has microsecond precision; Java Instant may have nanosecond data requiring deliberate handling during P12/P14.
- Foreign keys express Order child ownership in relational terms; CustomerId and RestaurantId are references to independently governed business concepts, NOT FK-backed in this schema.
- No Order version, database event stream, outbox, Payment table, service split, or automatic runtime PostgreSQL repository yet.

## Core distinctions and failure boundaries
aggregate != table; entity != row; OrderLine != separate aggregate; transaction != deployment boundary; root Maven verification != durability of running application.
Proposed multi-row save for COMPLETED+occurrence must later be one real transaction (P15). P11 has no app adapter writing these rows.
Schema constraints enforce identity and parent/child relationships, not full Order lifecycle eligibility, OrderLine positivity, history chronology, provider payment truth or successful replay.

## Migration evolution
Flyway stores applied migration version/checksum in flyway_schema_history. V1 is immutable after deployment; a future change should be a new versioned migration, not an edit to already applied V1. Separate additive/expand and removal/contract changes for rolling deployments when actually required.
A second migration invocation executes zero migrations; altering previously applied migration should provoke validation conflict (not a separate experiment in P11).
DB artifact and test harness are production-project code. Runtime app intentionally remains in-memory so P18 negative control is preserved through P11.

## Handoff
P12: introduce real runtime PostgreSQL connection/dataSource, Flyway execution, JDBC adapter implementation of OrderRepository.createNew/findCurrentById/saveCurrent, controlled Order.reconstitution without public invariant bypass, SQL error semantics and P18 process A SIGKILL -> process B same committed Order survives via a shared real database.
P13: selected relational domain/check constraints and invalid data hardening.
P14: mapping alternatives and faithful reconstitution of current aggregate.
P15: atomic multi-table commit/rollback; P16 isolation; P17 version-based stale conflict; P18 retries/unknown outcomes.
No premature Kafka, Redis, Saga, Outbox or DB-per-service architecture.
