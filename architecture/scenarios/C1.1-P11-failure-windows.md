# C1.1-P11 — Failure Windows

## Window A — Before domain evolution

PREPARING authoritative Order
→ request arrives
→ failure before a new Order is built

Authority remains PREPARING.

## Window B — During construction of a new immutable Order

If invariant verification fails, construction fails before the new representation is published.

Authority still points to the old Order.

## Window C — After valid local evolution but before repository replacement

A valid COMPLETED Order exists only as a local object.

If repository save fails before replacement:
- local decision/evolution existed;
- authoritative Order remains PREPARING.

Therefore local object creation is not commit.

## Window D — After repository replacement

Current in-memory authority points to the new complete Order.

If response generation/transport then fails, caller knowledge may differ from actual authority.

P11 documents this window but does not solve repeated-command/idempotency behavior.

## Deliberately fragile split-write window

If status and workflow history were independent stores:

write 1
→ FAILURE
→ write 2 never happens

Partial state becomes observable and invariant-invalid.

This is the core controlled P11 failure experiment.

## Process crash qualification

Because persistence is still in memory, a process crash loses both old/new authority on restart.

P11 does not claim crash durability.

P18 will study that failure directly.
