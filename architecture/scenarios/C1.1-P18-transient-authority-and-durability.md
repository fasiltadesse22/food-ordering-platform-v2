# C1.1-P18 — Process Crash, Transient State and Durability Non-Guarantees

## Engineering question

What happens to our correctness claims when the process that currently owns Order state disappears?

## Four concepts that must remain separate

### Authority

Which representation currently answers the application's Order query?

Today:
InMemoryOrderRepository inside the running JVM.

### Persistence

Has state been written outside the transient object graph to a storage medium/system intended to outlive that process?

Today:
No.

### Durability

After the system reports success under a stated failure model, is the committed state guaranteed to survive the failures included in that model?

Today:
No restart/crash durability guarantee exists.

### Recovery

After failure, how is authoritative business state reconstructed or restored?

Today:
a fresh process starts with an empty in-memory repository.

## Runtime path before crash

HTTP POST /orders
→ PlaceOrderService
→ InMemoryOrderRepository.saveCurrent
→ ConcurrentHashMap contains Order

HTTP POST /orders/{id}/cancel
→ OrderWorkflowService
→ immutable CANCELLED successor
→ saveCurrent
→ map contains CANCELLED Order

HTTP GET
→ same process/map
→ returns CANCELLED

This proves current visibility inside process A.

It does not prove persistence.

## Crash boundary

SIGKILL terminates the JVM.

The map exists only in process memory.

No shutdown hook copies Orders to durable storage.

No persistent storage adapter exists.

The authority disappears with the process.

## Restart boundary

Process B starts from the same executable artifact.

A new InMemoryOrderRepository is constructed with a new empty ConcurrentHashMap.

The same OrderId is not reconstructed from any durable source.

Expected result:
HTTP 404.

## Correctness consequence

Before crash, a customer can receive a successful Order creation/cancellation response.

After restart, the platform can be running and healthy at the process level while being unable to recover the acknowledged Order.

Therefore:
service/process availability after restart != preservation of business state.

## Business operation lifetime versus process lifetime

An Order may need to exist for hours/days.

A JVM may restart at any moment.

Business state whose required lifetime exceeds process lifetime cannot rely only on process memory.

## Recovery point

Current RPO under total process-memory loss is not established as an acceptable production objective.

For the selected Order, the experiment predicts complete loss of the in-memory state after restart.

P18 does not yet define a production RPO/RTO.

## Recovery time

Starting a new process may be fast.

But fast process recovery with missing business state is not correct business recovery.

## Negative knowledge

The absence of an Order after restart does not tell us whether:
- the customer never placed it;
- it existed and was lost;
- a different durable system has it.

Current architecture has no durable evidence to distinguish those possibilities after memory loss.
