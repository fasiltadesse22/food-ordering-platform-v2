# C1.1-P10 — Rule Classification Catalog

## Engineering question

Which rules define a valid business state, which merely establish structurally usable input, and which are persistence enforcement mechanisms?

## Classification

| Rule | Category | Current enforcement | Why |
|---|---|---|---|
| customerId must be nonblank | validation | HTTP Bean Validation + CustomerId | establishes usable identifier shape |
| restaurantId must be nonblank | validation | HTTP Bean Validation + RestaurantId | establishes usable identifier shape |
| quantity must be > 0 | validation / structural domain validity | HTTP Bean Validation + OrderLine | zero/negative quantity is not a meaningful line |
| unitPrice must be >= 0 | validation / structural domain validity | HTTP Bean Validation + OrderLine | current model disallows negative unit price |
| CANCEL transition requires PLACED | lifecycle precondition | Order state machine | operation eligibility at a point in time |
| cancellation actor must own Order | contextual guard | Order | operation-specific actor context |
| ORDER_CANCELLED history implies current CANCELLED state | business invariant | OrderInvariants | must hold for every valid representation |
| PREPARING requires acceptance + preparation history | business invariant | OrderInvariants | current state/history must not contradict |
| COMPLETED requires acceptance + preparation + completion history | business invariant | OrderInvariants | completion cannot exist without its required lifecycle history |
| refund requires recorded payment | contextual/temporal business rule | Order guard | eligibility depends on history |
| orders.customer_id NOT NULL | future DB constraint | not implemented | persistence integrity mechanism only |
| order_lines.quantity CHECK > 0 | future DB constraint | not implemented | storage-level reinforcement of structural validity |

## Critical distinctions

Validation asks:
"Can I form a structurally meaningful value/request?"

Precondition/guard asks:
"May this particular operation execute now in this context?"

Invariant asks:
"What must be true of every valid Order representation regardless of caller or adapter?"

Database constraint asks:
"What invalid persisted representation can the database itself refuse?"

The same business concern may be supported by several mechanisms, but the mechanisms are not interchangeable.

## Structurally valid but invariant-invalid example

These are all structurally valid values:
- OrderStatus.PREPARING
- ORDER_CANCELLED
- PREPARATION_STARTED
- valid participant enums
- valid Instants

But the combination:

current state = PREPARING
history contains ORDER_CANCELLED

is business-invalid because cancellation is terminal in the current lifecycle.

Passing type/shape validation therefore does not establish invariant validity.

## Guard versus invariant

Wrong restaurant accepting an otherwise PLACED Order fails a contextual guard.

The Order representation itself may still be perfectly valid before the attempt.

By contrast:

current state PREPARING
+
ORDER_CANCELLED history

is an invalid Order representation independent of who is currently calling it.

That is invariant territory.
