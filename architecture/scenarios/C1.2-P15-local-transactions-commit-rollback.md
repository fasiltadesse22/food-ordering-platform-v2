# C1.2-P15 — Local Transactions, COMMIT, ROLLBACK and Atomic Persistence

Authoritative scope: Course 2 Master Roadmap V8.0, derived Cluster 1.2 blueprint P15. Inherit frozen C1.2-P14 at 9143f1f627423ad8da4cef1a41c8ae20d0045775. Single Spring Boot deployable and Order aggregate, PostgreSQL V1/V2 schema, P12 JDBC adapter and validated P14 mapper. No new service/table/model merely to decorate transaction learning.

## Central question
When a valid immutable Order successor spans orders + order_lines + order_workflow_occurrences, can PostgreSQL commit all its related effects together or none, through actual SQL errors and abrupt session termination? What can the client know if COMMIT was attempted but its acknowledgement was lost?

## Business invariants and write set
Order.place: root identity + all initial lines + initial history, one consistency-boundary creation.
Accept: new status ACCEPTED + RESTAURANT_ACCEPTED occurrence (and full owned collections under current snapshot mapping).
Modify: replacement line contents + ORDER_MODIFIED occurrence.
Cancel: CANCELLED + ORDER_CANCELLED occurrence.
Local PAYMENT_RECORDED and REFUND_REQUESTED are Order-local facts; successful PostgreSQL COMMIT says nothing about external provider charging or refund settlement.
Current PostgresOrderRepository saveCurrent implementation: INSERT/UPSERT root, delete history, delete lines, batch insert lines, batch insert history, commit, all under one autoCommit(false) JDBC connection. A transaction can temporarily have a domain-inconsistent representation within its writer connection; uncommitted intermediate changes must not become separately authoritative. P13 row-local CHECK constraints apply, but full lifecycle completeness is enforced through selected domain checks/reconstruction not SQL.

## Failure windows
F0 Before connection/SQL: operation not yet attempted.
F1 After root insert/update, before child writes: rollback must restore old committed state or remove new root.
F2 After DELETE existing children, before replacement lines: rollback restores previous children.
F3 After replacement lines, before history: rollback restores root/lines/history together.
F4 Deferred trigger fails during COMMIT: even when all earlier SQL statements appear successful, PostgreSQL rejects the transaction. Independent observer confirms old committed state in tested case. Repository conservatively returns OrderCommitOutcomeUnknownException because COMMIT was attempted.
F5 Client loses COMMIT acknowledgement after database committed: caller receives an exception even though new Order/successor is authoritative. Test-specific JDBC dynamic proxy invokes genuine db.commit() then throws SQLState 08006 to simulate lost response. Caller cannot infer rollback from error.
F6 Uncommitted PostgreSQL backend terminated from independent connection: server aborts open transaction; old committed state remains.
F7 Separate SQL statements in default autocommit: status can commit alone and leave invalid status/history; P12 mapper detects InvalidPersistedOrderException. Negative control for missing transaction boundary.
F8 Success: new adapter retrieves whole committed Order with root, lines, history.
Read isolation and cross-statement snapshots remain P16. Stale last-writer-wins saveCurrent remains P17. Conflict/retry policy remains P18.

## Implemented production evolution
PostgresOrderRepository retains explicit JDBC transaction and the public OrderRepository interface. Adds a narrow package-private ConnectionSource constructor for deterministic test-only COMMIT acknowledgement failure after a real database commit. Public constructor keeps DriverManager and Flyway startup behavior. Tracks whether COMMIT was invoked:
- SQLException before COMMIT: attempt rollback; duplicate create-only SQLState 23505 still maps to OrderAlreadyExistsException, other SQL errors OrderPersistenceException.
- SQLException at/after COMMIT attempt: attempt rollback conservatively, raise OrderCommitOutcomeUnknownException (subclass of OrderPersistenceException) with original OrderId; this exception means no confirmed success, NOT confirmed rollback. Rollback after already successful COMMIT cannot undo the committed transaction. A SQL failure at COMMIT (e.g. deferred trigger) may actually have caused rollback; exception is conservative since the general client contract cannot prove the outcome.
- Runtime exception before or during DML attempts rollback and propagates; if rollback itself fails it is attached as suppressed. No automatic retries, provider actions, compensation or distributed transactions.
- OrderPersistenceException became nonfinal to support subtype.
- No change to Order state machine, optimistic versions, SQL schema, response contracts or general transaction isolation.

## Root-cause diagnosis
For Order status/history mismatch: compare business invariant, SQL transaction identifier, write timeline, COMMIT/ROLLBACK outcome, connection exception SQLState, independent post-error SELECT, and whether reader observed mixed snapshots (P16) versus committed invalid data (no transaction). A failed COMMIT acknowledgement alone is not proof of abort. Reconcile stable OrderId and operation identity; never blindly place an Order again with new UUID.
For duplicate create on retry: unique PK 23505 establishes identity conflict, not automatically same logical customer command. For provider payment: local transaction cannot atomically update provider authority.
