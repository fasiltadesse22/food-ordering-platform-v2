# C1.1-P15 — Repeated Commands and Replay Semantics

## Engineering question

When the same logical business intent appears again, what should repeated execution mean, how can the system know it is a replay, and which business effects/results must remain stable?

## Why repetition happens

A caller may repeat a command because:
- the first response was lost;
- a timeout occurred;
- the caller crashed before recording success;
- a UI was double-submitted;
- a network/client/proxy retried;
- a message was redelivered.

The repeated request may be identical at the transport level, but transport equality is not enough to establish logical identity.

## Lost-response timeline

T0 Order = PLACED
T1 Customer sends CANCEL
T2 server reads PLACED
T3 server creates/saves CANCELLED
T4 response is lost
T5 customer cannot know whether cancellation committed
T6 customer retries CANCEL
T7 server reads CANCELLED
T8 current implementation returns ILLEGAL_TRANSITION

Server state reached the desired result once.

Caller sees only the retry rejection.

Therefore:
state convergence != replay-stable outcome.

## Four different properties

### 1. State/effect convergence

Executing the operation repeatedly does not create additional current-state effect.

Sequential CANCEL currently has this property in the selected lifecycle because after the first transition the second is illegal.

### 2. Duplicate detection

The server knows:
"I have already processed this exact logical command."

Current CANCEL path does not have this property because it has no command identity.

### 3. Duplicate suppression

A repeated execution is prevented from producing another effect.

REFUND_REQUESTED currently has explicit semantic suppression through REFUND_ALREADY_REQUESTED.

Sequential CANCEL is suppressed indirectly by terminal lifecycle state.

### 4. Result replay

A retry can receive the same previously committed business result without re-executing the effect.

Current CANCEL and REFUND paths do NOT implement this.

## Same payload is insufficient

Two requests with:
orderId=O1
customerId=C1
operation=CANCEL

could be:
- retry of the same logical cancellation;
- a second intentional cancellation attempt;
- duplicate proxy delivery;
- concurrent duplicate delivery.

Without an identity token/command ID the server cannot distinguish them.

## Command identity

A future replay-aware contract may require a logical identifier scoped to:
- actor/account;
- operation;
- target resource;
- retention window.

The exact design is deferred.

## Correlation versus identity

Correlation ID:
groups observations/trace activity.

Request ID:
often identifies one transport attempt.

Idempotency key/logical command ID:
is intended to identify retries of one logical effect.

They can be related but are not interchangeable.

## Concurrent duplicates

If two duplicate cancellations both read PLACED before either saves:
- both can execute;
- both can return Accepted;
- final Order may still look as though cancellation happened once.

That final convergence does not prove at-most-once execution.

If an external effect existed inside the operation, it might have happened twice.

## Replay result semantics

Possible future choices include:
- return the original Accepted result;
- return an explicit AlreadyApplied result;
- reject as current-state conflict;
- return current resource representation.

The correct contract is business/API-specific.

P15 does not choose a universal rule.

## Critical safety boundary

Never infer:
"cancellation looks idempotent"
therefore
"payment is safe to retry."

Cancellation currently changes one local immutable lifecycle representation.

Payment may later invoke an external independently committed effect.

P16 owns that pressure.
