# C1.1-P03 — Intent, Command, Decision, Outcome and Fact

## Engineering question

When does requested intent become an accepted business fact?

## Semantic chain for Place Order

Customer goal
  → "I want to order these items" — intent
  → HTTP PlaceOrderRequest — transport representation
  → PlaceOrderCommand — application instruction
  → PlaceOrderService decision
      → rejected: PlaceOrderResult.Rejected, no Order state persisted, no OrderPlaced fact
      → accepted: create Order, save current in-process state, create OrderPlaced fact, return PlaceOrderResult.Accepted

## Required distinctions

### Intent != command

Intent is what the actor wants to achieve.

PlaceOrderCommand is the application-level instruction expressing that intent in a form the application can evaluate.

The same intent could arrive through another adapter later.

### Command != fact

PlaceOrderCommand says: please attempt to place this order.

OrderPlaced says: the placement decision was accepted and, in the current model, the resulting order became part of the application's current state.

A command may be rejected. A fact describes something accepted as having happened.

### Requested != accepted

Receiving a syntactically valid request does not make the requested business outcome true.

P03 demonstrates this with an invalid actor command:

Restaurant operator → PlaceOrderCommand → REJECTED

No order is persisted and no OrderPlaced fact is returned.

### Decision != result type

The decision is the application behavior that evaluates the command.

PlaceOrderResult.Accepted / Rejected is the explicit representation of that decision's outcome.

### Domain fact != integration message

OrderPlaced is an in-process semantic fact.

It is not a Kafka record, outbox row, Avro/JSON integration contract, message envelope, event-store record, or evidence of event-driven architecture.

### Event object != event-driven architecture

Creating an immutable object named after a completed business occurrence does not create an event-driven system.

EDA requires architectural communication/decoupling choices that have not been justified.

## Current acceptance boundary

For the executable P03 slice, PlaceOrderService first decides actor eligibility.

Rejected path:

command received
→ decision rejects
→ Rejected result
→ repository remains unchanged
→ no OrderPlaced fact

Accepted path:

command received
→ decision accepts actor eligibility
→ domain constructs valid Order
→ current repository saves Order
→ OrderPlaced fact is constructed
→ Accepted result returns Order + fact

## Important qualification

The word fact is scoped to the current model.

Cluster 1.1 still uses transient in-memory state. P03 does not prove durable historical truth after process loss.

Part 1.1.4 will deepen identity and authoritative-state reasoning; Part 1.1.18 will explicitly test process-crash and durability non-guarantees.

## Why fact construction is after the current save

The current application result reports OrderPlaced only after the repository save call returns successfully.

This avoids returning a successful fact result if the application's current state update has not completed.

It does not claim distributed atomicity, durable commit, or exactly-once behavior.

## Structural/validation failure remains separate

An empty order is still rejected by existing domain validation via IllegalArgumentException.

P03 does not create the final business-vs-technical failure taxonomy. Part 1.1.9 deepens that distinction, and Part 1.1.10 distinguishes validation rules, invariants and database constraints.

The P03 result model is intentionally narrow: it makes one acceptance/rejection decision explicit without prematurely solving all future failure semantics.
