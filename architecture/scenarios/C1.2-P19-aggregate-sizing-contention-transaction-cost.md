## Business scenario and engineering question
Order is currently one aggregate holding identity, customer/restaurant references, current status, commercial OrderLine values and ordered workflow occurrences, and one optimistic version. Its invariants require internally consistent state/history and local atomic state changes. What costs occur when lines or history grow, and how do shared-identity writers contend? What evidence, not DDD vocabulary, justifies changing persistence representation versus domain consistency boundary?

## Inspected mechanism
P15 JDBC PostgresOrderRepository saveCurrent: conditional UPDATE orders root+version (P17) first; DELETE EVERY order_workflow_occurrences and EVERY order_lines row; re-INSERT EVERY current line and history occurrence; COMMIT once. Root UPDATE locks the Order row until transaction ends, so child rewrite work can prolong lock tenure. No JPA dirty checking and no pooled data source; DriverManager connection per operation. P16 read uses read-only REPEATABLE READ with THREE SELECT statements (root, lines, workflow) and reconstructs one immutable Order with List.copyOf and selected history-scanning invariants. P18 allows at most one fresh-state re-evaluation for selected local lifecycle commands, so conflicts have workload/resource consequences.

## Cost model (not measured latency)
Let L=owned line count,H=current workflow occurrence count. Full read: 3 SQL statements, 1+L+H result rows for found Order, excluding additional metadata. Recording one local milestone performs root UPDATE (one root-row version comparison), child DELETE count L+H, child INSERT count L+(H+1), total 2L+2H+1 child-row DELETE/INSERT operations. Domain new successor copies H history references and creates immutable collection storage, asymptotic O(H) for copying; does not deep-copy each historical occurrence object. Costs vary with indexes/WAL/buffer usage/connection setup, so operation counts are neither bytes nor p99.
Examples: small (L=1,H=0): 2 rows read, 3 child changes; medium (8,16): 25 read, 49 changes; larger (48,96): 145 read, 289 changes. Old (12,24) single milestone needs 12 line deletes +12 line inserts +24 history deletes +25 history inserts=73 child operations.
Current root revision is aggregate-wide, so line replacement and payment milestone from same revision can conflict even with conceptually different touched fields. Different Order identities do NOT share a version CAS row, though they share physical DB resources.

## Important distinctions
1 Logical aggregate size (business invariants and ownership) != relational row count != serialized byte size != hot-writer cardinality.
2 Aggregate boundary != database table != service/bounded-context boundary.
3 Full-child rewrite inefficiency does NOT prove aggregate split is correct.
4 Database root row locking during transaction != indefinite pessimistic lock across application read. Plain MVCC readers may proceed under P16 snapshot.
5 One statement query joining two collections could multiply rows L*H; fewer round trips need not reduce transferred data.
6 P17 optimistic version conflict is a correctness outcome, not automatically a failure: P18 decides allowed retry and cost.
7 Keeping OrderLine and local required workflow facts together protects selected invariants. Do NOT move status and required history into separate authorities without full atomic consistency replacement, nor absorb independent Restaurant/Payment truth into Order.

## Architecture forces, alternatives and trade-offs
A Current full snapshot rewrite is simple and was useful for P15-P17 correctness, but updates unrelated owned rows. B Append-only history writes + CAS root in same SQL txn could reduce write operations from O(H) to O(1) per local milestone without splitting aggregate; must check prefix continuity, ordering, duplicate/rollback/version. C Differential line update could reduce unchanged-line writes but adds mapping/order diff complexity; validate before optimization. D Split Order and workflow history into independent aggregates reduces shared version contention only if invariants can be enforced across boundaries and failure cases; P20 scope warns artificial boundary. E Split all per-field versions may permit incompatible domain changes and undermine root invariant. F Fold Restaurant/Payment into Order worsens independent authority coupling; not justified. G Read-model summaries/materialization can optimize particular query shape but adds consistency/refresh semantics. H Global locks or Kafka not a solution to this local size issue.
P19 decision: retain selected logical Order boundary; characterize and preserve baseline; do not prematurely optimize production JDBC or split state without measured workload/quality-attribute evidence. Introduce no migration, microservice, cache, queue or provider interface.

## Quality-attribute connection
Data integrity and local consistency protected by one P15-P17 transaction+version. Performance risks: grows read result and child row rewrite, WAL/index activity, JVM copying; transaction duration may increase while root row lock held. Scalability and throughput depend on conflict rate on hot Order and database capacity. Reliability: P18 bounded retry can amplify load, but preserves history; monitor retry rate. Availability: excessive lock waits can consume JDBC connections (current no pooling). Maintainability: append/diff adds complexity vs full rewrite clarity. Observability: track L,H bytes, read/write p50/p95/p99, attempt count, CAS conflicts, wall transaction time, lock wait, pg_stat_activity, pg_stat_user_tables, pg_stat_wal, JVM alloc/GC, and PostgreSQL EXPLAIN ANALYZE BUFFERS/WAL with careful impact. No numeric SLO asserted.

## Production diagnostic chain
Symptom: p99 order write latency rises and 409 conflicts increase on long-history Orders.
Scope: per Order identity; L,H, command, traffic, deployment; distinguish hot Order vs global DB CPU/connection saturation.
Timeline: read snapshot at version V -> domain successor -> root CAS lock acquired -> child delete/insert -> commit -> competitor wait/zero-row conflict -> bounded re-evaluation.
Evidence: actual SQL statement counts, audit trigger row counts, lock waits pg_stat_activity, per-identity conflicts, connection timing, WAL/log bytes, response p95/p99, DB resource.
Hypotheses: child rewrite amplification, oversized logical aggregate, high request arrival, long transaction, connection setup, query index issues, client duplicate submissions, pathological retries.
Discriminating tests: isolate line/history count and identical workload, run same vs distinct Order concurrency; compare full rewrite against append/diff prototype only after controlled requirements; test before/after invariant preservation.
Mitigation: narrow SQL write delta first if measured bottleneck, shorten critical section, avoid unnecessary retries, consider boundary changes ONLY with business invariant and independent authority analysis. Validate conflict/currentness, status/history, read snapshot, P12 durable recovery, no regressions.
Transfers: banking ledger account vs immutable postings; reservation inventory holds; both must distinguish local atomic invariant from append log growth.
