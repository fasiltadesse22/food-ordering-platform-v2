# C1.2-P22 — Staff/Principal Architectural Defense and Cluster Mastery Exit Gate

## Architecture review exercise (45–70 min, practice time not CI assertion)
Present actual Food Ordering Platform starting from business invariants: actors -> use cases -> identity -> value semantics -> required state -> Order root -> status/history/lines guarantees -> transaction and isolation -> CAS -> retry taxonomy -> aggregate sizing -> undersized boundary -> domain service & independent stock/payment authority. For every step name actual source, observed test, assumptions and nonclaims.
Design prompts:
1. Customer places and modifies PLACED Order; explain owner guard, immutable successor vs authoritative persisted state and version.
2. Two restaurant staff accept/reject same v0 concurrently; derive at-most-one CAS publication and domain re-evaluation after conflict.
3. DB history INSERT fails after root UPDATE; predict SQL rollback and what caller knows. Change to failure during COMMIT; predict uncertainty, not assumed rollback.
4. Split Order status and history into two commits because p99 increased. Demonstrate actual P20 corruption and defend append-only physical optimization.
5. Hot stock item capacity1, two Orders each observe stock1. Distinguish pure planning vs authoritative admission; one same-DB transaction vs two independent commits.
6. Provider captured money but local PAYMENT_RECORDED absent. Diagnose authority and reconciliation, don't infer provider success or failure from Order version.
7. Restaurant accepts Order while Restaurant availability changes. Demand business requirement: authoritative Restaurant operational truth not yet implemented; don't invent strong consistency.
8. 'One table = one aggregate = one service': refute with real project, separate context definition later Cluster1.3.
9. Hypothetical Order with 200 history events: quantify 2L+2H+1 actual child-row operations, explain measure vs p99 claim, compare future options.
10. Justify why cluster exit does not imply full payment/inventory/restaurant feature completion. Identify exact next contracts.

## Five-level architectural English
Concept: explain business invariant and aggregate in 60–90 sec.
Mechanism: explain actual Postgres write path root CAS -> DELETE/INSERT children -> COMMIT and read REPEATABLE READ 2–3 min.
Application: trace Order placement, local payment, cancellation, refund and full recovery with fresh JVM 3–5 min.
Failure: status/history split and stock-first/order-first partial, commit uncertainty, stale overwrite, SQLState classifier; causal diagnosis 5 min.
Trade-off: defend one Order aggregate vs two status/history commits, physical append-only mapping, local shared transaction vs networked independent authority 5–7 min.
Adapt same explanation: backend engineer (JDBC and code), Staff architect (invariant and failure knowledge), engineering manager (business impact/risk and tested guarantees), nontechnical (why an Order can't be 'accepted' without proof, and stock observation != reservation). Assess technical accuracy, causal detail, clarity, spoken flow, audience adaptation independently.

## Independent transfer
Bank transfer: account or ledger invariants, idempotent transfer operation identity, transaction rollback vs external bank confirmation, domain decisions and authoritative funds admission.
Hotel reservation: shared room capacity, two eligible booking plans vs one actual admission, expiry, payment uncertainty, per-room hot keys, context translation.
Never present these as implementations of Food Ordering Platform.

## Exit grading matrix
A: boundary derivation (Order vs Restaurant/Payment/Inventory) with explicit invariant and authoritative evidence.
B: predict actual SQL row state before, during and after COMMIT and SIGKILL; distinguish known abort from unknown commit.
C: predict concurrency (CAS and stock conditional update) and why mere Java immutability is not concurrency safety.
D: diagnose one real reproducible failure with hypothesis and discriminating test, not only exception label.
E: compare simpler and over-engineered alternatives with quality attributes, complexity and operational pressure.
F: demonstrate ability to explain at five levels and transfer to unrelated banking/hotel.
G: actual GitHub exact verified cluster checkpoint, root Maven+Testcontainers and process restart.
Pass only with evidence, not vocabulary recall. Where production requirement unavailable, state missing question and what would make it answerable rather than inventing a rule.
