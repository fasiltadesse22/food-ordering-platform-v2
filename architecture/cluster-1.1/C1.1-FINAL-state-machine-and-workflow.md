# C1.1-FINAL — State Machine and Workflow Map

## Cluster question

What must remain correct regardless of the eventual architecture?

## Current Order lifecycle

```text
                      ACCEPT
              +--------------------+
              |                    v
           PLACED              ACCEPTED
          /      \                  |
    REJECT        CANCEL             | START_PREPARATION
      |              |               v
      v              v           PREPARING
   REJECTED       CANCELLED           |
    terminal        terminal          | COMPLETE
                                      v
                                  COMPLETED
                                   terminal
```

Implemented legal transitions:

- PLACED -> ACCEPTED
- PLACED -> REJECTED
- PLACED -> CANCELLED
- ACCEPTED -> PREPARING
- PREPARING -> COMPLETED

Terminal in the current Order lifecycle:
- REJECTED
- CANCELLED
- COMPLETED

Terminal means no later OrderStatus transition is currently modeled.

It does not mean no later workflow/compensating action can occur.

## Orthogonal workflow occurrences

The current Order can also record:

- PAYMENT_RECORDED
- REFUND_REQUESTED
- ORDER_MODIFIED

These do not constitute OrderStatus transitions.

Current selected rules:
- ORDER_MODIFIED requires PLACED and owning Customer;
- REFUND_REQUESTED requires PAYMENT_RECORDED and current REJECTED/CANCELLED;
- repeated REFUND_REQUESTED is rejected;
- PAYMENT_RECORDED currently has no state/context duplicate guard.

## End-to-end workflow candidates retained from discovery

### Selected happy path

```text
Customer places Order
    -> PLACED
    -> PAYMENT_RECORDED
    -> Restaurant ACCEPT
    -> ACCEPTED
    -> START_PREPARATION
    -> PREPARING
    -> COMPLETE
    -> COMPLETED
```

This is a selected learning path, not a universal food-ordering policy.

### Paid rejection

```text
PLACED
 -> PAYMENT_RECORDED
 -> REJECT
 -> REJECTED
 -> REFUND_REQUESTED
```

REFUND_REQUESTED is a compensating-action request.
It does not erase PAYMENT_RECORDED.

### Cancellation before payment

```text
PLACED
 -> CANCEL
 -> CANCELLED
```

### Cancellation after recorded payment

```text
PLACED
 -> PAYMENT_RECORDED
 -> CANCEL
 -> CANCELLED
 -> REFUND_REQUESTED
```

## Current unresolved workflow policies

Cluster 1.1 intentionally does not decide:
- whether payment must happen before or after restaurant acceptance;
- authorization versus capture semantics;
- whether cancellation after ACCEPTED should be permitted under another business command;
- whether payment after cancellation should be forbidden;
- whether modification after payment should be forbidden;
- final refund-provider completion semantics;
- real external payment authority design.

## Critical distinctions

workflow != state machine.

command != fact.

intent != accepted fact.

terminal lifecycle state != no future business action.

refund/compensation != rollback.

current selected state machine != eternal universal business policy.
