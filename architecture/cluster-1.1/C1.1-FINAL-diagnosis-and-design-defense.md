# C1.1-FINAL — Diagnosis and Design Defense

## Diagnosis method

For any correctness incident use:

symptom
-> scope
-> timeline
-> evidence
-> competing hypotheses
-> discriminating test
-> mechanism
-> causal chain
-> mitigation
-> validation

A timeout, exception, HTTP status, metric or log line is evidence.
It is not automatically the root cause.

## Example diagnosis — CANCELLED later appears PLACED

### Symptom

An Order observed as CANCELLED later appears PLACED.

### Competing hypotheses

- stale whole-object replacement;
- incorrect persistence mapping/manual data edit;
- wrong Order/environment;
- restoration from an old snapshot;
- bug bypassing domain transition path.

### Discriminating evidence

P17 already proves:
- retain old PLACED;
- current becomes CANCELLED;
- evolve stale PLACED;
- unconditional save;
- current returns to PLACED.

### Mechanism

saveCurrent carries no expected version and accepts an obsolete successor.

### Mitigation direction

Once real persistence exists:
- bind write to expected authoritative version/state;
- convert conflict to explicit application/domain handling;
- re-evaluate intent against fresh state.

### Validation

Reuse the P17 stale-state scenario and require stale commit rejection.

## Example diagnosis — customer charged twice, Order shows one payment

P16 provides one causal hypothesis:

provider charge #1 commits
-> response lost
-> no local payment fact
-> retry
-> provider charge #2 commits
-> local payment fact written once.

Do not infer this from symptom alone.
Use payment-operation/provider/request evidence when such identities exist.

## Design defense — why one deployable remains correct

Cluster 1.1 evidence concerns business correctness, not service-decomposition pressure.

Splitting Order, Payment and Restaurant into services would add:
- network uncertainty;
- deployment boundaries;
- more distributed consistency problems;

without solving the current local correctness requirements.

Therefore the single deployable remains the simplest defensible topology.

## Design defense — why in-memory authority was retained through P18

It exposed:
- domain semantics;
- races;
- stale-state behavior;
- durability failure;

without hiding them behind DB/framework behavior.

P18 now supplies evidence that this adapter must eventually stop being the sole production authority.

## Design defense — why PostgreSQL belongs next, not earlier

The requirement is now concrete:
- acknowledged Order state must survive process replacement;
- local atomicity needs a durable transactional mapping;
- stale concurrent writes need an authority-level conflict mechanism;
- future constraints need executable relational enforcement.

Cluster 1.2 is where aggregate/consistency boundaries and real relational persistence are derived together.

## Design defense — why not Kafka/Saga/Outbox yet

Current evidence does not require asynchronous inter-service coordination.

The platform first needs:
- correct aggregate boundaries;
- durable local state;
- local transactions;
- concurrency semantics.

Adding distributed workflow patterns before those are known would multiply failure modes without solving the immediate proven failures.

## Adversarial follow-ups

### "Traffic becomes 10x tomorrow."

C1.1 contains no throughput/capacity evidence.
Do not introduce sharding/microservices from this statement alone.
Measure workload/saturation in the appropriate later clusters.

### "We need zero duplicate payments."

Now ask:
- what identifies one logical payment?
- which authority owns charge truth?
- what retry window/provider semantics exist?
P16 proves the risk; later idempotency/payment evolution must implement the mechanism.

### "Use a distributed lock to fix races."

Current authority will soon be one relational DB.
A DB version/transaction tactic is simpler and aligned with authority.
A distributed lock would add failure/lease/fencing complexity before evidence requires it.

### "The app restarted quickly, so availability is good."

P18 proves compute recovery can coexist with lost business state.
Business availability must include ability to continue prior Orders correctly.
