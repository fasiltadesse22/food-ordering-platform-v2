# C1.1-FINAL — Invariant and Contract Catalog

## Construction/value correctness

Current model requires:
- Order identity exists;
- CustomerId and RestaurantId exist;
- an Order has at least one line;
- line identity/name are nonblank according to current constructors/validation;
- quantity is positive;
- unit price is nonnegative;
- total is derived from lines rather than independently mutable.

These rules may be enforced through value/domain construction today.
They are semantic rules; a future DB constraint would be an enforcement mechanism, not the invariant itself.

## Lifecycle/history invariants enforced by OrderInvariants

Current Order construction verifies:

1. ORDER_CANCELLED history requires current status CANCELLED.
2. RESTAURANT_REJECTED history requires current status REJECTED.
3. ORDER_COMPLETED history requires current status COMPLETED.
4. PREPARATION_STARTED history requires PREPARING or COMPLETED.
5. ACCEPTED current state requires RESTAURANT_ACCEPTED history.
6. PREPARING current state requires RESTAURANT_ACCEPTED and PREPARATION_STARTED.
7. COMPLETED current state requires RESTAURANT_ACCEPTED, PREPARATION_STARTED and ORDER_COMPLETED.

These are representation invariants for one Order object.

They do not guarantee:
- no stale whole-object replacement;
- no lost decision;
- durability;
- external payment truth.

## Operation preconditions and guards

| Operation | State precondition | Contextual guard |
|---|---|---|
| Accept | PLACED | acting RestaurantId owns Order |
| Reject | PLACED | acting RestaurantId owns Order |
| Cancel | PLACED | acting CustomerId owns Order |
| Start Preparation | ACCEPTED | acting RestaurantId owns Order |
| Complete | PREPARING | acting RestaurantId owns Order |
| Modify Lines | PLACED | acting CustomerId owns Order |
| Request Refund | REJECTED or CANCELLED | PAYMENT_RECORDED exists and no prior REFUND_REQUESTED |
| Record Payment | none currently | none currently |

## Stable successful postconditions for lifecycle evolution

Current normal lifecycle evolution preserves:
- OrderId;
- CustomerId;
- RestaurantId;
- lines unless the operation is Modify Lines;
- placedAt;
- derived semantics associated with unchanged lines.

Successful lifecycle transition also appends the corresponding workflow occurrence.

## Guard versus invariant

"Wrong restaurant cannot accept" is a contextual guard.

It is not an invariant of an already-valid Order representation.

"COMPLETED must carry acceptance/preparation/completion history" is an invariant.

## Validation versus invariant

A request body may be structurally invalid before a domain object exists.

An invariant concerns states the domain considers valid.

Some semantic rules can be enforced at more than one boundary, but the semantic rule must not be confused with the mechanism.

## Atomicity requirement

For lifecycle decisions represented simultaneously by:
- current status;
- matching workflow occurrence;

the two must become authoritative together.

The current immutable Order evolution achieves one local logical publication.

That does not make repository read -> decide -> save atomic across competing writers.

## Temporal correctness requirement

A decision whose correctness depends on authoritative state must not become authoritative after relevant state changed without conflict detection/revalidation.

Current implementation does not guarantee this.

## Durability requirement now justified

Acknowledged Order business state must eventually outlive one application JVM/process.

Current implementation does not satisfy this requirement.

## External-effect requirement now justified

One logical payment operation must not multiply an independently committed financial effect merely because delivery/retry repeats.

Current production model has no real external payment/idempotency mechanism yet.
