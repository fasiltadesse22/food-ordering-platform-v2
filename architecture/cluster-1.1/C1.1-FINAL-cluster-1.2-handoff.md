# C1.1-FINAL — Cluster 1.2 Handoff

## Exact inherited baseline

Cluster 1.2 must start from the final verified C1.1 commit/branch produced by P19.

Do not regenerate the application.

Do not skip directly to multiple services.

## Evidence-backed forces carried forward

### 1. Durable state

P18:
a real CANCELLED Order disappeared after JVM replacement.

Required next capability:
durable Order authority/recovery across application-process replacement.

### 2. Consistency boundary

P10/P11:
lifecycle status and matching history contain invariants that must move together.

Required next reasoning:
which Order state belongs inside one aggregate/transaction consistency boundary?

### 3. Concurrency/version conflict

P13/P14/P17:
multiple or stale writers can make individually valid local decisions and overwrite newer authority.

Required next capability:
authority-level conflict detection/serialization consistent with aggregate boundaries.

### 4. Relational constraints

P10 distinguished semantic invariant from DB enforcement.

Required next work:
map selected enforceable invariants to real PostgreSQL schema constraints without pretending DB constraints replace the domain model.

### 5. Atomic durable transaction

P11 demonstrated partial-state windows if one logical decision is split.

Required next work:
map one aggregate decision to an actual local transaction and experimentally validate rollback/commit behavior.

## Cluster 1.2 scope contract

Engineering question:
Which state and rules belong together because they must remain consistent together?

Required distinctions include:
- entity != row;
- value object != DTO;
- aggregate != table;
- aggregate != bounded context;
- aggregate boundary != service boundary;
- transaction boundary != deployment boundary.

## Authorized mechanisms for Cluster 1.2

The roadmap authorizes Cluster 1.2 to introduce real durable relational persistence when justified by the aggregate/consistency reasoning.

Expected evolution pressure includes:
- PostgreSQL;
- migrations;
- Testcontainers/equivalent reproducible DB tests;
- local transactions;
- selected DB constraints;
- optimistic concurrency implications.

These must still be derived from actual invariants; they are not blanket defaults.

## Explicitly still deferred

Unless separately justified later:
- Kafka;
- Redis;
- Saga;
- Outbox;
- CQRS;
- Event Sourcing;
- independent Spring Boot services;
- distributed locks;
- database-per-service;
- Kubernetes/AWS topology.

## Regression expectations

Cluster 1.2 should preserve or consciously update:
- P06 lifecycle legality;
- P07 actor/guard behavior;
- P08 terminal/compensation semantics;
- P09 failure taxonomy;
- P10 invariant semantics;
- P11 atomicity expectations;
- P12 claim-strength discipline.

It should use P13/P14/P17 failures as before-state evidence and eventually show how the selected persistence/concurrency mechanism changes those outcomes.

It should rerun a P18-equivalent restart scenario and demonstrate recovery from durable authority.

## Handoff question

Cluster 1.2 begins only after the learner can explain:

Why is Order likely to be one immediate consistency boundary today, what evidence could force that boundary smaller/larger, and why does that still not imply one future microservice?
